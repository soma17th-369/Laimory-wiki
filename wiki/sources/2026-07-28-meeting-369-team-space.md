# 369팀 스페이스 회의 - 2026-07-28

## 개요

AI 타임라인 생성의 데이터 정합성, AI 서버의 직접 DB 접근 제거, 모바일 테스트 앱의 전체 흐름을 함께 점검한 개발 회의다. `source_id`와 `row_id` 용어 불일치, 불필요한 내부 ID가 LLM 입력에 섞이는 문제, JSON 필수 필드가 보장되지 않는 문제를 AI 출력 실패의 유력 원인으로 파악했다. AI 서버가 RDB를 직접 수정하지 않고 API 서버를 통해 조회·저장하도록 바꾸며, 서버 간 요청은 API 서버가 관리하는 토큰으로 인증하는 방안을 검토했다.

모바일에서는 타임라인 조회·수정·삭제 흐름과 디버그용 데이터 수집 화면이 연결됐고, 실제 앱 테스트 중 FCM 발송 실패, 3분 폴링 만료, 콜백 저장 실패와 에러 코드 타입 불일치가 발견됐다. 팀은 테스터 앱으로 각자 타임라인을 생성하고 사소한 문제까지 알파 테스트 페이지에 기록해 프롬프트와 사용자 흐름을 개선하기로 했다. Redis Lua 스크립트가 실제로 강한 원자성을 요구하는 구간에만 필요한지, 인프라 메모리 경고를 스펙 상향과 임계값 조정 중 어떻게 다룰지는 추가 검토 과제로 남았다.

## 상세 요약

### AI 데이터 정합성과 구조화 출력

- 에이전트별로 같은 식별자를 `source_id`와 `row_id` 등 다르게 부르고 있었고, 표준 용어를 `row_id`로 통일하는 작업을 진행 중이었다. (`0:41–1:51`)
- 원본 항목에 불필요한 내부 ID를 별도로 부여하고 LLM이 두 ID 중 하나를 선택하는 로직 때문에 잘못된 ID가 결과에 포함된 것으로 판단했다. (`1:56–3:13`)
- LLM API가 제공하는 구조화 출력 기능을 사용해 JSON 형식과 필수 필드를 보장하도록 수정 중이며, 기본적인 형식 실패가 줄어들 것으로 기대했다. (`3:15–4:15`)

### AI 서버의 직접 DB 접근 제거

- AI 서버가 RDB를 직접 수정하는 대신 API 서버가 입력 조회와 결과 저장을 책임지도록 조회·저장 API를 추가하는 작업이 진행 중이었다. (`4:17–4:58`)
- 기존 콜백 토큰을 각 서버 호출에서 검증·갱신하는 체인 방식이 제안됐다. API 서버가 토큰 관리 주체가 되고 AI 서버는 받은 토큰을 다음 요청에 전달하는 구조다. (`4:58–7:25`)
- HMAC으로 추정되는 서버 간 인증도 논의됐지만 아직 적용된 곳이 없어, 모든 서버 간 호출에 공통 적용할 별도 이슈로 넘기기로 했다. (`7:27–8:49`)

### 모바일 앱 연결과 테스트 흐름

- 테스트 앱 배포, API 응답의 문자열 ID를 정수형으로 바꾸는 변경, 타임라인 전체 조회·수정·삭제가 앱에서 연결됐다고 보고됐다. (`9:10–12:03`)
- 현재 수집 흐름은 사진·헬스·일정 데이터를 디버그 화면에서 직접 눌러 인앱 DB에 적재한 뒤 초안 생성에 사용하는 방식이며, 사용자 흐름에 맞춘 자동화가 필요하다. (`23:03–29:23`)
- 완성된 타임라인은 이벤트 유형, 제목, 설명, 사진, 메모를 수정하고 이벤트를 삭제할 수 있는 UI로 연결됐으나 일부 수정 동작 오류가 현장에서 발견됐다. (`32:34–36:03`)

### FCM, 폴링과 콜백 장애

- FCM이 오지 않는 원인을 확인한 결과 Firebase 발송 자체가 실패했지만 로그 레벨이 낮아 놓친 것으로 보였다. 로그 수준을 오류로 올려야 한다는 의견이 나왔다. (`17:59–18:24`)
- 회의 중 타임라인 생성은 AI 서버까지 전달됐지만 3분 이상 걸려 폴링이 만료됐고, 이후 콜백 저장도 실패했다. (`18:33–20:26`, `30:25–36:38`)
- 콜백 요청의 `error_code`를 API 서버는 정수로 바꿨지만 AI 서버가 문자열로 보내 400 응답이 발생한 것으로 확인했다. AI 서버도 정수형으로 통일하기로 했다. (`46:13–51:58`)
