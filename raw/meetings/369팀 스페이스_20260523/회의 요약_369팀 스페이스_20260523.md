# 369팀 스페이스 회의 - 2026-05-23

## 개요

기획심의 초안을 공동 검토하고 멘토에게 전달하기 전 문구, 경쟁 분석, 추진 일정, 위험 대응, 사용자 검증 계획을 다듬은 장시간 작업 회의다. 팀은 스마트폰에 흩어진 데이터를 연결해 타임라인과 회고를 제공하고, 이를 장기적으로 사용자의 실제 삶을 이해하는 퍼스널 AI 메모리로 확장한다는 기획 의도를 정리했다. 자동 수집으로 오해될 수 있는 표현, AI가 데이터를 "판단"한다는 모호한 표현, 기존 서비스 비교표의 기준을 구체화하는 작업이 이어졌다.

개발 측면에서는 AI 출력 품질, 서버 과부하, Android 권한·배터리, 개인정보 보호를 주요 위험으로 보았다. 부하 테스트로 필요한 서버 사양을 선제 검증하고, 서버에 보내는 개인 식별 정보를 최소화한다는 대응 방향은 합의됐지만 AI 품질 검증 방법과 모델 선택은 멘토의 도움이 필요한 미결 과제로 남았다. 베타 테스터, 앱스토어 리뷰, 설문, GA4 등의 피드백 채널과 기능별 성공 지표도 검토했다. 커뮤니티 기능은 리텐션을 높일 확장안으로 논의됐으나 목적과 형태가 불명확해 멘토 피드백 이후 결정하기로 했다.

## 상세 요약

### 기획 의도와 용어 정리

- 첫 번째 기획 의도는 스마트폰에 흩어진 정보를 연결해 타임라인 형태로 정리하고 회고할 수 있게 하는 것이었다. 기존 셀프 트래킹 서비스가 직접 입력에 크게 의존한다는 한계를 줄이려 했다. (`0:34–1:48`)
- `자동으로 수집`이라는 표현은 운영체제 데이터 접근을 과장하거나 오해를 낳을 수 있어, `연결`, `통합`, `축적`, `손쉽게` 같은 표현을 검토했다. (`2:22–4:19`, `2:20:19–2:20:51`)
- 사진, 캘린더, 이동 동선, GPS, Health Connect, 앱 사용 정보 등을 단순 수집하는 것이 아니라 AI가 하루의 맥락으로 구성한다는 의도를 담고자 했지만, `판단`이라는 단어는 모호하다는 의견이 나왔다. (`6:46–8:57`)
- 퍼스널 AI 메모리는 실제 생활 데이터를 바탕으로 삶의 흐름을 이해하고 대화·회고를 지원하는 장기 방향으로 설명됐다. (`1:49–2:18`, `10:25–10:43`, `21:48–23:04`)

### 주요 기능과 경쟁 서비스 비교

- 주요 기능 설명은 기능마다 한 줄 수준으로 줄이고, 타임라인·기록 복원·회고·퍼스널 AI 챗의 관계를 더 명료하게 표현하기로 했다. (`9:01–10:24`)
- 경쟁 사례로 플랫폼 기반 저널링, AI 저널링, 웨어러블 기반 기억 보조 서비스 등이 검토됐다. 플랫폼 서비스는 기기 데이터 추천을 제공해도 최종 기록은 수동 작성이라는 한계가 있다고 봤다. (`14:24–19:03`)
- 팀 서비스의 차별점은 여러 생활 데이터를 연결해 자동 기록과 회고를 제공한다는 것이지만, 비교 대상마다 범위가 달라 하나의 표에서 같은 기준으로 단점과 차별점을 정리하기 어렵다는 문제가 있었다. (`28:10–37:22`)

### 역할, 일정과 결과물

- 팀 역할은 AI, 백엔드, Android로 포괄적으로 정리하고 멘토 역할은 각 전문 분야의 구체적 조언 중심으로 기술하기로 했다. (`40:27–41:24`)
- 추진 일정은 기획·분석, UI/UX, 시스템·DB·API 설계, MVP 개발, 1·2차 확장, 운영·테스트로 구성했다. 구독 결제는 MVP 이후 확장 기능으로 두는 안이 제시됐다. (`41:59–44:54`)
- 완성 서비스의 운영·배포, 사용자 피드백, 유지보수도 결과물과 일정에 포함하는 방향으로 정리했다. (`44:34–45:18`)

### 예상 문제와 기술 대응

- AI는 품질 불안정, 백엔드는 사용자 증가 시 과부하와 응답 지연, Android는 권한 정책과 배터리 사용을 주요 개발 위험으로 선정했다. (`47:39–49:24`)
- AI 품질 문제의 해결책으로 호출 제한과 결과 캐싱을 쓰는 문구는 비용 절감과 품질 개선을 혼동한다는 이유로 삭제하기로 했다. 품질 검증 방법은 AI 분야 멘토의 도움이 필요한 과제로 남았다. (`51:07–53:29`)
- 동시 요청 부하 테스트를 통해 필요한 서버 사양을 선제적으로 파악한다는 대응안이 채택됐다. (`54:01–54:24`)
- 개인정보는 AI 처리 전에 가능한 범위에서 비식별화하거나 서버에 보내는 개인 정보를 최소화하는 방향으로 설명하기로 했다. (`54:30–55:07`)

### 사용자 확보, 리텐션과 커뮤니티

- 초기 베타 테스터 모집 이후 광고를 통해 앱 설치를 유도하고, 앱스토어 리뷰와 테스터 설문으로 피드백을 수집하는 방안이 문서에 포함됐다. (`45:18–46:35`)
- 상용화 문제를 신규 사용자 확보와 기존 사용자 이탈 방지 중 어느 쪽으로 정의할지 모호했다. 초기 사용자에게 별도 알림을 제공하는 아이디어도 나왔으나 효과는 확인되지 않았다. (`50:27–58:05`)
- 기록 공유, 챌린지 인증, 친구의 공개 타임라인, 자기계발·성장 주제 커뮤니티 등이 리텐션 확장안으로 논의됐지만, 회의 시점에 막 나온 아이디어라 문서에 확정 반영하지 않고 멘토와 상의하기로 했다. (`1:39:35–1:54:49`)

### 지표, 관측성과 검증

- API 엔드포인트별 지연 시간, P95, TPS, 서버 메모리·CPU 점유율과 같은 운영 지표가 논의됐다. (`1:55:07–1:56:55`)
- 서비스 성공 지표는 기능별로 달라야 한다고 보고, 타임라인 생성·수정, 회고 완료, 재방문 같은 행동 지표를 검토했다. (`1:56:55–2:13:06`)
- GA4, 리뷰, 설문, 가능하다면 심층 인터뷰를 사용자 피드백 수집 수단으로 추가하기로 했다. 다만 인터뷰 대상 모집 방법은 미정이었다. (`1:58:52–1:59:57`)

### 초안 마감과 작업 분담

- 토요일 오전 9시까지 멘토에게 초안을 보낸다는 기존 계획과 문서 품질을 더 높이고 싶다는 의견이 충돌했다. 팀은 완성본이 아니라 피드백을 받기 위한 초안이라는 점을 재확인하고, 가능한 범위까지 작성한 뒤 멘토 피드백을 반영하기로 했다. (`1:06:39–1:16:17`)
- 각자 작성한 부분을 우선 수정하고, 반영한 댓글은 삭제하지 않고 이모지 등으로 표시해 작업 이력을 남기기로 했다. (`1:16:21–1:26:02`)
- 회의 말미에는 문서 초벌을 멘토들에게 전달하고, 피드백을 바탕으로 업데이트하면 된다는 방향을 확인했다. (`2:18:11–2:32:44`)

## 진행 상황

- 기획심의 문서 전반의 초벌이 마련됐으며 문구, 표, 일정, 역할, 위험 대응을 실시간 공동 편집했다.
- 문제 인식과 기획 의도의 중복 문장을 줄이고 `수집`을 `연결·통합`, `자연스럽게`를 `손쉽게`로 바꾸는 수정이 반영됐다. (`2:20:19–2:21:34`)
- 경쟁 서비스 비교표는 O/X 중심으로 단순화했으나 `자동 기록`, `회고 지원` 같은 평가 기준은 추가 검토가 필요했다. (`2:23:32–2:24:23`)
- AI 배포 환경과 사용할 모델은 아직 확정하지 못했으며 멘토에게 문의할 항목으로 남았다. (`2:25:41–2:26:19`)

## 열린 질문

- AI 출력 품질을 어떤 데이터셋, 평가 방식, 성공 기준으로 측정할 것인가?
- 경쟁 서비스가 서로 다른 범위를 가질 때 비교표의 공통 기준을 어떻게 설계할 것인가?
- 커뮤니티 기능이 해결하려는 리텐션 문제와 구체적 사용자 행동은 무엇인가?
- 베타 테스터와 심층 인터뷰 대상자를 어디서 모집할 것인가?
- 기능별 핵심 성공 지표와 목표값은 무엇인가?
- AI 모델과 배포 환경을 어떤 비용·성능·품질 기준으로 선택할 것인가?

## 주의 사항

- 원문은 자동 전사본이며 `회고`가 `해고`, `MVP`와 `NPS`, `success metric`, 서비스·멘토 이름 등이 잘못 기록된 구간이 많다.
- `NPS`로 추정되는 지표가 원문에서는 `MPS` 등으로 나타나며, 정확한 기획 문서 용어 확인이 필요하다.
- 회의 중 AI로 작성한 문구를 검토하는 장면이 많다. 문서에 나온 해결책이 팀의 확정된 기술 설계라는 의미는 아니다.
- 팀원의 개인 사정과 피로에 관한 대화는 일정 맥락 외에는 요약하지 않았다.
- 화자 라벨은 원문에 있으나 자동 화자 분리의 정확성은 검증하지 않았다.
