# 369팀 스페이스 회의 요약 - 2026-09-01

## 개요

이번 회의에서는 약관 web hosting 전환과 AI Timeline 정량 평가 준비 상황을 공유한 뒤, 실제 기기에서 동작하는 onboarding 화면을 길게 검토했다. onboarding은 단순히 permission을 받는 화면이 아니라, photo·calendar·location·notification이 어떤 방식으로 Timeline에 쓰이는지 설명하고 결과에 대한 기대를 만들어 사용자를 설득해야 한다는 방향으로 정리되었다. (`00:17-03:31`, `03:37-14:43`, `32:28-42:47`)

photo의 시간·위치만 보여주는 데서 그치지 않고 AI가 사진 속 의미를 해석한다는 점, 일정이 많은 calendar를 읽는다는 점, 이동 경로와 유용한 notification을 수집한다는 점을 더 구체적인 문구와 visual로 표현해야 한다는 피드백이 나왔다. 큰 3D emoji와 감성적 문구가 실제 app 동작을 가리고 있다는 지적에 따라, 핵심 기능과 data 처리 설명을 앞세우기로 했다. (`12:27-19:47`, `24:44-38:34`)

release 목표 때문에 전면 재설계는 피하고, 우선 문구·emoji 크기·page별 명확한 피드백을 반영해 다음 날 onboarding을 마무리하고 목요일 점검 후 금요일 release를 시도한다는 일정이 제시되었다. 이는 목표 일정이며 실제 release 완료 보고는 아니다. (`39:35-46:50`)

## 상세 요약

### 진행 상황과 당일 우선순위

- 앞선 회의에서 전달받은 오류를 수정했고, 약관 제공을 web posting 방식으로 완전히 전환했다고 보고했다. mentor 사전 질문에도 답변을 보냈다. (`00:17-00:50`)
- AI Timeline prompt를 분석하면서 정량 metric을 정하는 중이며, 1~2일 안에 기준을 마무리한 뒤 prompt 개선을 본격화할 계획이라고 했다. (`00:55-01:13`)
- landing page와 SEO도 검토했지만 onboarding design이 먼저 고정되어야 문구·visual을 재사용할 수 있어 당장은 보류했다. (`01:20-03:31`)

### onboarding의 역할과 permission 흐름

- onboarding은 best Timeline example을 먼저 보여준 뒤 photo, calendar, location, notification 읽기, reminder notification과 관련한 안내·권한 흐름으로 이어지는 구조로 시연되었다. 일부 permission은 Android system dialog 또는 설정 화면으로 연결된다. (`03:37-09:11`)
- onboarding의 핵심 목적을 `생성될 Timeline에 대한 기대를 만든 뒤 permission 허용을 설득하는 것`으로 정의했다. 따라서 어떤 data를 왜 읽고 어떻게 처리하는지 한 화면에서 직관적으로 이해할 수 있어야 한다고 보았다. (`13:04-14:43`, `38:13-42:47`)
- permission 설정에 몇 단계가 필요한 흐름은 beta tester에게 실제 난이도와 이탈 이유를 확인해야 한다는 후속 과제로 남았다. (`07:34-09:11`)

### photo·calendar·location·notification 표현

- photo page는 촬영 시각·위치뿐 아니라 AI가 음식·거리·날씨 같은 사진의 의미를 해석한다는 점을 명시해야 한다는 피드백을 받았다. 현재 film-camera visual 자체보다 이 기능 설명이 빠진 것이 더 큰 문제라고 정리했다. (`12:27-15:02`, `44:46-45:28`)
- calendar page는 일정이 비어 보이는 예시보다 약속·미용실·업무·여가처럼 실제로 빼곡한 일정을 보여줘, 기록이 많을수록 AI가 더 풍부한 Timeline을 만들 수 있다는 기대를 주기로 했다. (`16:14-20:06`)
- location page의 부채꼴 mask는 의미가 불명확하므로 직사각형 version과 비교하고, 하루 동안 여러 위치가 이어지는 route를 더 분명히 보여주자는 의견이 나왔다. 실제 지도 대신 특징만 살린 synthetic map을 만드는 대안도 제시되었다. (`24:44-28:37`)
- notification page는 결제·예약·배송 등 활용 대상을 보여주는 방향은 긍정적이었지만, 3D icon의 존재감이 너무 커 실제 notification과 app 동작이 가려지는 문제가 있었다. (`15:02-16:13`, `28:37-33:39`)

### 문구와 visual 우선순위

- `시간과 장소가 남아 있다`처럼 감성적·추상적인 문구보다 `오늘 촬영한 사진을 읽는다`, `calendar 일정을 가져온다`, `수집한 정보를 이렇게 처리한다`처럼 app 동작을 직접 설명해야 한다고 정리했다. (`33:43-36:38`)
- 큰 문장은 수집 대상, 작은 문장은 처리와 사용자 이익을 설명하는 구조가 제안되었다. 감성은 주된 selling point가 아니며 편리한 기능과 permission 필요성을 설득하는 것이 우선이라고 보았다. (`36:03-39:35`)
- 실제 Timeline UI를 반복적으로 노출하는 방안도 논의했지만, 방향이 확실하지 않고 일정이 촉박해 이번 반영 범위에서는 제외할 수 있다고 했다. (`35:20-38:09`, `40:41-41:33`)

### onboarding asset의 client/server 위치

- image asset을 app에 포함하면 app size가 늘지만 구현이 단순하고, server에서 내려주면 app update 없이 교체하거나 A/B test를 할 수 있다는 trade-off를 논의했다. (`20:08-23:33`)
- 장기적으로 server-driven onboarding도 가능하다는 의견이 있었지만, beta 단계에서는 현재처럼 client에 구현하고 시간 여유가 생기면 다시 논의하기로 했다. (`23:42-24:44`)

### release 일정

- 다음 날까지 onboarding을 작업자가 완료했다고 판단할 수준으로 만들고, 목요일 최종 점검 뒤 금요일에 mentor에게 release 상태를 보여주는 일정이 목표로 제시되었다. (`39:35-40:20`)
- 일정상 필수 반영은 구체적인 문구, 과도한 emoji 크기 조정, 명확한 page별 피드백으로 좁혔다. 큰 구조 변경과 실제 UI 삽입은 뒤로 미룰 수 있다고 했다. (`40:21-46:33`)

## 열린 질문

- photo 의미 분석을 permission 안내에서 어디까지 설명해야 과장 없이 기대를 만들 수 있는가?
- system 설정으로 이동해야 하는 permission 흐름에서 실제 허용률과 이탈은 어느 정도인가?
- onboarding image를 client bundle에 둘 때 허용 가능한 app size와 update 유연성 기준은 무엇인가?
- 감성적 visual과 기능 설명 사이의 최적 비중은 beta user에게 어떻게 검증할 것인가?
- 금요일 release 목표가 실제 Play Store 제출·내부 test·지인 배포 중 무엇을 의미하는가?

## 주의 사항

- Figma와 실제 기기 화면이 전사에 포함되지 않아 visual 배치와 세부 문구는 정확히 재현할 수 없다.
- `photo 의미 분석`, `server-driven UI`, `code push` 관련 발언은 회의 중 설계 논의이며 구현 완료를 뜻하지 않는다.
- 금요일 release는 목표 일정이며 이 회의에서는 완료가 확인되지 않았다.
- mentor 이름과 일부 제품·도구 명칭은 자동 전사가 불명확해 원문 표현을 일반화했다.
