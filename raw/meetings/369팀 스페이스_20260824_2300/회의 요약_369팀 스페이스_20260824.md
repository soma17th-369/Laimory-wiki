# 369팀 스페이스 회의 요약 - 2026-08-24

## 개요

이번 회의에서는 베타 테스트와 Play Store 등록을 앞두고 출시 준비 범위와 목표 시점을 점검했다. 주요 논의는 GA4 지표·퍼널 설계, 프로모션 팸플릿, AI 인프라 및 모델 전환, backend API와 비용 점검, Android 읽기·편집 화면과 자동 데이터 수집, 지도 표시, 알림 필터 관리였다.

베타 테스터에게 실제 앱을 전달하려면 먼저 테스트용 release가 필요하다는 판단 아래, 사전에 후보자를 생각해 두되 실제 연락은 설치 가능한 build가 나온 뒤 진행하자는 방향이 제시되었다. 초기 목표는 8월 28일 금요일까지 Play Store 등록을 시도하는 것이었지만, GA4·logging·deep link·모바일 UI 등 남은 작업 때문에 지연 가능성도 명시되었다. (`01:43-02:45`, `51:41-54:09`)

GA4 초안은 첫 가치 경험, retention, 생성 funnel, 입력 데이터 선택·제외, AI 생성 결과의 수정·삭제·추가, 메모 작성, permission 허용·거부 등을 측정 대상으로 삼았다. 첫 가치 행동은 이틀 안에 유도하되 최대 7일까지 추적할 수 있다는 의견이 나왔고, 세부 산식과 event naming은 구현 과정에서 보완하기로 했다. (`04:28-12:26`)

AI 쪽에서는 AgentCore 전환과 세 개 PR 검수가 진행 중이었으며, GPT 계열 모델과 전사상 `노바트 라이트`로 들리는 Bedrock 모델 사이의 비용·품질·JSON 형식 보장 차이가 논의되었다. 회의 중에는 해당 Bedrock 모델로 빠르게 전환해 비교 테스트하고, 품질이 부족하면 GPT로 되돌리는 방향을 실행 계획으로 잡았다. 다만 정확한 모델명과 실제 적용 완료 여부는 코드·배포 기록 확인이 필요하다. (`17:11-23:23`)

## 상세 요약

### 베타 테스트와 출시 준비

- 설치 가능한 release가 없는 상태에서 지인에게 연락해도 보여줄 결과물이 부족하므로, 실제 beta tester 모집 연락은 release가 준비된 뒤 진행하자는 의견이 제시되었다. 후보자는 그 전에 각자 생각해 둘 수 있다. (`01:43-02:45`)
- 베타 테스트 준비 항목은 사용자 관련 지표 설계, 앱 홍보 팸플릿, 인프라 작업, AI 타임라인 품질 점검과 모델 전환의 네 묶음으로 정리되었다. (`16:49-17:11`)
- 목표 시점으로 8월 28일 금요일이 제시되었지만, 모바일 logging, GA4, backend 연동, deep link 등을 고려하면 지연될 가능성이 있다는 응답이 있었다. 늦어도 9월 초에는 제출하자는 희망도 언급되었다. (`51:41-54:09`)
- Play Store에 제출한 뒤 심사 기간 동안 beta test를 진행할 수 있다는 운영 구상이 공유되었다. 심사에 약 2주가 걸릴 수 있다는 수치는 회의 발언자의 추정이며 확인된 일정은 아니다. (`53:28-53:51`)

### GA4 지표와 퍼널 설계

- 369팀 공유 문서에 `GA4 스펙` 초안이 작성되었다. 첫 가치 행동의 목표는 설치 후 이틀 안으로 잡고, 관찰 window는 7일까지 유지할 수 있다는 의견이 나왔다. (`04:28-06:35`)
- 핵심 지표 후보로 첫 가치 경험까지 걸린 시간, D1·D3·D7 retention, 7일 안의 반복 기록률, 필수 단계 funnel 이탈률이 언급되었다. 전사에서 일부 지표명과 숫자가 흐릿해 실제 문서를 확인해야 한다. (`06:09-07:19`)
- 입력 데이터별로 사용자가 확인·제외한 비율을 측정하고, AI가 생성한 event의 수정·삭제·추가, field별 수정 여부, 메모 작성 event 수와 메모 길이를 기록하는 방안이 설명되었다. 산식은 아직 단순해 보강이 필요하다고 명시되었다. (`07:21-09:35`)
- onboarding 중 permission별 허용·거부와 이후 재허용, 모든 핵심 permission 확보율도 측정 후보로 제시되었다. (`09:37-10:23`)
- 생성 funnel은 회원가입, 데이터 준비, 날짜 선택, 입력 데이터 검토·확정, 생성 요청·완료, 결과 재진입, 수정·메모 작성·저장 단계로 나누는 안이 소개되었다. Android 구현 세부는 추가 검토 대상이다. (`10:37-12:26`)

### 프로모션 팸플릿과 사업자 등록

- 사진·캘린더·위치·알림을 모아 하루의 기록으로 정리한다는 흐름과 AI 초안, 사용자 수정, 일기 재열람을 설명하는 팸플릿 초안이 만들어졌다. 구성은 유지할 만하다는 반응이 있었으나 이미지와 디자인 자산은 추가 개선이 필요하다. (`13:35-16:47`)
- 캘린더를 꾸준히 쓰는 사람에게 자동 연동 수요가 있을 수 있다는 초기 대화 경험이 팸플릿 구성의 근거로 언급되었다. 이는 정식 사용자 조사 결과가 아니다. (`15:29-16:18`)
- 초안을 Figma로 옮겨 디자인을 보완하고 Play Store 소개 자료로 활용하는 계획이 정리되었다. (`14:46-16:47`)
- 사업자 등록은 당일 신청했다고 보고되었으며, 승인 여부는 이 회의 시점에 확인되지 않았다. (`13:18-13:30`)

### AI 인프라와 모델 선택

- AgentCore 전환을 위한 설정과 세 개 PR이 올라와 있고, 검수와 연결 테스트가 남아 있다고 보고되었다. (`02:50-03:20`)
- GPT·Gemini 계열과 달리 전사상 `노바트 라이트`로 기록된 모델은 JSON schema를 보장하기 위해 tool configuration을 사용하는 것으로 이해하고 있었으나, 정확한 동작 방식은 확인이 필요하다고 말했다. (`17:38-18:35`)
- 모델별로 prompt와 처리 logic이 달라지면 이중 유지보수 비용이 생길 수 있으므로, A/B test를 별도로 운영하지 않는다면 주력 모델 하나를 빠르게 정하는 편이 낫다는 의견이 나왔다. (`18:36-20:28`)
- 회의 중에는 인프라 전환과 함께 Bedrock 쪽 모델로 먼저 바꾸고, 기존 결과 중 애매한 사례를 재생성해 품질 차이를 확인하며, 품질이 부족하면 GPT로 되돌리는 방향을 잡았다. (`21:46-23:23`)
- beta test 중 생성 품질과 성능을 관찰할 체계도 구축하려 했으나, 이는 beta test 전에 모두 완료해야 하는 필수 조건이 아니라 운영 중 발전시킬 항목으로 설명되었다. (`22:42-23:23`)

### Backend 작업과 API 조정

- load 관련 인프라 작업과 사진 장소 주소 저장은 완료되었고, 감정 수정 및 event 생성 API를 작업 중이라고 보고되었다. 예산표와 실제 비용을 교차 확인했으며, ElastiCache를 쓰지 않게 되어 예상 비용이 줄었다는 설명이 있었다. (`23:36-24:18`)
- event 생성 API에 사진을 함께 받도록 optional field를 두고, S3 file name을 전달하는 방식으로 정리했다. 별도 사진 연결 API를 client가 연속 호출하는 안보다 event 생성 요청에 포함하는 쪽을 택했다. (`24:18-26:02`)
- mentor feedback에 따라 사용자 조회 endpoint 이름을 변경하고 mobile도 해당 endpoint를 반영하기로 했다. (`26:05-26:41`)

### Android UI와 자동 데이터 수집

- 알림 field가 title·text 외 다른 위치에 들어가 광고나 진행형 notification을 놓치거나 반복 수집하는 문제가 있어, 추가 field를 찾아 filtering logic을 보완했다고 보고되었다. (`27:25-28:53`)
- timeline event의 AI 질문 문구를 `이 순간에 대한 메모`로 교체하고, 저장된 결과에서는 메모가 없으면 입력 UI를 숨기는 등 읽기에 집중하는 화면을 시험했다. 다만 읽기 mode와 편집 mode의 경계와 최종 UX는 미결이었다. (`28:53-29:45`)
- 회원 탈퇴 UI에는 안내와 확인 checkbox를 넣어 실수로 탈퇴하기 어렵게 했다고 보고되었다. (`29:29-29:59`)
- permission이 허용된 경우 앱 진입 시 한 번, 사용자가 생성 날짜를 선택할 때 다시 한 번 calendar·건강 데이터를 갱신하는 자동 수집 방식을 구현 중이었다. 사진은 사용자가 직접 선택하므로 자동 갱신 대상에서 제외했다. (`32:18-34:36`, `41:27-44:13`)
- 건강 데이터에는 걸음 수뿐 아니라 사용자가 별도 permission을 허용하면 수면 정보도 포함될 수 있다고 설명되었다. (`44:18-44:35`)

### 지도 표시와 알림 필터 운영

- 사용자가 생성 전 위치 데이터를 지도 marker로 확인하고 toggle로 제외할 수 있도록 Google Maps를 사용한 화면이 구현되었다. Naver Map의 과금 가능성과 Google Map의 UI 차이가 논의되었고, beta feedback에서 문제가 크지 않으면 우선 Google Map을 유지하자는 방향이었다. (`29:47-40:42`)
- Google Maps SDK 사용에 별도 동의나 약관 반영이 필요한지 확인이 필요하다고 말했다. 호출 단가와 무료 범위에 관한 회의 중 수치는 불명확해 공식 문서 확인이 필요하다. (`30:44-32:18`)
- 알림 filter는 사용자마다 필요한 앱·pattern이 달라 한 번에 확정하기 어렵기 때문에, 공유 문서에 package/app과 keyword 규칙을 정리하고 계속 협의하기로 했다. (`46:09-50:49`)
- 알림 정책은 배포 이후에도 바뀔 수 있으며, 너무 많은 불필요 알림은 생성 품질과 운영 안정성에 영향을 줄 수 있다는 우려가 제기되었다. (`47:00-50:39`)

## 열린 질문

- GA4의 첫 가치 행동, 반복 기록률, 데이터 제외율, AI 수정률을 어떤 event schema와 산식으로 구현할 것인가?
- 전사상 `노바트 라이트`로 기록된 모델의 정확한 이름은 무엇이며 JSON schema 보장 방식은 어떻게 동작하는가?
- beta test의 주력 모델은 무엇이며 비용 지원과 품질 기준을 어떻게 비교할 것인가?
- 읽기 mode와 편집 mode를 어떻게 전환하고 AI 질문·메모 입력을 어느 화면에 배치할 것인가?
- calendar·건강 데이터 자동 갱신이 실패하거나 앱이 background로 내려간 사이 데이터가 추가된 경우 어떻게 처리할 것인가?
- Google Maps SDK 사용에 필요한 이용약관·동의와 실제 호출 비용 조건은 무엇인가?
- 사용자별로 다른 알림 pattern을 어떻게 지속적으로 검증하고 filter regression을 관리할 것인가?

## 주의 사항

- 전사에는 화자명이 있지만, 발언만으로 실제 코드 owner나 최종 책임자를 확대 추론하지 않았다.
- `GA4`, `AgentCore`, `JSON`, `Bedrock`, `ElastiCache`, `Google Maps`로 보이는 용어 일부가 자동 전사에서 왜곡되어 있다.
- `노바트 라이트`, `로버트 라이트` 등으로 적힌 모델명은 동일 대상을 가리킬 수 있으나 정확한 정식 명칭은 코드나 AWS console에서 확인해야 한다.
- 일정, 심사 기간, 지도 호출 비용 수치는 회의 중 추정이 포함되어 있으며 외부 정책의 확정값으로 취급하면 안 된다.
- 원문에는 개인 일정과 운영 세부가 포함되어 있으므로 공개 범위를 제한해야 한다.
