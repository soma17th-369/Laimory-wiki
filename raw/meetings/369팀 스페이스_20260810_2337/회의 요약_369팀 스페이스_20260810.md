# 369팀 스페이스 회의 요약 - 2026-08-10

## 개요

이번 회의는 AI 구독·API 비용 점검, 중간 발표 보고서의 구성, 사용자 데이터 비식별화와 민감정보 필터링, 개인정보 제3자 제공 및 국외 이전 동의 UX, 그리고 회고 기능을 목표·할 일 관리 기능으로 바꿀 가능성을 중심으로 진행되었다.

AI 도구 비용과 관련해서는 월 100달러 구독의 실제 사용률이 낮아 보인다는 문제의식과 구독료 외에 API 사용료가 별도로 발생한다는 점이 논의되었다. Claude와 GPT 계열 중 무엇을 줄일지는 실제 사용량을 더 확인한 뒤 판단하기로 했으며, 회의 중 제시된 “100달러로 1,000달러의 효과” 같은 값은 AI가 추산한 설명일 뿐 검증된 비용 절감 수치가 아니다. (`02:59-09:09`)

개인정보 보호 측면에서는 이메일·주민등록번호·여권번호·면허번호·카드번호·전화번호·계좌번호처럼 정규식으로 잡을 수 있는 값과 사람 이름·상세 주소·병원·종교·정치처럼 비정형이거나 맥락 의존적인 정보를 구분했다. 사용자와 AI 저장 데이터의 연결 관계를 끊거나 별도 저장소·매핑 테이블을 사용하는 방안이 논의되었지만, 정확한 비식별화 구조와 비정형 민감정보 처리 방법은 아직 미결이다. (`14:35-20:09`)

동의 UX에서는 회원가입 동의와 타임라인 생성 시점의 제3자 제공·민감정보 처리·국외 이전 고지를 구분하고, 동의 시점과 승인 상태를 server에 저장할 필요가 있다는 해석이 공유되었다. 동의 이력용 별도 DB table을 만드는 방향이 제시되었으나, 약관 본문을 API로 내려줄지 Notion 같은 외부 문서로 제공할지는 정하지 않았다. (`20:14-25:14`)

제품 기능은 기존 회고 기능이 현재 수집 가능한 데이터와 MVP 구조로는 충분한 품질을 내기 어렵다는 문제를 다시 검토했다. 회고를 과감히 빼고 타임라인을 기반으로 한 목표·할 일 또는 challenge 기능을 구체화하자는 방향이 제안되었지만, 목표 검증 데이터와 기능 정의가 부족해 최종 명세로 확정되지는 않았다. AI 대화 기능은 기록을 풍성하게 만드는 가치와 비교적 잘 맞는다는 의견이 있었다. (`28:13-35:05`)

## 상세 요약

### AI 구독과 API 비용

- 월 100달러 요금제를 사용하지만 주간 사용량이 20%를 넘는 경우를 거의 보지 못했다는 경험이 공유되었다. 다른 참석자는 자신도 주간 사용량이 50%를 넘는 경우가 많지 않다고 답했다. (`03:05-06:18`)
- 구독 계정에 API 사용량이 포함되는 것으로 오해했으나 실제로는 구독료와 API 비용이 별도라는 점을 확인했다고 말했다. (`07:38-08:16`)
- 비용을 줄인다면 GPT 계열부터 줄이는 편이 낫다는 의견이 있었지만, 실제 사용량과 5시간·주간 한도를 더 면밀히 확인하기로 했다. (`08:24-09:09`)
- AI가 “100달러를 쓰며 1,000달러 효과를 본다”고 설명했다는 발언은 API 종량제 환산 추정으로 보이며, 실제 invoice나 benchmark로 검증된 값은 아니다. (`04:02-05:10`)

### 중간 발표 준비와 AI 평가 시스템

- 중간 발표에 개인정보가 어떻게 저장되고, 사용자 동의를 어떻게 받고, 유출되더라도 식별되지 않게 어떤 rule을 적용하는지를 반드시 포함해야 한다는 판단이 나왔다. (`10:01-11:25`)
- 생성형 AI evaluation system을 계속 만들고 있으며, 더 정량적인 metric을 정해 논문이나 특허로도 발전시킬 수 있도록 하자는 피드백이 반영되었다. 현재는 개선과 metric 설계가 진행 중이다. (`11:30-12:05`)
- 마케팅 쪽에서는 persona, 소구점, 첫 가치 행동, retention 지표를 정리해 중간 발표 내용에 반영할 계획이라고 했다. (`12:07-13:17`)
- 보고서는 기존 기획심의 문서를 확장하되, 시스템 구성도·AI 활용 전략·추진 일정·수행 방법·개발 진행 현황·결과물·KPI·수익 모델을 새 양식에 맞게 재배치해야 한다고 논의했다. (`26:32-49:35`)

### Bedrock 또는 모델 전환과 임시 한도

- API 비용을 줄이기 위해 Bedrock으로 옮길 수 있다는 의견이 나왔고, 테스트를 계속해야 하므로 관련 내용을 추가로 설명하기로 했다. (`13:21-13:40`)
- 전사상 `로버트 라이트`로 들리는 모델은 성능이 많이 떨어질 수 있다는 예상이 나왔으며 정확한 모델명은 확인이 필요하다. (`13:40-13:56`)
- 현재 한도가 5달러로 설정되어 있고 이미 이를 넘었기 때문에, MVP에서 기존 GPT-4 mini 기준의 결과를 보여줄 수 있도록 테스트 기간 동안 한도를 임시로 올리겠다는 설명이 있었다. (`13:47-14:23`)

### APM과 tracing

- APM 작업이 회의 당일 약 17시경 마무리되었다고 보고했다. (`14:35-14:45`)
- Grafana의 Explore에서 `Tempo`를 통해 trace를 확인할 수 있다고 안내했다. 구체적인 배포 환경과 검증 범위는 전사에 없다. (`14:45-15:00`)

### 민감정보 필터링과 비식별화

- 정규식으로 탐지할 대상으로 이메일, 주민등록번호, 여권번호, 면허번호, 카드번호, 전화번호, 계좌번호를 열거했다. (`15:00-15:33`)
- 사람 이름과 상세 주소, 병원·종교·정치처럼 법적으로 민감할 수 있는 맥락 정보는 정규식만으로 다루기 어렵다고 판단했다. (`15:34-19:09`)
- 주소 column을 제거하거나 place와 address의 역할을 바꾸는 아이디어가 나왔지만, place가 없을 때 address가 필요할 수 있어 schema 변경으로 확정되지는 않았다. (`15:45-16:38`)
- 사용자 ID와 AI item 또는 user memory 사이의 관계만 끊으면 충분한지, 별도 AI agent 저장소를 둘지, server가 mapping table을 관리할지 논의했으나 결론을 내리지 못했다. (`16:42-18:40`)
- 비정형 민감정보를 다루려면 전사상 `SSLM`으로 들리는 기술이 필요할 수 있다는 의견이 있었지만 비용과 개발 시간 때문에 즉시 적용하기 어렵다고 보았다. 정확한 기술명은 확인해야 한다. (`19:30-20:09`)

### 동의·국외 이전 UX와 저장

- 제3자 정보 제공과 민감정보 처리 동의에 더해, 외부 LLM API로 정보가 해외에서 처리될 수 있음을 알리는 개인정보 국외 이전 고지 또는 동의가 필요할 수 있다는 조사 결과가 공유되었다. 이는 법률 검토가 완료된 결론이 아니다. (`20:14-21:18`)
- 회원가입 때 필요한 동의와 타임라인 생성 때 필요한 동의를 구분하고, 사용자가 언제 무엇에 동의했는지 server에 저장해야 한다는 해석에 참석자들이 동의했다. (`21:19-22:15`)
- 동의 이력을 위해 별도 DB table을 만드는 것이 필요하다는 의견이 나왔고, 구현 자체는 어렵지 않을 것이라는 평가가 있었다. (`22:52-23:07`)
- 약관을 app update 없이 변경하기 위해 Notion link, API로 내려주는 text, image 등 여러 방식을 비교했다. 임시로 Notion을 사용할 수 있다는 의견은 있었지만 최종 전달 방식은 정하지 않았다. (`23:07-25:14`)

### Timeline edit와 UI 일정

- 사용자가 하나의 전체 flow를 완성하는 수준은 수요일 또는 목요일까지를 목표로 하고, edit mode와 완성 UI를 명확히 분리하는 작업은 빠르면 목요일, 늦으면 금요일 새벽까지 걸릴 수 있다고 예상했다. 이는 추정 일정이며 완료 약속으로 확정된 것은 아니다. (`25:16-26:22`)

### 회고 기능과 목표·할 일 기능 재검토

- 기존 제품의 핵심 가치는 사용자가 쉽고 간편하게 사진과 하루 활동을 정리한 일기를 만드는 것이라는 설명이 있었다. user memory 등 더 큰 가치는 후에 붙은 개념이라 제품 범위가 불명확해졌다는 자기 평가도 나왔다. (`29:34-30:29`)
- AI 대화 기능은 그날의 일기와 대화하면서 기록을 더 풍성하게 할 수 있어 핵심 가치와 비교적 잘 맞는다는 의견이 있었다. (`30:46-31:33`)
- 회고 기능은 MVP 과정에서 필요한 입력 정보가 많이 빠져 현재 구조로 구현하기 어렵고, 과감하게 빼는 것이 맞다는 의견이 나왔다. (`31:34-33:28`)
- 대안으로 타임라인을 기반으로 목표, todo list 또는 challenge를 추적하는 기능을 기획하자는 방향이 제안되었다. 다만 어떤 목표를 검증할지와 어떤 데이터를 수집할지가 목표마다 달라 구체적인 기능 계획이 더 필요하다. (`31:41-34:23`)
- 이 변경을 반영한다면 문제 인식과 기획 의도에 개인의 성장 또는 목표 관리 가치를 추가하고, 시장 분석에는 todo·challenge app을 보완적으로 포함하는 방안이 논의되었다. (`34:15-35:05`)

- 전사상 `로버트 라이트`, `SSLM`으로 들리는 정확한 모델·기술 명칭은 무엇인가?

## 주의 사항

- 이 전사에는 화자명이 없어 발언 주체와 담당자를 추측하지 않았다.
- 비용·사용률·모델 성능 관련 수치는 회의 중 경험과 추정이며 invoice, benchmark, provider 문서로 검증되지 않았다.
- 개인정보 동의, 국외 이전, 보관 기간 관련 내용은 법률 자문 결과가 아니라 팀의 조사와 해석이다.
- `로버트 라이트`, `SSLM`, `APIP`, `해고 기능`, `기획 침해` 등은 자동 전사 오류 가능성이 높다. 문맥상 일부는 model name, API, 회고 기능, 기획심의를 가리키는 것으로 보이지만 원음·문서·code 확인이 필요하다.
- 제품 기능 변경은 탐색적 논의가 많아 구현 완료나 최종 roadmap으로 기록해서는 안 된다.
