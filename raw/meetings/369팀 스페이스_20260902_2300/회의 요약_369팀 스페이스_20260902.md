# 369팀 스페이스 회의 요약 - 2026-09-02

## 개요

이번 회의에서는 AI Timeline prompt의 정량 기준 정리, server query·cache 개선, Android release build 준비 상황을 공유했다. 전날 피드백을 반영한 onboarding을 실제 기기에서 다시 확인하고 현재 상태로 고정한 뒤, 읽기·편집 mode와 AI 질문 표시 방식, 수집 data가 없는 첫날의 Timeline 경험을 집중 논의했다. (`00:33-03:56`, `04:02-16:44`, `17:50-50:52`)

onboarding은 photo 의미 분석을 더 직접적으로 말하는 문구, 일정이 채워진 calendar, 직사각형 map과 여러 location marker, Timeline 완료·회고 reminder를 반영했다. 14세 이상 확인이 필요하지만 Kakao login에서 나이를 가져오지 못하므로 login 또는 onboarding에서 self-attestation을 받는 방안이 제시되었다. (`04:02-13:34`)

읽기 mode에서는 AI 질문을 숨기고, 편집 mode에서는 기존 event 편집 화면으로 한 단계 들어가 수정하도록 현재 구조를 유지하기로 했다. AI 질문은 미작성 memo의 placeholder로 우선 유지하고, inline 편집이나 질문을 별도 보존하는 design은 일정 이후 재검토하기로 했다. (`14:00-34:46`)

input이 전혀 없을 때 생성 자체를 막아 첫 가치 품질을 보호할지, AI를 호출하지 않은 빈 Timeline을 제공해 사용자가 직접 일기를 쓰게 할지 의견이 나뉘었다. 공통적으로 data 부족 이유와 권한·입력 개선 방법을 설명해야 한다는 데는 합의했으며, event 추가 기능은 이미 구현되었다고 보고되었다. 최종 empty-state flow와 beta 반영 범위는 확정되지 않았다. (`34:48-50:52`)

## 상세 요약

### AI prompt와 server 성능 작업

- Timeline 생성 prompt와 component를 검토하며 `과도하다`, `강하다`처럼 측정하기 어려운 표현을 정량 기준으로 바꾸고, 모순되거나 불필요한 instruction을 일괄 정리할 준비를 했다. 생각보다 문제가 많아 작업 시간이 길어졌다고 보고했다. (`00:33-01:54`)
- 약관·보안 작업 뒤 여러 API에서 query가 늘어난 문제를 보고했고, cache를 처음 적용하기 위해 학습과 구현을 병행 중이라고 했다. 자동 전사가 query 유형을 명확히 담지 못해 정확한 병목은 code 확인이 필요하다. (`01:56-02:30`)
- Android 쪽은 release build 환경, 난독화·압축, app size, deep link/server 설정을 준비하고 있었다. (`02:37-03:56`)

### onboarding 수정과 고정

- photo page 문구는 `언제 어디서`와 AI 분석을 직접 말하는 방식으로 바꾸었고, calendar는 업무·약속·여가 일정이 채워진 형태로 수정했다. (`04:02-06:03`)
- 부채꼴 location visual은 직사각형 map으로 바꾸고 여러 marker를 추가했다. notification과 reminder는 결제·예약·배송 같은 수집 대상과 Timeline 완료·하루 회고 시점의 알림을 설명하도록 했다. (`06:03-07:32`, `09:21-10:48`)
- system 설정까지 이동하는 location·notification permission은 단계가 깊어 beta tester에게 난이도와 허용 경험을 확인할 필요가 있다고 했다. (`10:49-11:42`)
- 약관 화면의 표가 mobile에서 어색한 문제를 확인하기로 했고, 14세 이상 확인은 login 또는 onboarding에서 self-attestation으로 받는 방안이 제시되었다. Kakao에서 나이를 가져오지 못한다는 구현 제약이 언급되었다. (`11:45-13:30`)
- 전날 피드백이 대부분 반영됐고 시간이 촉박하므로 onboarding은 현재 상태로 고정하고 읽기·편집 mode로 넘어가기로 했다. (`13:30-16:44`)

### 읽기·편집 mode와 AI 질문

- 읽기 mode는 기존 UI에 편집 진입 button을 추가하고, 실제 수정은 기존 event 수정·생성 UI를 재사용하는 별도 화면에서 처리하는 안이 제시되었다. (`14:00-16:02`)
- inline 편집은 편할 수 있지만 scroll 중 모든 영역이 button처럼 느껴질 위험이 있고, 기존 depth 하나를 유지해도 치명적인 불편은 아니라는 의견에 따라 현재 구조를 우선 구현하기로 했다. (`17:50-23:38`)
- AI 질문은 사용자의 기록을 시작시키는 prompt다. 읽기 mode에는 보이지 않게 하고, 편집 mode에서 memo를 쓰는 동안 질문을 잊지 않게 별도 표시하는 design이 논의되었지만 일정상 우선 placeholder 방식으로 유지하기로 했다. (`23:40-34:12`)
- 읽기·편집 mode와 logging을 9월 3일까지 마무리하고 9월 4일 release를 시도한다는 강한 목표가 제시되었으나, 작업량상 달성 여부는 미확인이다. (`18:12-21:30`, `34:14-34:46`)

### input이 없는 첫날과 manual Timeline

- 현재는 수집 data가 전혀 없으면 event가 생성되지 않고 사용자가 아무것도 할 수 없는 화면이 된다고 확인했다. AI 자동 생성은 selling point지만 제품의 본질은 일기 작성이므로, 빈 날에도 수동 기록을 허용해야 한다는 주장이 나왔다. (`34:48-36:53`)
- 반대 의견은 품질이 매우 낮은 첫 결과가 First Value Action을 훼손하고 즉시 이탈을 만들 수 있으므로 data가 충분할 때까지 생성을 막는 편이 낫다는 것이었다. (`37:06-37:52`)
- photo·calendar만으로도 첫 Timeline 품질을 낼 수 있다는 기대가 있었지만, 신규 user가 두 data를 모두 갖고 있지 않거나 permission 직후 수집량이 부족한 경우는 별도로 다뤄야 한다고 확인했다. (`39:25-42:01`)
- AI를 호출하지 않고 빈 Timeline을 만들고 사용자가 event를 직접 추가하게 하는 절충안이 제시되었다. event 생성 기능과 API는 이미 구현되어 있지만, empty state에서 그 기능으로 연결하는 flow는 남아 있었다. (`42:03-44:37`)
- event가 0~2개처럼 적게 생성되면 data 부족 이유, 미허용 permission, photo·calendar 활용법을 설명하자는 제안이 나왔다. block·manual 작성·안내 방식은 logging과 A/B test로 비교할 수 있다고 했다. (`44:38-50:30`)
- deadline 안에 반영하기 어렵다면 beta tester에게 첫날보다 다음 날 생성하도록 안내하는 임시 운영도 허용했다. 따라서 manual empty-state가 이번 release에 확정 구현되었다고 볼 수 없다. (`49:58-50:52`)

### 운영 준비와 비용 신청

- 금요일 mentor 일정과 주말 AI mentoring을 조율했으나 일부 시간·참석은 잠정적이었다. (`51:02-52:44`)
- AI 관련 지원 신청과 GPT API prepaid credit 금액을 금요일 함께 정하기로 했다. credit 소진 단위와 실제 요청당 비용을 먼저 계산해야 한다는 과제가 남았다. (`55:18-56:55`)

## 열린 질문

- 14세 이상 확인을 login과 onboarding 중 어디서 받으며 self-attestation만으로 충분한가?
- AI 질문을 placeholder로만 보여줄 때 입력 중 질문이 사라지는 문제를 어떻게 해결할 것인가?
- 수집 data가 전혀 없는 첫날에는 생성을 막을지, manual blank Timeline을 줄지, 다음 날을 안내할지?
- 저입력 결과의 기준을 event 수, source 수, confidence 중 무엇으로 판단할 것인가?
- empty-state 대안을 비교할 logging event와 A/B test 기준은 무엇인가?
- query 증가와 cache 적용의 실제 대상·효과·consistency risk는 무엇인가?

## 주의 사항

- 14세 관련 논의는 법률 검토가 아니라 구현팀의 product discussion이다.
- query 유형과 mentor·도구 명칭 일부는 자동 전사가 불명확하다.
- onboarding 완료와 event 추가 기능은 회의 중 구현 보고이며 source code·release build 검증은 하지 않았다.
- 9월 4일 release와 empty-state 반영은 목표 또는 제안이며 완료 상태가 아니다.
