# 369팀 스페이스 회의 요약 - 2026-08-27

## 개요

이번 회의에서는 Bedrock model 전환 장애와 timeline 품질 개선, production data backup·탈퇴 후 삭제 scheduler, Android onboarding·감정·event 추가 UI, 초기 release를 막는 남은 과제를 점검했다. 후반에는 messenger notification을 대화 event로 해석하는 현재 방식이 중요하지 않거나 민감한 event를 과도하게 생성할 수 있다는 사례를 바탕으로, 즉시 scope를 넓히기보다 AI 판단과 최대 event 수를 먼저 조정하고 beta test에서 deletion pattern을 관찰하기로 했다.

AI model 쪽에서는 전사상 `노바트 라이트`로 들리는 model의 JSON 출력 mechanism과 max token 문제가 의심되었고, 아예 output이 나오지 않는 사례가 있어 전환 준비가 완료되지 않았다. `GPT 5.6 Luna`로 들리는 model은 조직의 SCP 권한에 막힌 것으로 추정해 권한 요청을 다시 제출했다. 그 사이에는 기존 API key 기반 model을 유지할 수 있어 release 자체가 즉시 막힌 것은 아니라는 판단이었다. (`00:37-05:48`, `09:27-13:20`)

제품 가치 측면에서는 단순히 방문 장소와 사진을 나열하는 Google Timeline류와 달리, 사진의 의미와 사용자가 왜 그곳에 갔고 무엇을 했는지까지 육하원칙 수준으로 정리하는 것을 Laimory timeline의 차별점으로 잡았다. user memory가 있을 때와 없을 때 결과 차이도 확인해 prompt와 context 사용을 개선하려 했다. (`02:31-03:58`)

## 상세 요약

### AI model 전환과 timeline 품질

- Bedrock model 호출을 위해 기존 OpenAI 호출과 다른 JSON validation mechanism을 수정하고 있었다. output max token 초과가 오류 원인일 수 있다고 추정했지만 log가 충분하지 않아 확정하지 못했다. (`00:37-01:51`)
- `GPT 5.6 Luna`로 들리는 model은 신규 공개된 뒤 조직 SCP가 허용하지 않아 호출이 막힌 것으로 추정했다. AgentCore 때와 유사하게 권한 요청을 할 계획이며, 한 차례 요청이 반려되어 다시 제출했다고 보고되었다. (`01:52-02:28`, `09:27-09:56`)
- 실제 사례는 notification, 특히 KakaoTalk 대화를 지나치게 중요한 event로 만들었다. 처음에는 Bedrock model 결과로 오해했으나 생성 시점을 확인한 뒤 기존 GPT 기반 결과일 가능성이 높다고 정정했다. (`03:59-05:48`)
- timeline은 사실과 위치·사진 matching은 대체로 맞았지만 너무 많은 대화 event를 포함했다. 대화 event 최대 개수, 더 보수적인 판단 rule, max total event 수를 검토하기로 했다. (`10:00-11:37`, `24:23-26:11`)
- 기존 API key model을 당분간 쓸 수 있으므로 초기 release가 model 문제 때문에 완전히 막힌 것은 아니고, Bedrock output 오류와 SCP가 해결된 뒤 전환·비교 test를 하려는 계획이었다. (`11:37-13:20`)

### 제품 차별점과 user memory

- Google Timeline과의 차이를 방문 위치·사진 나열이 아니라 `왜 갔는지`, `무엇을 했는지`, 사진이 무엇을 의미하는지까지 하루의 맥락으로 정리하는 것으로 설명했다. (`02:31-03:25`)
- 기존 timeline 사례와 두 사용자의 user memory를 확인하며 memory가 있을 때와 없을 때 결과 차이를 비교하고 개선 지점을 정리 중이었다. 구체적인 benchmark나 결론은 아직 없었다. (`03:25-03:58`)

### production data lifecycle와 server maintenance

- production MySQL에 backup이 없던 문제를 보완하고, 회원 탈퇴 7일 뒤 user data를 제거하는 scheduler, 어느 event에도 연결되지 않은 orphan item을 삭제하는 scheduler를 작업했다고 보고되었다. (`05:49-06:42`)
- 이 작업들은 거의 끝나 당일 취침 전 마무리될 것으로 예상했지만, 실제 배포 완료 여부는 회의에서 확인되지 않았다. (`06:32-06:42`)

### Android onboarding과 timeline 기능

- initializer API를 연결한 onboarding flow는 module 문제를 정리해 완료했다고 보고했다. 안내 화면에서 `계속`을 누를 때 system permission prompt를 단계적으로 호출하도록 구성했다. (`06:48-07:42`)
- onboarding의 실제 image와 최종 text는 아직 매칭되지 않아 Figma 등에서 추가 작업할 계획이었다. (`07:42-07:58`)
- 감정 수정 API를 반영해 app bar의 날짜 옆에 emoji 형태로 감정을 표시하는 안을 적용했다. event 추가는 기존 event edit page를 재사용하고 edit mode 우측 하단 floating action button으로 진입시키는 방식으로 마무리했다고 설명했다. (`07:58-09:07`)
- 초기 release 관점에서 남은 Android 과제는 onboarding image·text, draft와 saved mode를 통일감 있는 UI로 구성하는 작업, notification 수신 설정, privacy policy·terms 연결이었다. server API는 대부분 있고 mobile 연동이 남은 것으로 확인되었다. (`13:40-18:04`)

### 초기 release 목표

- AgentCore 연결은 production endpoint와 ARN 등 설정이 들어가 있어 test가 필요하지만 비교적 빠르게 끝낼 수 있을 것으로 보았다. model 전환은 당장 기존 API 방식으로 우회 가능했다. (`11:37-13:20`)
- backend의 급한 기능은 거의 없고 Android UI가 마지막 큰 병목으로 정리되었다. 다음 날 대면에서 UI 결정을 최대한 확정하고 주말에 마무리해 다음 주부터 초기 release와 지인 test를 시작하는 목표를 잡았다. (`13:31-18:55`)
- 이는 목표 일정이며, 실제 review 요청이나 release 완료를 의미하지 않는다.

### 대화 notification의 가치와 민감성

- notification을 클릭했다는 이유만으로 messenger 대화 event를 만들면 단체방을 잠깐 읽은 경우도 중요 기록으로 간주되어 불필요한 event가 생긴다는 사례가 공유되었다. (`19:40-20:29`)
- 사람 관계 정보를 넣고 싶다면 call log가 더 직접적일 수 있다는 제안이 나왔지만, 기술·법적 이유로 이전에 전화·문자를 scope에서 뺐던 기억이 있어 재검토가 필요했다. (`20:31-24:16`)
- messenger notification에는 민감한 내용이 많고, 과도하게 event로 노출되면 사용자 경험에 부정적일 수 있다는 우려가 제기되었다. (`21:57-22:27`)
- 당장은 call log 등 새 data source를 넣지 않고, AI가 notification을 event로 선택하는 판단을 더 보수적으로 만들고 max event 수를 검증하기로 했다. call log는 beta 기간 중 다시 고려할 수 있는 후속 아이디어로 남겼다. (`24:23-26:35`)
- beta test에서는 사용자가 불필요한 event를 삭제하는 pattern을 지표로 남겨 어떤 source·rule이 문제인지 확인하자는 접근이 제시되었다. (`25:25-26:11`)

## 열린 질문

- Bedrock output 실패의 실제 원인은 max token, JSON tool configuration, network 중 무엇인가?
- 조직 SCP에서 신규 model을 허용받을 수 있으며 언제 적용되는가?
- user memory가 timeline의 맥락과 정확도를 실제로 얼마나 개선하는가?
- 탈퇴 7일 유예 동안 복구·재가입·삭제 취소 정책은 어떻게 동작하는가?
- 민감한 messenger notification을 어떤 기준으로 제외하고, 중요한 약속 대화는 어떻게 보존할 것인가?
- call log를 향후 수집한다면 Android permission, privacy, 법적 고지, spam filtering을 어떻게 처리할 것인가?

## 주의 사항

- 자동 전사에서 `Nova Lite`, `GPT 5.6 Luna`, `SCP`, `ARN`, `floating action button` 등 기술 용어가 왜곡되어 있다.
- timeline 사례의 생성 model은 회의 중 한 번 정정되었으므로 Bedrock 결과로 단정하면 안 된다.
- scheduler는 작업 완료 예상만 언급되었으며 production 배포와 실행 검증은 확인되지 않았다.
- call log는 아이디어였을 뿐 scope 추가 결정이 아니며, privacy·법적 검토 없이 수집 대상으로 기록하면 안 된다.
- 원문에는 개인 일정과 민감 notification에 관한 대화가 포함되어 있으므로 공개 범위를 제한해야 한다.
