# 369팀 스페이스 회의 요약 - 2026-09-03

## 개요

이번 회의에서는 marketing mentor에게 보여줄 landing page·pamphlet 준비, AI Timeline 정량 평가와 예상 inference cost, Android 읽기·편집 mode·notification·theme 구현, release build와 logging의 남은 작업을 점검했다. (`00:09-12:16`)

읽기 mode에서 편집 화면으로 들어가 event를 수정·추가하는 기능이 구현되었고, notification 수신 설정과 light·dark·system theme도 추가됐다고 보고되었다. 그러나 release build, login, logging은 남아 있어 다음 날보다 주말 release가 현실적일 수 있다고 일정이 조정되었다. (`11:00-20:03`)

beta 운영에서는 만족도·불만을 직접 수집하고, onboarding에 user 정보를 미리 넣는 실험과 일일 AI 호출 제한을 후속 검토하기로 했다. 이어 하루에 여러 번 draft를 생성할 때 server append 동작, client time window, 기존 record 조회·cache가 맞물려 UX가 불완전하다는 사실을 확인했다. 이 복수 생성 문제는 beta 중 재설계로 미루고, 초기 beta에는 하루 한 번 오후 9시 이후 생성하도록 app과 안내문에서 유도하기로 했다. (`20:05-35:13`)

## 상세 요약

### marketing asset과 AI 평가 준비

- landing page는 release와 동시에 완성할 필요는 없지만, 실제 UI와 더 나은 copy를 추가해 구조를 먼저 완성하기로 했다. 다음 날 marketing mentor에게 landing page와 promotion pamphlet을 보여줄 계획이었다. (`00:09-03:08`)
- AI Timeline 정량 metric을 거의 확정했고, prompt 변경 전후 결과를 동일 기준으로 점수화해 regression과 개선 폭을 확인하는 evaluation system에 반영할 계획이라고 했다. 분석 과정에서 prompt 문제도 다수 찾았다고 보고했다. (`03:12-03:57`)

### server 작업과 AI inference cost

- server 쪽은 cache 관련 구현을 다시 점검하며 잘못된 부분을 수정 중이라고 보고했다. 정확한 기술 용어는 자동 전사가 불명확하고, 작업 현황 문서에 상세 내용을 적었다는 언급만 있다. (`05:04-05:32`)
- Timeline 생성과 User Memory update를 한 묶음으로 보아 평균 약 `$0.1`, 대략 100~200원 수준이라는 내부 계산을 공유했다. User Memory update 단독 비용으로 들리는 `$0.0031`도 언급되었으나 정확한 model·token·환율·sample 조건은 제시되지 않았다. (`05:41-06:21`)
- 100명이 75일 동안 매일 한 번 사용하면 인당 약 `$7.5`라는 계산을 바탕으로 prepaid credit을 검토했다. 운영 기간, 최대 user 수와 비용 절감 여지가 남아 있어 총 신청액은 다음 날 정하기로 했다. (`06:21-10:40`)

### Android 기능과 release hardening

- 읽기·편집 mode를 같은 visual 구조로 맞추고, 편집 mode에서 AI 질문을 보여주며 별도 depth에서 수정하도록 구현했다고 보고했다. event를 원하는 시간대에 추가하는 기능도 server request와 연결됐다. (`11:00-15:37`)
- server notification 수신 설정과 app의 light·dark·system theme 선택을 구현했다. notification toggle naming과 즉시 theme loading은 추가 점검 대상이었다. (`11:08-11:40`, `15:37-16:43`)
- 기능 작업 뒤 release build, login, logging을 병행해 다음 날 release app을 목표로 했지만, 회의 후반에는 주말 release가 더 현실적일 수 있다고 보았다. (`11:40-11:59`, `16:47-20:03`)
- `수집 데이터 자세히 보기`는 debug build에만 남기고 user release에서는 숨기는 것으로 설명되었다. `초안 만들기` 문구는 자연스럽게 바꿀 필요가 있었다. (`18:09-19:21`)

### beta feedback과 onboarding experiment

- 지인 beta tester에게 link와 최소 사용 설명을 전달하고, 종료 시 form을 받는 단순 운영이 제안되었다. Timeline 완료 뒤 별점·불만 text를 받는 in-app feedback은 release 후 추가할 수 있다고 했다. (`20:05-22:50`)
- user 정보를 onboarding에서 직접 받는 것이 필요한지 검증하기 위해, 일부 지인의 동의를 받아 User Memory를 미리 넣고 결과 차이를 비교하는 아이디어가 나왔다. 실제 beta 중 수행 여부는 정해지지 않았다. (`21:30-22:15`)
- Play Store 심사·download 유지 서비스가 실제 AI call까지 수행하는지는 확인되지 않아 조사하기로 했다. 비용 때문에 release에는 일일 call limit이 필요할 수 있으며 beta에서 실제 생성 빈도를 먼저 관찰하기로 했다. (`22:55-25:54`)

### 하루 복수 생성과 beta 임시 운영

- 처음에는 beta tester가 원하는 때 자유롭게 생성하게 해 실제 사용 pattern을 보자는 의견이었다. (`25:57-26:31`)
- 현재 server는 같은 날 `DRAFT`가 있으면 새 data를 append하고 `SAVED`면 요청을 거절한다고 설명되었다. 이미 사용한 source item은 제외하고 새 item만 AI에 넣는 구조도 보고되었다. (`26:33-29:04`)
- 반면 client는 이전 Timeline의 end를 다음 window start와 연결하거나, 기존 날짜의 draft 존재를 정확히 조회해 button을 바꾸는 흐름이 완성되지 않았다. cached past record와 server 상태가 연결되지 않아 이미 생성한 날에도 `초안 만들기`가 보일 수 있다고 했다. (`29:05-33:14`)
- 기존 draft를 삭제하고 재생성하면 user memo가 사라질 수 있어 단순 reset도 안전하지 않았다. append quality와 window responsibility를 포함한 별도 설계가 필요하다고 판단했다. (`27:34-32:10`)
- full redesign은 beta 중으로 미루고, 초기 beta에는 하루에 한 번, 가능하면 오후 9시 이후 충분한 data가 쌓인 시점에 생성하도록 app button 주변과 안내문에서 알리기로 했다. (`33:18-35:13`)

## 주의 사항

- AI 비용은 회의 중 내부 계산이며 billing export나 재현 가능한 sample로 검증되지 않았다.
- 기능 구현과 server behavior는 회의 참여자의 보고이며 code·release artifact를 직접 확인하지 않았다.
