# 369팀 스페이스 회의 요약 - 2026-08-15

## 개요

이번 회의에서는 중간 보고서와 발표자료 마감 계획, 베타 테스트 진입 조건, Android UX·분석 로그의 우선순위, 회원 탈퇴와 재가입 처리, 발표용 시연 방식이 논의되었다. 작업 공유로는 scheduler multi-process 및 load script 정리 완료와 API 작업 진행, Laimory용 date-time picker component 설계, 보고서에 넣을 AI 생성 timeline 예시 제작이 보고되었다. (`01:08-02:49`)

팀은 발표 준비와 베타 준비를 병렬로 진행하는 방향을 잡았다. 당시 계획은 8월 16일까지 중간 보고서와 발표자료 초안을 마무리하고 19일까지 세부 내용을 다듬은 뒤 21일 발표를 진행하는 것이었다. 베타 테스트는 앱 UX를 release 가능한 수준까지 끌어올리고 외부 사용자를 모집한 뒤 시작하며, 이상적으로는 23일부터 29일까지 진행하면서 앱 심사를 병행하고 9월 초·중순 release와 marketing으로 이어가는 일정이 제시되었다. 다만 일정 지연 가능성도 언급되어 최소 3일이라도 테스트를 실행하는 것을 목표로 삼았다. (`03:17-10:53`)

베타 준비의 제품 과제로는 onboarding과 권한 설명, login, 사용 행동 지표, crash log가 제시되었다. 회원 탈퇴 후 즉시 재가입한 사용자를 soft-deleted row 복구로 처리할지 새 사용자로 만들지는 결정되지 않았다. 데이터 보존의 법적 근거와 app review 요구사항에 대한 발언도 있었지만 확인된 정책은 아니므로 별도 검증이 필요하다. (`11:13-16:47`)

## 상세 요약

### 개발 작업 공유

- Scheduler의 multi-process 관련 작업과 load script 정리를 마쳤고 API 작업을 진행 중이라고 보고했다. 구체적인 API 범위와 merge 여부는 전사에 없다. (`01:08-01:21`)
- Laimory 고유 component로 date-time picker를 만들기 위해 Figma 설계와 시간 설정 flow를 작업 중이라고 보고했다. beta tester가 timeline을 생성할 때 필요한 UX라는 설명이 붙었다. (`01:25-02:24`)
- 중간 보고서에 넣을 timeline 사례 이미지는 AI와 Figma를 이용해 event 형태를 시안으로 만들었고, 문서에 넣을 수 있는 수준이라는 판단이 공유되었다. 대학생·직장인·아르바이트 맥락의 세 예시를 고려했다. (`02:30-02:49`, `17:38-18:16`)

### 중간 보고서와 발표자료 일정

- 발표자료의 `50%` 제출 기준이 불명확해, 우선 outline과 내용 뼈대를 Google Slides로 구성하는 방식이 제안되었다. Design보다 내용의 안정성이 중요하고 design은 발표 직전까지 수정할 수 있다는 의견이 있었다. (`03:17-04:55`)
- 발표자가 직접 발표할 가능성이 높으므로 발표자료 초안을 먼저 작성하기로 했고, 중간 보고서도 함께 마무리해 가능한 한 16일 제출하는 것을 목표로 했다. (`04:32-05:52`)
- 회의 후반에는 보고서 page 수가 운영체제나 문서 rendering 환경에 따라 25·27 page로 다르게 보이는 문제가 확인되었다. 최종 PDF를 생성하는 환경에서 분량과 font·layout을 다시 검수하고 용어도 통일하기로 했다. (`21:30-25:55`)
- 결과물 형태는 긴 설명 대신 Android application으로 출시한다는 한 문장으로 정리하고, 실제 UI와 design 진행상황은 별도 화면·이미지에서 보여주는 방향이 논의되었다. (`23:14-25:12`)

### 베타 테스트와 release 계획

- 배포 infrastructure를 제외한 앱 UX를 beta test와 release에 사용할 수 있는 수준까지 완성하는 것을 첫 조건으로 두고, 이와 동시에 개발진이 아닌 외부 사용자를 모집하기로 했다. 약 10명도 유의미하다는 의견이었으나 확정 모집 인원은 아니다. (`06:18-07:00`)
- 테스트에서 어떤 행동과 지표를 수집할지 중간 보고서보다 더 구체화할 필요가 있다고 보았다. 발표 준비와 beta test 설계를 병렬로 진행하기로 했다. (`07:02-07:33`)
- 이상적 일정으로 8월 23~29일 beta test, test 중 app review 접수, 9월 초·중순 release 및 marketing 시작이 제안되었다. 이는 계획이지 확정 release 일정이 아니다. (`07:37-08:23`)
- Onboarding에서 회원가입 후 서비스 설명과 권한 요청을 어떻게 연결할지, 앱 내부 행동을 어떤 지표로 측정할지가 release 전 UX 과제로 제시되었다. Onboarding 자체는 beta 이후로 미룰 가능성도 언급되었다. (`09:00-09:31`)
- AI 쪽에서는 timeline 구성 결과를 여러 agent·model 후보와 비교하는 실험이 언급되었지만 자동 전사가 불명확하여 정확한 model 조합과 평가 계획은 확인이 필요하다. (`09:31-09:49`)
- 최종 일정 정리에서는 16일까지 보고서와 발표자료 초안, 19일까지 세부 수정, 21일 발표와 동시에 beta 준비를 진행하되, 일정이 밀리더라도 최소 3일의 beta test를 실행하는 것이 최우선 과제로 정리되었다. (`10:03-10:53`)

### 회원 탈퇴, 재가입과 데이터 삭제

- 회원 탈퇴 직후 같은 정보로 재가입할 때 새 user row를 만들지 기존 soft-deleted row를 복구할지 질문이 제기되었다. (`11:13-11:25`)
- 기존 row를 즉시 물리 삭제하지 않고 soft delete 상태로 보존한 뒤 가입 시 중복 정보를 확인해 복구하는 방법과, 악용 방지 기록만 남기고 새 사용자로 생성하는 방법이 모두 제시되었다. 어느 방식도 최종 결정되지 않았다. (`11:28-12:31`)
- 탈퇴 시 어떤 데이터가 남거나 삭제되는지 안내 message가 필요할 수 있다는 의견이 나왔다. beta 단계에서는 완전한 데이터 삭제 기능을 미루고 탈퇴 기능까지만 구현하는 방안도 언급되었다. (`12:36-13:01`)
- 계정에 개인 data를 저장하는 서비스이므로 탈퇴·삭제 기능이 app review에서 필요할 수 있다는 우려가 제기되었다. 이는 회의 참가자의 추정이며 실제 법률·store policy 확인 결과가 아니다. (`13:04-14:03`)

### Analytics와 mobile 안정성

- Onboarding·login 개선과 함께 beta tester의 행동을 측정할 logging을 병렬로 준비하기로 했다. (`14:14-15:58`)
- 우선순위는 business metric log와 crash/error log이며, performance log는 앱 성능 지표이므로 후순위로 두는 방안이 설명되었다. (`15:17-16:27`)
- Business metric은 GA4, mobile error·crash는 Firebase 계열 도구를 활용하는 방향이 언급되었다. 정확한 event schema와 수집 동의 범위는 정해지지 않았다. (`15:23-16:47`)

### 발표용 시연과 문서 이미지

- 발표에서는 live demo보다 변수를 줄인 사전 녹화 영상을 사용하는 쪽이 낫다는 의견이 모였다. 실제 수집이 잘 된 날의 data로 timeline 생성·편집·저장 flow를 보여주는 시나리오가 제안되었다. (`18:33-21:14`)
- Android Studio의 screen recording과 cut editing을 활용할 수 있고, 구현이 부족하면 prototype을 보조적으로 사용할 수 있다는 제안이 있었다. 구체적인 촬영본은 다음 주 상태를 보고 결정하기로 했다. (`19:03-21:14`)
- Timeline 예시 이미지와 실제 앱 icon·화면을 보고서에 추가하되, 최종 PDF page 수를 확인해 크기와 배치를 조정하기로 했다. (`17:06-18:28`, `24:35-25:55`)

## 주의 사항

- 전사에는 참가자 label이 있지만 자동 전사 오류가 많아 담당 범위와 완료 상태는 명시된 발언 밖으로 확장하지 않았다.
- Beta test와 release 일정은 목표안이며 뒤 회의에서 변경될 수 있다.
- 회원 탈퇴 data 보존과 app review 관련 발언은 법률 또는 platform policy 확인 결과가 아니다.
- `Firebase`, `GA4`, AI model 비교 관련 용어 일부가 왜곡되어 정확한 도구와 설정은 code·issue에서 확인해야 한다.
- 원문에는 개인 일정과 이동 계획이 포함되어 있으므로 공개 범위를 제한해야 한다.
