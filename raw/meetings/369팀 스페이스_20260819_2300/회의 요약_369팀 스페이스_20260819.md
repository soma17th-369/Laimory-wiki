# 369팀 스페이스 회의 요약 - 2026-08-19

## 개요

이번 회의는 다음 날 중간 발표를 위한 시연 영상 검토와 전체 rehearsal이 중심이었다. 약 4분 50초의 원본 앱 사용 영상을 30초로 편집했고, 개별 화면 자막보다 발표자가 data 선택, loading, timeline 생성·편집·emotion 선택을 짧게 narration하기로 했다. 최종 화면과 calendar 재진입까지 보여주기 위해 영상을 조금 늘리는 안도 논의되었다. (`01:34-07:10`)

전체 발표 rehearsal은 중간 중단과 영상 전환을 포함해 약 18분 17초가 걸렸다. 팀은 20분 제한 안에 여유가 있지만 기술 section의 말이 빨라 청자가 따라가기 어렵고, 문제 인식·기획 의도·시장 분석 사이 전환이 갑작스럽다는 feedback을 확인했다. Section title slide를 추가하고, “기록을 통한 성장” 연구 근거는 기존 문제 정의와 연결이 약하므로 기획 의도에서 빼는 방향으로 정리했다. (`28:20-49:35`)

Rehearsal script에는 MVP와 architecture, beta·marketing 계획이 폭넓게 포함되었다. Login부터 data 수집, AI timeline 생성, 편집·저장까지 실제 기기에서 동작한다는 발표 문구와 함께, Android local normalization·batch, API server의 data·job 관리, multi-agent AI pipeline, model comparison과 evaluation, 8월 말 beta test, KPI와 revenue model이 설명되었다. 다만 이는 발표 rehearsal의 주장으로, 수치와 외부 시장·연구 근거, 구현 완료 상태를 이 회의에서 독립 검증한 것은 아니다. (`10:06-28:14`)

## 상세 요약

### 시연 영상 검토

- 원본 앱 사용 영상은 약 4분 50초였고, timeline data 확인부터 loading·결과 편집까지 빠르게 보여주는 30초 version으로 cut editing했다. (`01:34-02:40`)
- 자막이 너무 빠르게 지나갈 수 있어, 영상에는 최소한의 화면만 두고 발표자가 기능 흐름을 narration하는 쪽으로 정리되었다. (`03:06-04:50`, `06:12-07:10`)
- 30초 version이 timeline 완성 직전에 끝나는 문제가 있어, emotion 선택·저장과 calendar에서 기록을 다시 여는 화면까지 추가하면 약 35~43초가 될 수 있다는 추정이 나왔다. 실제 최종 길이는 확정되지 않았다. (`05:02-06:11`)
- 발표 narration은 수집 data 확인·선택, generation loading, 생성된 timeline의 memo·time·event 수정, emotion 선택 순서로 구성하기로 했다. (`06:12-07:10`)

### 제품 문제와 MVP 발표 내용

- 발표 script는 사람들이 일상을 기록하려는 수요는 있지만 사진·위치·일정이 여러 app에 흩어져 있고 정리 비용이 커 지속하기 어렵다는 problem definition을 제시했다. (`10:22-11:16`)
- Laimory는 mobile data를 연결해 하루 초안을 먼저 만들고, 기록 부담을 낮추며 장기적으로 personal AI memory experience를 제공하는 service로 설명되었다. (`11:16-12:37`)
- 세 핵심 기능은 timeline 기반 기록, 목표 관리, 누적 기록을 이해하는 AI conversation으로 소개되었고, 현재 minimum MVP는 첫 번째 daily timeline flow로 좁혔다고 설명했다. (`12:37-13:29`)
- Login, data collection, AI timeline generation, user editing·save까지 실제 기기에서 동작한다는 발표 문구가 있었다. 이는 rehearsal 문구이며 feature별 test evidence는 이 전사에 첨부되지 않았다. (`13:14-13:29`, `16:21-17:43`)

### Mobile과 API server 발표 내용

- Mobile은 서로 다른 permission과 format의 data를 공통 구조로 normalize해 local에 보존하고, 일부 data source가 실패해도 전체 flow가 중단되지 않도록 설계했다고 설명했다. Location의 stay·movement 등 필요한 정보는 야간 batch로 처리해 동작을 줄인다는 설명도 있었다. (`18:44-19:32`)
- AI timeline 생성이 약 40초 이상 걸리므로 job key를 보관하고 polling과 FCM으로 완료를 알리며, app 종료·재실행 뒤에도 작업 continuity를 확인하는 비동기 flow를 설명했다. (`19:33-19:55`)
- API server는 authentication, input validation, masking, location·job status·result를 관리하며 computing resource부터 APM까지 monitoring을 구성했다고 발표했다. (`19:56-20:15`)
- GPS에 없는 address·place name을 Kakao 계열 API로 보강하면서 duplicate coordinate를 제거하고 네 개씩 병렬 처리하며 partial failure를 허용한다고 설명했다. 정확한 batch size와 구현 상태는 code 확인이 필요하다. (`20:15-20:30`)
- AI server가 DB schema에 직접 의존하던 구조를 API server 경유로 바꿔 DB 관리 책임을 분리했다고 설명했다. User identifier는 secret-key 기반 one-way transform으로 처리하고 key는 AWS Secrets Manager에 분리한다는 문구가 있었다. 자동 전사의 algorithm 명칭은 불명확하다. (`20:35-21:12`, `46:44-46:55`)

### AI pipeline과 quality control 발표 내용

- Input으로 location 기반 stay·movement, calendar schedule, Health Connect data, notification, photo, User Memory를 모아 하루 일정을 추론한다고 설명했다. (`21:12-21:31`)
- 전체 pipeline은 source별 event agent가 병렬 분석하고, normalized result를 timeline agent가 통합하며, 전사상 `리테일 에이전트`로 들리는 검증 agent가 결과를 검토·개선하고 question agent가 journal prompt를 만드는 multi-agent 구조로 소개되었다. 정확한 agent 명칭은 확인이 필요하다. (`21:32-22:22`)
- 실행 경로를 통제하기 위해 LangGraph를 선택했고, GPT·Gemini·Amazon Nova 계열 model을 교체 비교해 quality와 cost를 기준으로 선정할 예정이라고 설명했다. (`22:22-22:49`)
- Prompt에 보존해야 할 input과 length·time constraint, style rule을 명시하고, 가능한 consistency rule은 code로 결정론적으로 검증한다고 했다. 관계·생활 pattern·관심사를 User Memory로 갱신해 다음 timeline에 참고하는 구조도 소개했다. (`22:50-23:54`)
- LLM으로 result를 평가하고 improvement와 test data를 만드는 evaluation system, 운영 event와 agent run을 분리 관찰하는 monitoring이 언급되었다. Tool 명칭은 전사상 `Elasticsearch`, `랭스`로 들려 정확한 stack을 확인해야 한다. (`23:55-24:17`)
- 현재 deployment를 전사상 `이 시`로 들리는 환경에서 운영하고 향후 AWS AgentCore로 전환해 cost를 줄일 계획이라는 문구가 있었다. 현재 환경 이름과 전환 feasibility는 확인되지 않았다. (`24:11-24:25`)

### Beta, marketing과 KPI 발표 내용

- 발표 script에는 8월 24~30일 또는 24~31일 약 20명을 대상으로 beta test를 진행하고, behavior metric·survey·interview로 개선한 뒤 9월 release한다는 일정이 포함되었다. 같은 rehearsal 안에서도 종료일이 다르게 언급되어 확정 일정 확인이 필요하다. (`16:21-16:43`, `25:20-25:43`)
- Marketing message는 “오늘 하루를 기억하고 남기고 싶다”와 “일기 작성 부담을 줄인다” 두 appeal을 A/B test하는 방향으로 설명되었다. (`24:26-25:20`)
- Campaign KPI는 click뿐 아니라 install, first journal completion, first-value-action conversion과 acquisition cost를 보고, in-app KPI는 주요 기능 이용과 day 1·7·30 retention을 본다는 계획이었다. (`25:44-26:22`)
- Subscription tier, 월 운영비 약 90만원, tier별 break-even user 수가 발표에 포함되었지만 이는 draft business assumption이며 근거 자료를 이 회의에서 검증하지 않았다. (`26:57-27:47`)

### Rehearsal feedback과 script 수정

- Rehearsal은 중간 interruption을 포함해 약 18분 17초였다. 20분 안에는 들어오지만 pause와 실제 발표 변수를 고려해 여유를 남기자는 의견이 있었다. (`28:20-28:43`, `32:43-34:32`)
- 문제 인식, 기획 의도, MVP, 시장 분석처럼 topic이 바뀔 때 전환이 갑작스러웠다. Section title slide 또는 명시적인 전환 문장을 추가하기로 했다. (`29:19-31:38`)
- 기술 section은 정보량이 많아 말이 빠르고 청자도 숨이 차는 느낌이라는 feedback이 있었다. 내용을 더 넣기보다 pace를 늦추고 미정제 문장을 다듬기로 했다. (`32:43-34:32`)
- “목표 진행을 기록하면 성과가 향상된다”는 연구를 이용해 성장 가치를 기획 의도에 넣었지만, 기존 problem definition에서 갑자기 등장한다는 문제가 있었다. 팀은 해당 부분을 빼는 쪽으로 정리했다. (`34:36-43:41`)
- MVP 다음에 바로 market analysis가 나오는 흐름도 지적되었지만, 보고서 순서를 따르는 구성이라는 설명과 section transition을 추가하면 수용 가능하다는 의견이 있었다. (`44:19-46:17`)
- Technical script에는 `Secret Manager`를 `AWS Secrets Manager`로 명확히 고쳤고, 마지막 anticipated-question slide는 Q&A reference로 남기되 발표 중 설명은 시간에 따라 optional하게 하기로 했다. (`46:21-49:35`)

### Beta tester 모집

- 회의 말미에 beta tester 한 명을 추가로 모집했다고 보고했고, 두 명 정도를 더 모집할 가능성도 언급했다. 전체 확정 인원은 확인되지 않는다. (`51:21-52:17`)
- 다음 날 발표 후 beta test 준비를 본격적으로 진행하기로 했다. (`51:21-52:19`)
