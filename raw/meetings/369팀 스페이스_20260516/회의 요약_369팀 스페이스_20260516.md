# 369팀 스페이스 회의 - 2026-05-16

## 개요

이 회의는 기획심의 전까지 팀 논의를 자주 이어 가기 위한 일정 조율과 제품 방향 재정의가 중심이었다. 팀은 기존의 “일기를 쉽게 쓰게 해 주는 앱”이라는 설명에서 벗어나, 모바일 기기에 흩어진 디지털 흔적을 AI가 수집·가공해 사용자의 삶을 기록하는 라이프로깅 서비스로 문제 범위를 넓히려 했다. 일기와 회고는 여전히 중요한 사용 경험이지만, 핵심 제품 자체라기보다 자동 생성된 생활 기록을 사용자가 되돌아보고 의미를 붙이는 선택적 인터페이스로 보는 의견이 강하게 제시되었다. (`00:30-19:28`)

또한 서비스가 답을 대신 내려 주기보다 사용자의 회상과 성찰을 돕는 “서포터”가 되어야 한다는 관점, 모바일 데이터가 충분한 사용자를 우선적인 고객으로 삼아야 한다는 관점, 장기적으로는 개인의 일상을 이해하는 AI agent 또는 second brain으로 발전할 수 있다는 비전이 논의되었다. 모바일 구현 측면에서는 실제 기기 데이터가 필요하므로 emulator만으로는 검증이 어렵고, test build와 release build를 구분해 오류를 확인하는 개발 환경이 필요하다는 의견도 나왔다. (`09:23-25:13`)

## 상세 요약

### 회의 운영과 일정

- 전주에 팀이 충분히 만나지 못해 아이디어 진척이 적었다는 평가가 나왔고, 기획심의 전까지 주 5일 이상 짧게라도 논의하자는 제안이 있었다. (`00:30-01:11`)
- 평일에는 늦은 시간, 대략 오후 10시부터 30분에서 1시간 정도 논의하는 방안이 선호되었으나 요일별 가능 시간은 달랐다. (`01:11-03:08`)
- 다음 회의는 논의 끝에 `15:30-16:30`으로 잡힌 것으로 보이며 일정이 수정되었다는 발언이 있다. (`36:09-39:04`)

### 제품 문제 정의의 전환

- 목표를 먼저 정하고 기록을 통해 반복 패턴이나 실수를 발견하며 회고를 돕자는 아이디어가 제시되었다. (`03:16-04:30`)
- 제품의 핵심을 “AI를 통한 라이프로깅”으로 보고, 사람들이 왜 라이프로깅을 필요로 하는지와 현재 방식에서 겪는 뾰족한 문제를 찾아야 한다는 의견이 이어졌다. (`04:35-06:16`)
- 기존 일기 문제만으로는 제품 필요성을 설득하기 어렵고, 해결책이 반드시 일기 형식일 필요도 없다는 문제 제기가 있었다. 구현 가능한 기능보다 먼저 명확한 문제 문장을 세우자는 취지다. (`06:24-08:10`, `13:05-18:08`)
- 반대로 일상은 하나의 문제로 설명하기 어려울 만큼 다양하므로 지나치게 좁은 문장에 맞추기 어렵다는 이견도 있었다. 팀이 이날 하나의 최종 문제 문장에 합의한 것은 아니다. (`14:26-15:19`)

### 라이프로깅, 일기, 회고의 관계

- 모바일 기기에서 정보를 저장·가공하고 AI가 하루의 기록을 자동으로 만들어 주는 것이 중심 기능으로 제시되었다. (`04:44-05:15`, `12:56-14:14`)
- 일기는 자동 생성된 하루 기록 위에 사용자가 생각이나 감정을 더할 수 있는 선택적 기능으로 보는 안이 논의되었다. 일기를 쓰지 않더라도 로그 자체는 남길 수 있어야 한다는 의견이다. (`09:23-13:05`)
- 회고의 최종 주체는 사용자이며 서비스는 목표, 질문, 힌트를 제공해 사용자가 스스로 돌아보도록 지원해야 한다는 “서포터” 관점이 제시되었다. (`11:19-12:52`)
- 기록만 모으는 데서 끝나지 않고, 수집된 데이터를 이용해 무엇을 해결할지와 어떤 가치를 보여 줄지 정리해야 한다는 점에는 공감대가 있었다. (`18:38-19:28`)

### 사용자와 데이터 범위

- 모바일에 사진, 일정 등 많은 흔적을 남기는 사용자가 서비스의 “베스트 고객”에 가깝고, 데이터가 거의 없는 사용자는 초기 핵심 고객과 거리가 있다는 의견이 나왔다. (`19:35-20:42`)
- 모바일 데이터를 적게 남기는 사람에게 수기 입력이나 일기를 요구할지, 초기 범위에서 제외할지는 결정되지 않았다. (`19:35-20:25`)
- 장기적으로는 축적된 라이프로그를 기반으로 사용자의 일상을 이미 이해하는 개인 AI agent를 만들 수 있다는 비전이 제시되었다. (`24:09-25:24`)

### 모바일 구현과 테스트 환경

- 실제 사진·일정 등 기기 데이터를 다루므로 emulator만으로는 충분한 검증이 어렵고, 실제 Android 기기 또는 공기계가 필요할 수 있다는 경험이 공유되었다. (`21:26-22:53`)
- 팀원이 사용할 APK를 배포하고, test mode와 release mode를 구분하며 test mode에서는 오류와 로그를 쉽게 확인하도록 하는 아이디어가 제시되었다. (`23:13-24:09`)
- 모바일에서 수집 가능한 정보의 범위와 난이도를 조사해 제품 방향과 연결하자는 제안이 있었다. (`28:29-28:59`)

## 진행 상황

- 기존 일기 중심 아이디어를 모바일 AI 라이프로깅 관점으로 다시 정의하는 중이다. (`04:35-19:28`)
- 일기·회고를 선택적 사용자 입력으로 두고 자동 생성 기록을 중심에 두는 기능 구성을 탐색 중이다. (`09:23-14:14`)
- 실제 모바일 데이터 수집 가능성과 test/release 환경을 조사·설계하려는 단계다. (`21:26-24:09`, `28:29-28:59`)
