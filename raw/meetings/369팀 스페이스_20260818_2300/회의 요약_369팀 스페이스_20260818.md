# 369팀 스페이스 회의 요약 - 2026-08-18

## 개요

이번 회의에서는 50장 안팎의 중간 발표자료와 script 검수, push notification의 광고성·야간 수신 동의, 사업자 등록이 필요한 약관 준비, Android 시연 flow와 notification filtering 구현, 발표용 promotion image와 영상이 논의되었다. 발표자료는 mobile·server section을 담당자가 검수하고, 20분 제한 안에서 30초 내외 시연 영상을 포함하도록 연습하기로 했다. (`00:19-03:04`, `16:22-17:39`)

Push API는 1차 구현이 끝나 review를 앞두고 있었지만, retention 목적 notification이 광고성인지 정보성인지가 불명확했다. 현재 code는 광고 type이면 앞에 광고 표시와 수신 거부 경로를 붙이는 방식으로 작성되었고, 광고·야간 수신 동의를 user flow에 넣는 문제는 미결로 남았다. 회의에서 과거 업무 경험과 다른 app 사례가 공유되었지만 법률 검토 결과가 아니므로 광고성 분류, 21시 이후 발송 제한, 동의 방식은 별도 확인이 필요하다. (`03:14-10:17`)

Mobile에서는 timestamp spinner, calendar API, draft/saved 상태별 저장 flow를 적용했다고 보고했다. Notification은 privacy filter, keyword filter, 반복 갱신되는 live notification 제거를 issue로 정리했지만 아직 완료되지 않았다. 발표 영상을 위해 loading 화면, nickname 조회, notification 정리를 진행한 뒤 app tester에 배포할 계획이었다. (`10:22-12:24`)

## 상세 요약

### 발표자료와 script 검수

- 발표자료는 약 50 slide이며 mobile section과 server section의 기술 설명을 각 담당자가 확인해 달라는 요청이 있었다. AI가 만든 초안이므로 내용 오류와 누락을 comment로 남기기로 했다. (`00:19-02:36`)
- 발표 script도 작성 중이었고, 발표자가 이해할 수 없는 수준은 아니지만 각 section에서 강조할 내용을 추가해 달라고 요청했다. (`00:41-02:13`)
- 발표 시간이 25분이 아니라 20분임을 확인했다. 50 slide와 약 30초 demo를 포함하므로 실제 rehearsal로 pace를 측정하고, 필요하면 내용을 줄이기로 했다. (`16:22-17:39`)
- Promotion mockup은 발표자료의 제품 소개를 보강하는 용도이며, beta·release용 정식 marketing asset과는 구분했다. 무료 template이나 Figma·Canva 계열 도구를 검토했고, 한 참가자가 8월 19일 15시까지 만들어 보기로 했다. (`12:29-16:20`)

### Push notification API와 동의

- 약관 작업과 push notification API를 진행 중이라고 공유했다. Push API는 1차 구현을 마쳐 review하면 되는 단계라고 보고했다. (`03:14-05:05`)
- Retention notification이 광고성인지 정보성인지 기준이 불명확했고, 광고성일 경우 앞에 광고 표기와 수신 거부 경로를 넣어야 한다는 이해를 바탕으로 type별 formatting code를 작성했다. (`03:30-04:42`)
- 광고성·야간 push 수신 동의를 client user flow에서 언제, 어떻게 받을지 함께 설계할 필요가 있다고 했다. (`03:34-05:01`)
- 승인 기관이 별도로 있는 것이 아니라 잘못 분류하거나 동의 없이 야간 발송했을 때 법적 risk가 있다는 설명이 나왔다. 다른 참가자는 과거 알림톡 template 승인 경험과 일반 push 경험을 공유했지만, 현재 서비스에 그대로 적용할 수 있는 근거는 아니다. (`05:33-08:26`)
- 광고 표시는 가급적 붙이지 않는 방향이 선호되었지만, marketing 수신 동의 또는 일반 알림 수신 동의가 필요하다는 점을 다시 확인했다. 다만 정확한 동의 명칭과 법적 요건은 결론나지 않았다. (`07:06-09:13`)
- 다른 app의 설정처럼 notification category별 opt-in/out 또는 방해금지 시간을 제공하는 참고 사례가 언급되었다. Laimory가 어떤 category와 setting을 제공할지는 미결이다. (`09:15-10:17`)

### 약관과 사업자 등록

- 약관 준비 과정에서 사업자 등록이 필요하다고 파악했다는 보고가 있었다. 등록은 약 이틀이면 된다는 검색 결과가 공유되었고, 목요일에 신청하는 일정이 제안되었다. (`05:05-05:30`)
- 사업자 등록 필요 여부와 처리 기간은 회의 중 조사 결과에 불과하므로 실제 관할기관 절차와 제출 서류를 확인해야 한다.

### Android 구현과 demo 준비

- Date-time 관련 timestamp spinner 적용, calendar API 연동, timeline 조회 결과가 saved인지 draft인지에 따라 저장 상태를 처리하는 변경을 완료했다고 보고했다. (`10:22-10:59`)
- Notification은 작업량이 커 완료하지 못했지만, privacy 관련 filtering, keyword별 수집, 계속 갱신되는 live notification 제거를 issue 수준에서 정리했다. (`10:50-11:36`)
- AI 결과를 기다리는 loading 화면을 구현 중이며, FCM message 도착 전 user가 보는 flow를 발표 영상에 포함하려 했다. 이후 notification 정리와 nickname 조회를 연결해 recording 가능한 상태를 만들 계획이었다. (`11:29-12:24`)
- Recording 준비가 되면 app tester에 build를 배포하기로 했다. 배포 완료가 아니라 계획 상태다. (`11:52-12:24`)

### 시연 영상과 발표 시나리오

- 시연 영상은 실제 앱을 켜고 수집 data 확인·선택, timeline 생성, loading, 결과 편집, emotion 선택과 저장, calendar에서 이전 기록 확인까지 보여주는 약 30초 시나리오로 정리되었다. (`21:28-23:25`)
- YouTube link를 여는 대신 laptop의 다른 desktop에 video를 미리 전체화면으로 준비하고 PDF와 swipe로 전환하는 방안이 제안되었다. Network나 link loading 변수를 줄이려는 목적이다. (`21:28-22:24`)
- 영상은 완성품의 proof를 보여주는 목적이 크고, login과 notification filter가 완전하지 않더라도 실제 동작 부분을 압축해 보여주자는 의견이었다. (`22:24-23:25`)

### Saved timeline 수정 검증

- Saved 상태의 event가 server에서 수정 가능한지 불확실하다는 문제가 제기되었다. Mobile에서 수정 중 문제가 있었고 AI 설명으로는 draft에서만 허용된다고 했지만, AI가 잘못 이해했을 가능성이 있어 server code를 교차 검증하기로 했다. (`23:53-25:38`)
- Server에서 문제가 확인되면 수정하고, 정상이어도 mobile side 확인을 위해 결과를 공유하기로 했다. (`24:24-25:38`)

### Mentoring 일정

- 중간 발표 직후 beta 작업에 집중하기 위해 이번 주 mentoring을 건너뛰거나 online·async feedback만 받는 선택지가 논의되었다. 확정된 mentoring 방식은 없다. (`17:45-21:23`, `26:00-26:48`)

## 주의 사항

- Push 광고성 분류와 야간 발송 제한에 관한 내용은 회의 참가자의 조사·경험이며 법률 자문이 아니다.
- `21시`, `사업자 등록 이틀` 같은 수치는 공식 문서로 검증되지 않았다.
- Implemented, completed라는 표현은 발언자의 작업 보고 기준이며 integration·deployment 완료를 의미하지 않을 수 있다.
- FCM, Firebase, Android tool과 server API 명칭은 자동 전사에서 일부 왜곡되었다.
- 원문에는 개인 약속과 숙박·이동 계획이 포함되어 있으므로 공개 범위를 제한해야 한다.
