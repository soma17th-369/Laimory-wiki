# 369팀 스페이스 회의 요약 - 2026-08-06

## 개요

주요 참가자들은 사용자 메모리 갱신, 생성형 AI 결과의 품질 검증, API 부하 테스트, Android 위치·체류 데이터 개선 작업을 진행하는 개발자들이다. 이번 회의에서는 동일 사용자의 여러 타임라인이 동시에 저장될 때 User Memory 갱신 작업이 충돌할 수 있는 문제, 전사상 `SSLN`으로 들리는 고차원 필터의 역할과 검증 방법, LLM 기반 AI 품질 검증 프로그램, 외부 지도 관련 API 호출에서 관찰된 성능 저하, 실제 이동 데이터를 이용한 위치·체류 판정 검증이 논의되었다.

User Memory와 관련해서는 MQ가 없는 현재 구조에서 처리 중인 사용자의 추가 작업을 Redis에 보관하고, 트래픽이 낮은 시간대에 하루 한 번 batch로 처리하는 방안이 설명되었다. 다만 발언자가 같은 구간에서 “수정했다”와 “설계했다”를 모두 사용했기 때문에, 이것이 최종 합의이자 구현 완료 상태인지 아니면 잠정 설계인지 전사만으로 확정할 수 없다. 또한 `DLQ`라는 표현은 등장하지만, 일반적인 dead-letter queue와 동일한 구현인지 단순한 보류·실패 작업 저장소인지 확인이 필요하다. (`00:48-03:13`)

부하 테스트에서는 외부 지도 관련 API 호출이 포함된 구간이 동시 사용자 약 5명부터 눈에 띄게 느려졌다는 관찰이 공유되었다. 동시에 하루 한 번 호출될 것으로 예상되는 draft API에 높은 동시성 부하 테스트를 적용하는 것이 실제 사용 패턴에 부합하는지 의문도 제기되었다. 위치 데이터 쪽에서는 개선된 build를 앱 콘솔에 배포했고, 다음 날 실제 이동 데이터로 위치·체류 수집을 검증하기로 했다. 위도·경도를 사람이 읽을 수 있는 주소로 바꾸는 기능은 Android 내부 기능을 활용해 별도 API key 없이 구현했지만, 도로명 주소와 지번 주소가 일관되지 않는 문제가 남아 있다. (`04:12-10:00`)

외부 지도 서비스의 장소명 조회와 관련해서는 서버 측 API 부하가 해결되지 않을 경우 client에서 주소를 추출하고 Kakao 계열 API로 장소명을 조회하는 대안이 제시되었다. 회의에서는 여러 지도 앱도 client에서 key를 사용한다는 취지의 의견과 서버 부담 또는 노출을 줄일 수 있다는 기대가 나왔지만, 이 방식의 보안성이 검증되거나 최종 결정된 것은 아니다. client key의 플랫폼 제한, 호출 제한, 악용 방지와 server-side proxy 방식의 장단점은 별도로 검토해야 한다. (`10:04-11:35`)

## 상세 요약

### 사용자 메모리 관리

- 타임라인이 하나 작성될 때마다 해당 타임라인을 바탕으로 하나의 User Memory를 갱신하는 작업이 진행 중이라고 보고되었다. (`00:48-01:13`)
- 핵심 문제는 동일 사용자가 여러 타임라인을 거의 동시에 저장할 때 User Memory 갱신 작업이 겹칠 수 있다는 점이다. 개별 작업은 약 30초에서 1분 내외로 예상되지만, 오늘 데이터와 전날 데이터처럼 여러 작업이 한꺼번에 들어오면 처리 순서와 충돌 관리가 필요하다. (`01:13-01:49`)
- MQ가 있다면 작업을 보존하고 선행 작업의 완료를 감지해 후속 작업을 처리할 수 있지만, 현재는 그러한 중간 처리 장치가 없다고 설명했다. (`01:49-02:10`)
- 처리 중인 사용자의 추가 요청을 Redis에 저장하고, 트래픽이 낮은 시간대에 하루 한 번 batch로 처리하는 방안이 언급되었다. User Memory는 실시간 갱신이 필수적이지 않아 하루 한 번으로도 충분하다는 판단이 그 배경이다. (`02:12-02:54`)
- 한 번의 batch에 작업이 여러 개 쌓였을 때 일부만 성공하고 나머지가 실패하는 경우의 처리 순서, 재시도, 성공·실패 확인 방식은 추가 검증 과제로 남았다. 회의에서 성공률과 실패율을 실제 지표로 모니터링하기로 확정했다는 발언은 확인되지 않는다. (`02:54-03:13`)
- 전사에는 `DLQ`, “데드레터 Q”라는 표현이 나오지만 실제 아키텍처가 표준 dead-letter queue인지, 실패 작업만 저장하는 목록인지, 혹은 충돌을 피하기 위한 대기 저장소인지 구분되지 않는다. (`02:16-02:35`)

### 불확실한 필터 기술 용어

- `03:13-03:41` 구간에서는 전사상 `SSLN 도입`으로 기록된 어떤 필터 기술이 언급된다. 발언자는 이 필터가 어떤 역할을 해야 하는지부터 생각하고 있으며, “좀 더 고차원의 필터”라고 설명했다. (`03:13-03:35`)
- 구현 접근법과 테스트 방법을 계속 고민하는 초기 탐색 단계로 보인다. 기능 범위나 평가 기준이 확정되었다는 근거는 없다. (`03:25-03:41`)
- `SSLN`은 자동 전사 오류일 가능성이 있으므로 정식 기술명으로 사용하면 안 된다. 원음, 관련 이슈, 설계 문서 또는 코드에서 정확한 용어를 확인해야 한다.

### AI 품질 검증 프로그램

- LLM과 관련된 AI 품질 검증 프로그램을 local 환경에서 개발 중이라고 보고했다. 자동 전사의 “생선이 AI 품질검증”은 “생성 AI 품질 검증” 등을 잘못 인식했을 가능성이 있다. (`03:41-03:53`)
- 프로그램이 완성되면 repository에 올려 팀이 접근할 수 있게 할 예정이라고 말했다. 현재는 local 개발 단계이며, 완료 시점이나 통합 방식은 제시되지 않았다. (`03:53-04:04`)

### 부하 테스트 및 API 성능

- 부하 테스트 설계를 마치고 테스트를 진행 중이며, 테스트에서 발견되는 내용은 기존 작업 현황 화면에 기록하고 있다고 보고했다. (`04:12-04:34`)
- 외부 지도 관련 API 호출이 포함된 구간에서 동시 사용자 약 5명만 되어도 체감상 크게 느려졌다는 관찰이 공유되었다. 이는 회의 발언에 근거한 잠정 수치이며, 측정 환경·응답 시간·오류율이 제시된 정식 benchmark 결과는 아니다. (`04:34-04:55`)
- 하루 한 번 요청될 것으로 예상되는 draft API는 사용자 요청이 실제로 겹칠 가능성이 낮아, 이 API를 고부하 테스트의 핵심 대상으로 선택한 것이 적절한지 의문이 제기되었다. (`04:58-05:23`)
- 대부분의 API 응답 데이터가 사용자마다 달라 일반적인 caching을 적용하기 어렵다는 제약도 언급되었다. (`05:29-05:39`)
- 실제 동시성 요구를 재검토하면서도 현재 API 성능 자체가 좋지 않다고 판단해 개선 작업을 계속하고 있다고 보고했다. (`05:42-05:56`)

### 위치·체류 데이터 개선

- 위치와 체류 정보 수집 로직을 개선한 build가 앱 콘솔에 배포되었다. 팀원들에게 다음 날 출발 전에 update하고 실제 이동 중 수집된 데이터를 함께 확인해 달라는 요청이 있었다. (`06:04-07:00`)
- 실내나 정적인 테스트만으로는 충분하지 않아 실제 이동 데이터를 바탕으로 위치·체류 판정이 의도대로 동작하는지 확인하려는 목적이다. (`06:10-06:49`)
- 회의 후반에는 체류와 이동 구분이 함께 올바르게 작동해야 한다고 언급했다. 전사상 이동 관련 기준을 20분으로 설정한 것으로 들리며, 20분 미만 이동이 잘못 잡히면 빠르게 수정하겠다고 말했다. 정확한 설정값과 의미는 코드 확인이 필요하다. (`09:33-09:56`)

### 주소 변환 및 표시 개선

- 제3자에게 전달될 수 있는 위치 데이터가 무엇인지 사용자가 확인할 수 있도록, debug 화면의 위도·경도만 표시하던 방식을 더 읽기 쉽게 개선했다. (`07:02-07:38`)
- Android 내부 라이브러리 또는 기능을 활용해 별도의 외부 API key 없이 위도·경도를 주소로 변환하고, 위치 데이터 화면에서 좌표와 함께 주소를 표시하도록 구현했다고 보고했다. (`07:38-08:16`)
- 좌표 기반 주소 변환은 대체로 정확해 보였지만, 같은 유형의 결과가 도로명 주소와 지번 주소 사이에서 일관되지 않게 나오는 문제가 있었다. (`08:17-08:44`)
- 완전한 지도 API나 추가 처리를 사용하기 전 단계로, 우선 해당 좌표에 어떤 주소가 대응하는지 1차적으로 확인할 수 있게 한 상태다. (`08:44-09:00`)

### 제3자 데이터 공유 및 보안

- 위치 데이터가 결국 server를 거쳐 제3자에게 제공될 수 있으므로, 사용자가 어떤 데이터가 전송되는지 이해할 수 있어야 한다는 문제의식이 제시되었다. 주소 표시 개선은 이 맥락에서 설명되었다. (`07:02-07:38`)
- server 측 외부 지도 API 호출이 병목이 되고 추가 개선이 어렵다면, client에서 주소를 추출한 뒤 장소명 조회를 위해 Kakao 계열 API를 호출하는 방안이 “최후의 보루”로 제안되었다. (`10:04-11:22`)
- 이전에는 client가 지도 API key를 알게 되는 것을 우려했지만, 많은 지도 앱이 client 측 key를 사용하는 것으로 보인다는 의견을 근거로 그 우려가 결정적인 문제는 아닐 수 있다는 재평가가 나왔다. 이는 회의 참석자의 의견이지 보안 검증 결과가 아니다. (`10:30-11:05`)
- client 호출이 server 측 부담이나 server에 집중되는 위험을 줄일 수 있다는 기대가 언급되었으나, client에 포함된 key의 노출 가능성 자체가 사라지는 것은 아니다. 플랫폼 제한, domain/package 제한, quota, key 회수·교체, 악용 대응 정책은 회의에서 다뤄지지 않았다. (`11:05-11:35`)
- 이 방안은 가능한 대안으로만 남았고, 당장 중요한 결정을 내릴 필요는 없다는 발언도 뒤이어 나왔다. 최종 아키텍처 결정으로 기록해서는 안 된다. (`11:35-12:11`)

- draft API가 기대하는 실제 동시 사용자 수와 성능 목표는 얼마인가?
- reverse geocoding과 장소명 조회를 Android client와 server 중 어디에서 수행할 것인가?
- client에 배포되는 지도 API key에 어떤 플랫폼·사용량 제한과 악용 방지 정책을 적용할 것인가?

## 주의 사항

- 자동 전사 파일에는 화자명이 없어 역할, 담당자, 발언 주체를 추측하지 않았다.
- 띄어쓰기, 문장 경계, 기술 용어 인식 오류가 포함되어 있다.
- `DLQ`, `SSLN`, “외부지로 API”, “카카오 메이 APR” 등의 표현은 원음이나 구현 코드에서 확인해야 한다.
- “수정했다”와 “설계했다”가 같은 설명 안에서 함께 사용되어 User Memory batch 처리가 구현 완료인지 잠정 설계인지 확정할 수 없다.
- 동시 사용자 5명부터 느려졌다는 내용은 환경과 지표가 명시되지 않은 회의 중 관찰이다.
- client 측 지도 API 호출은 제안일 뿐이며, API key 보안과 최종 아키텍처가 확정되었다고 볼 수 없다.
- 원문에는 일정과 위치에 관한 개인 정보가 포함되어 있으므로 공개 범위를 제한해야 한다.
