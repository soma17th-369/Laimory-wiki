# 369팀 스페이스 회의 요약 - 2026-08-13

## 개요

이번 회의에서는 중간 또는 주간 보고서 작성 진행, server scheduler·API·Redis script 정리, mobile calendar UI와 timeline loading 수정, 20분 미만 이동 data 처리, draft·saved timeline의 API response policy를 점검했다.

보고서는 현재 28page까지 늘어났으며, 먼저 필요한 내용을 모두 넣은 뒤 나중에 한꺼번에 줄이는 방식으로 작업하기로 했다. AI 관련 수행 방안과 개발 진행 현황을 8월 13일까지 1차 마무리하고, 8월 14일에는 marketing 부분을 마무리해 8월 15일까지 전체를 끝내는 목표가 공유되었다. (`01:15-02:50`)

server에서는 multi-process 환경의 scheduler, 요청받은 API, project 전반에 흩어진 Redis script 정리를 진행하고 있다고 보고했다. mobile에서는 calendar API가 완성되기 전 전체 data를 받아 월별로 mapping하는 임시 UI를 구현했고, saved·draft 상태에서 loading 처리가 이상한 문제를 수정했다. movement는 20분 미만이면 저장하지 않도록 변경했다고 보고했으나, 이 기준이 모든 edge case에 적절한지는 별도 검증이 필요하다. (`02:55-05:33`)

draft와 saved timeline을 조회할 때 어느 상태를 보낼지 논의한 결과, 둘 다 보내고 감정 값이 없는 경우 `null`로 전달하기로 했다. 상태 값도 함께 제공해 향후 saved data만 user memory에 반영하는 등 business logic이 달라질 때 활용할 수 있도록 하는 방향이다. (`05:36-07:30`)

## 상세 요약

### 보고서 작성

- 보고서가 이미 28page까지 늘어났지만, 현재 단계에서는 분량을 줄이기보다 들어가야 할 내용을 모두 넣고 마지막에 한 번에 줄이기로 했다. (`01:15-02:09`)
- 수행 방안과 project 진행 현황의 AI 부분을 작성 중이며, 8월 13일까지 AI 내용을 1차 마무리할 계획이라고 말했다. (`02:10-02:31`)
- 8월 14일에는 marketing 관련 부분을 마무리하고 문서를 다듬어 8월 15일까지 전체를 끝내는 목표를 공유했다. (`02:31-02:50`)
- mobile 관련 보고서 내용은 다음 날 아침 일찍 모여 다른 구성원들과 맞추며 작성하기로 했다. (`05:09-05:33`)

### Server scheduler·API·Redis

- server 관련 보고서에는 AI 쪽 내용을 거의 그대로 옮겨 둔 상태여서 다시 읽고 정리하거나 정제할 계획이라고 했다. 자동 전사의 `계산`은 `개선` 또는 `정리` 등을 잘못 인식했을 가능성이 있다. (`02:55-03:09`)
- multi-process 환경에서 scheduler가 동작하도록 하는 작업, 다른 구성원이 요청한 API, project에 흩어진 Redis script 정리를 진행 중이라고 보고했다. (`03:09-03:24`)
- 전사상 관련 `파악` 또는 설계가 끝나 하나씩 AI를 활용해 code를 변경하면 될 것 같다고 했으나, 정확히 무엇이 완료되었는지 문장이 불명확하다. 구현 완료로 해석해서는 안 된다. (`03:24-03:36`)

### Calendar UI와 mobile 수정

- server calendar API가 준비되기 전에 전체 data를 조회해 월별로 mapping하는 임시 구현을 만들었다. 향후 API가 나오면 mobile에서 다루는 response 범위를 줄이는 정도의 변경이 될 것으로 예상했다. (`03:41-04:10`)
- saved와 draft 상태를 다루는 화면에서 loading 처리가 이상하게 동작하는 문제를 수정했다. (`04:11-04:31`)
- movement data는 20분 미만이면 아예 저장하지 않도록 변경했다고 보고했다. 여러 edge case가 발생하지만 우선 짧은 movement를 무시하는 단순 rule을 적용한 상태다. (`04:31-04:57`)
- calendar에서 하루 timeline을 감정 기반 UI로 보는 부분을 구현해 둔 상태라고 보고했다. (`04:57-05:09`)

### Draft·saved API response

- timeline 단건 조회에서 상태 값이 아직 없으며, 이를 추가할 예정이라는 확인이 있었다. (`05:41-06:01`)
- saved record만 보낼지 draft와 saved를 모두 보낼지 논의했다. draft에는 감정이 없을 수 있으므로 감정 값은 `null`로 전달하기로 했다. (`06:03-06:36`)
- 최종적으로 draft와 saved를 모두 보내고 상태 값도 함께 주는 방향으로 합의했다. 현재 당장 필요 없더라도 향후 요청에 대응하기 쉽고, saved data만 user memory에 반영하는 것처럼 business logic이 달라질 수 있다는 이유가 제시되었다. (`06:36-07:30`)
