# 369팀 스페이스 회의 요약 - 2026-08-12

이번 회의는 중간 발표 보고서 작성, AI evaluation system, 사용자 데이터 비식별화, 개인정보 동의 UX, 위치·이동 데이터의 선택적 제외, on-device AI의 필요성, 핵심 persona, 회고 기능을 대체할 목표 관리 기능을 약 2시간 9분 동안 폭넓게 논의한 회의다.

개발 현황으로는 AI evaluation system이 PR 확인 단계에 가까워졌고, server에서는 사용자 ID를 secret key로 단방향 hash한 값과 별도 subject ID를 mapping하는 구조를 만들고 기존 data migration을 진행 중이라고 보고했다. mobile에서는 타임라인 생성 직전의 동의 flow, edit mode와 saved 처리, 감정별 calendar view의 Figma 및 issue 작업을 진행했다. (`01:10-05:45`)

중간 발표 문서에서는 기존 기획심의 내용을 옮기되, 회고 기능을 대신할 목표 추적 기능, persona, on-device AI와 개인정보 보호 설명을 다시 정해야 한다고 보았다. persona는 나이 자체보다 “이제 막 직장 생활을 시작했고 기록을 적극적으로 하는 사람”으로 좁히는 방향에 합의했다. 목표 기능은 todo보다 월 단위 목표를 먼저 받고, 타임라인에서 목표와 관련된 행동을 찾아 사용자가 확인하게 하며, progress와 reminder를 제공하는 방향으로 정리되었다. 이 기능의 주된 설명 근거는 추상적인 “성장”보다 재방문과 retention을 높이는 데 두기로 했다. (`06:02-14:41`, `42:30-50:56`, `1:55:02-2:03:32`)

개인정보·위치 처리에서는 사용자가 빼고 싶은 장소를 선택하면 그 장소 자체와 연관된 이동 기록을 mobile에서 제거해 server로 아예 보내지 않는 방향을 정했다. 반복 동의 UX는 매번 받아야 하는지, onboarding에서 한 번만 받으면 되는지 법적·정책적 확인이 필요해 미결로 남았다. 현재 flow에는 on-device AI가 필수적이지 않다는 결론을 내렸지만, 발표에서 개인정보 질문에 답할 수 있도록 정규식 masking, 사용자 확인, hash·mapping 분리 구조를 명확히 설명해야 한다고 정리했다. (`51:06-1:13:35`, `1:25:05-1:29:14`)

## 상세 요약

### 개발 현황

- 중간 발표 문서에 문제 인식, 기획 의도, 시장 분석, persona, 유사 서비스, 개발 환경 등 기존 기획심의 내용을 옮기고 수정할 부분을 표시해 두었다. (`01:10-02:05`)
- 생성형 AI evaluation system을 계속 작업 중이며, 마무리 후 PR을 확인할 단계에 가까워 중간 발표 보고서에 반영할 수 있을 것으로 예상했다. (`02:08-02:38`)
- server 쪽에서는 user ID를 secret value와 함께 단방향 hash하고, hashed user ID로 mapping table에 접근하는 구조를 만들어 기존 data migration을 진행 중이라고 보고했다. (`03:09-04:17`)
- mobile 쪽에서는 타임라인 생성 마지막 단계의 동의, edit mode와 saved 처리, 감정별 calendar view를 위한 Figma와 issue 작업을 진행했다. calendar 조회용 server API 요청이 뒤따를 수 있다고 말했다. (`04:21-05:45`)

### 중간 발표 보고서 구조

- 주요 기능을 기준으로 수행 방법을 나누기보다 AI, Android, backend, 협업·개발 process, system 통합·배포처럼 영역별로 나누는 것이 반복을 줄인다고 판단했다. (`15:50-17:18`)
- 협업·개발 process에는 coding agent, 공유 skill, LLM wiki 등을, 통합·배포에는 AWS와 app test·Play Store 배포 계획을 넣는 방안이 설명되었다. (`16:44-17:18`)
- 기존 문서의 Sentry, Firebase Analytics, Google Analytics 등 monitoring 항목과 design·privacy·예상 문제점을 현재 상태에 맞게 갱신할 필요가 있다. (`17:18-18:41`)
- 개발 진행 현황은 현재 MVP와 각 분야에서 실제로 해결한 중요한 문제, 계획대로 구현한 부분을 보여주는 차별화 section으로 만들기로 했다. (`18:41-23:15`)
- free·premium·max tier는 기능 차이보다 사용 횟수나 목표 개수로 제한하는 편이 현실적이라는 의견이 나왔다. AI 호출 비용은 하루 약 70원 수준을 목표로 검토하기로 했지만, 확정 가능한 원가 수치는 아니다. (`23:50-27:58`)

### 핵심 기능 초안과 회고 대체 논의

- 기존 회고 기능 대신 사용자가 목표를 입력하고, 작성된 timeline을 바탕으로 목표에 가까워졌는지 질문·확인하며 progress를 보여주는 기능 초안이 제시되었다. (`06:11-09:51`)
- 목표를 숫자로 자동 판정하기 어렵기 때문에 LLM이 관련 사건을 찾아 질문하고 사용자가 `yes/no`로 확인하는 흐름이 제안되었다. 목표의 범위를 timeline data로 확인 가능한 항목으로 제한할 가능성도 언급했다. (`07:46-09:41`)
- 목표를 100% 정량적으로 추적하기 어렵고, photo·location 등 현재 수집하는 data가 목표마다 충분하지 않을 수 있다는 한계가 반복해서 지적되었다. (`33:03-42:24`)
- 기능이 단순 todo list와 무엇이 다른지, 사용자가 왜 이를 써야 하는지, 심사 질문에 어떻게 답할지 명확하지 않아 정의가 중요하다는 데 의견이 모였다. (`37:44-42:24`, `1:29:19-1:36:49`)
- 최종적으로 todo는 사용자 입력 부담이 크므로 월 단위 목표에서 시작하고, timeline에서 관련 행동을 찾아 질문·확인한 뒤 progress를 표시하는 쪽으로 정리했다. (`1:55:02-2:00:25`)
- reminder 빈도는 사용자가 조절할 수 있게 하고, 매일 강제 질문해 피로를 만드는 것을 피해야 한다는 제안이 있었다. (`2:00:48-2:02:40`)
- 이 기능의 설명 목적을 추상적인 “성장”보다 timeline 작성 후 재방문을 유도하는 retention으로 두면 설득력이 있다는 결론이 나왔다. (`2:01:41-2:03:32`)

### Persona 정리

- 기존의 “30대 직장인” persona가 팀의 이해와 실제 사용 상황을 충분히 반영하는지 검토했다. 활동과 calendar가 풍부하고 사진·기록을 자주 남기는 사람이 서비스에 더 적합하다는 판단이 나왔다. (`42:30-48:10`)
- 대학생과 직장인의 생활 pattern, 구매력, marketing 차이를 논의한 끝에 연령을 직접 명시하기보다 `사회 초년생`을 중심으로 하는 방안이 제시되었다. (`48:10-49:33`)
- 최종 표현은 대학생을 포함하는 넓은 의미가 아니라 “이제 막 사회에 발을 디딘 직장인”으로 두고, 적극적으로 기록하는 성향을 함께 넣기로 했다. (`49:38-50:56`)

### 반복 동의 UX

- 타임라인 생성에 사용될 data와 제3자 제공·민감정보 처리 동의를 한 화면에서 보여주는 Figma flow가 공유되었다. (`51:06-53:12`)
- 동의를 생성 때마다 받아야 한다는 해석과 onboarding에서 한 번만 받아도 된다는 해석이 엇갈렸다. 매일 여러 필수 checkbox를 보여주는 UI는 거부감을 줄 수 있다는 우려가 있었다. (`53:14-1:00:43`)
- 매번 data를 보여주되 동의는 최초 한 번만 받거나, 모든 필수 항목에 동의하는 하나의 행동 버튼을 제공하는 대안이 논의되었다. 실제 법적·정책적 요구를 더 조사하기 전까지 확정하지 않았다. (`56:15-1:06:32`)
- 사용자가 전송될 data를 직접 보고 원하지 않는 항목을 제외할 수 있게 하는 것이 핵심 UX로 유지되었다. (`56:20-58:18`, `1:08:12-1:08:54`)

### 위치·이동 data 선택적 제외

- 사용자가 이해하기 쉽게 이동 record와 체류 record를 모두 나열하기보다 장소 중심으로 보여주는 방안이 제안되었다. 중복 장소는 합치고 map pin을 함께 제공하는 아이디어도 나왔다. (`1:09:03-1:15:05`)
- 특정 장소를 제외하면 그 장소와 연결된 출발·도착 movement record까지 모두 제거해야, 가려진 장소가 timeline에 간접적으로 드러나지 않는다는 판단이 나왔다. (`1:10:17-1:13:15`)
- 제외한 장소와 관련된 정보는 mobile에서 먼저 제거해 server에 아예 보내지 않는 방향을 명시적으로 정했다. (`1:13:07-1:13:35`)
- 현재 address만으로 사용자가 장소를 알아보기 어려울 수 있어 map pin 또는 지도 표시를 검토하기로 했다. (`1:14:03-1:15:40`, `1:23:20-1:25:01`)
- 체류 20분 기준과 위치 update 방출 방식 때문에 의도치 않은 이동 noise가 생긴 것으로 보고, 이동 수집 logic을 개선한 뒤 다시 확인하기로 했다. (`1:16:18-1:17:31`)
- 장소를 제거하면 사진과 다른 data의 맥락이 어긋나 timeline 품질이 떨어질 수 있으므로 실제 test가 필요하다. (`1:22:31-1:23:20`)

### On-device AI와 비식별화

- 현재의 data 검토·제외 flow에는 on-device AI가 필수적이지 않다는 결론을 내렸다. (`1:25:05-1:25:29`)
- 다만 기획심의 때 on-device AI로 개인정보를 미리 처리한다고 답했던 만큼, 이를 빼면 개인정보 질문에 대응할 다른 설명이 필요하다고 지적했다. 발표 문서에 남길지 실제 구현에서 뺄지는 혼동하지 않아야 한다. (`1:25:29-1:26:31`)
- 번호류의 정규식 masking, 민감정보 동의, 사용자와 AI data의 연결 관계 분리를 함께 제시하면 방어 가능하다는 의견이 있었다. 이는 법률 또는 security audit로 검증된 결론이 아니다. (`1:26:31-1:27:08`)
- user ID를 AWS Secrets Manager의 secret으로 단방향 hash하고, 그 hash를 mapping table의 key로 사용해 별도 subject ID를 얻는 구조가 설명되었다. DB와 secret이 모두 유출되면 식별 가능할 수 있다는 한계도 명시했다. (`1:27:09-1:29:14`)

### Retention, onboarding, monetization

- 사진·위치·일정 권한을 허용할 이유를 사용자가 체감하도록, data 종류별로 생성 결과가 어떻게 달라지는지 onboarding에서 예시를 보여주자는 제안이 나왔다. (`1:39:11-1:40:50`)
- 제한된 자동 수집 data도 LLM이 맥락을 추론하고 user memory를 누적하면 더 사용자 친화적인 결과를 만들 수 있다는 설명을 보고서에 넣기로 했다. (`1:43:02-1:44:24`)
- 과거 timeline reminder와 작성 유도 알림을 retention 수단으로 검토했으나, 매번 LLM으로 알림을 만들면 비용이 커질 수 있다는 우려가 있었다. (`1:44:26-1:45:58`)
- 무료 횟수를 다 쓴 사용자가 다음 timeline을 만들려 할 때 마지막 단계에서 upgrade를 제안해 지불 의사를 측정하는 방안이 제안되었고 긍정적인 반응이 있었다. 실제 구현 확정 여부는 전사만으로 분명하지 않다. (`1:48:18-1:50:23`)

## 주의 사항

- 화자 label이 있지만 자동 전사이므로 이름·전문 용어·문장 경계 오류가 있다. 명시적 발언과 분담만 기록하고 숨은 의도나 역할을 추측하지 않았다.
- `회고`가 `해고`, `persona`가 `소나`, `on-device AI`가 일부 구간에서 불완전하게 인식되는 등 오류가 있다.
- 개인정보 동의와 비식별화 설명은 내부 설계 논의이며 법률 자문이나 security audit 결과가 아니다.
- one-way hash와 mapping table 구조의 안전성은 algorithm, secret rotation, access control, threat model을 확인해야 평가할 수 있다.
- persona, 목표 기능, monetization 일부는 회의 안에서 방향이 정해졌지만 상세 명세와 구현 상태는 미확정이다.
- 원문에는 참석자의 일정과 민감한 위치 예시가 포함되어 있으므로 공개 범위를 제한해야 한다.
