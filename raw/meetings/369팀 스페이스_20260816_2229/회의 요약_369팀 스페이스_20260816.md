# 369팀 스페이스 회의 요약 - 2026-08-16

## 개요

이번 회의에서는 중간 보고서·발표자료 제출, 약관 API 관리 방식, 실제 앱 시연 영상, Android notification 수집·filtering의 우선순위, 서비스가 기록을 넘어 제공할 장기 가치가 논의되었다. API 작업으로 timeline 저장 상태와 calendar 월별 조회가 merge되었다는 보고가 있었고, 약관은 client가 저장 위치를 알지 않아도 되도록 server가 DB 또는 external document link를 추상화해 제공하는 방향이 제시되었다. (`04:40-06:07`)

가장 긴 논의는 notification filtering이었다. 결제·예약·배송 같은 keyword나 category, 주요 app을 기준으로 유의미한 notification을 우선 수집하고, 최대 약 100개 후보에서 category를 우선하는 방안이 설명되었다. 당시 이 로직은 아직 적용되지 않았다. 시연을 위해 기존 수집 data를 수동 삭제하는 임시안도 제안되었지만, 결론은 beta/release user flow를 완성하려면 사용자가 app별 filter를 직접 조작하지 않아도 제품이 최소한의 notification을 자동 선택해야 하며, 이 작업을 Kotlin migration이나 logging 정리보다 먼저 진행한다는 것이었다. (`12:40-24:00`)

발표자료는 AI로 만든 Google Slides를 대폭 수정하고 보고서 UI image를 추가한 뒤 8월 17일 12시 제출하는 일정으로 정리되었다. Mentor feedback으로 제기된 “일기를 쓰는 것보다 더 높은 지속 가치”에는 공유, 목표, AI memory·assistant 같은 아이디어가 나왔지만 합의된 답은 없었다. 중간 보고서에 성급히 넣기보다 이후에도 해결할 project-level question으로 남기기로 했다. (`24:26-34:49`)

## 상세 요약

### 보고서와 발표자료 준비

- Beta test에서 무엇을 측정할지 아직 정리 중이었고, mentor가 남긴 feedback을 어떻게 반영할지도 검토 중이라고 공유했다. (`02:07-02:41`)
- Google Slides 발표자료는 AI로 초안을 만들었지만 수정할 부분이 많았다. HTML로 만드는 대안도 언급되었으나, 이미 PPT 형태로 만들었고 team 수정에도 문제가 없다는 의견이 모였다. (`02:41-03:38`)
- 중간 보고서는 환경에 따라 27 page로 보였고, 최종 검수 뒤 발표자료와 함께 가능한 한 회의 당일 또는 다음 날 제출하기로 했다. (`03:45-04:34`)
- Timeline 예시 image를 진행상황 section에 추가하고, 설치 가능한 APK와 app icon, 내부 화면을 한 page에서 보여주는 구성이 제안되었다. Page가 늘어나는 만큼 다른 부분을 줄이는 작업이 남았다. (`24:39-27:48`)
- 최종적으로 제출 시점을 8월 17일 12시로 정하고, 공식 deadline인 15시 전에 mentor feedback에 대한 답글 또는 문서 수정을 추가 검토하기로 했다. (`27:48-28:03`, `34:07-34:49`)

### API와 약관 관리

- 서비스 관련 API 가운데 timeline 저장 상태와 calendar 월별 조회를 완료해 merge했다고 보고했다. 정확한 branch와 deployment 상태는 전사에서 확인되지 않는다. (`04:40-04:57`)
- 약관 내용은 server가 관리하고 client는 server에서 받아 표시하는 구조가 제안되었다. Server DB에 문서 본문이나 document link를 두고 interface를 추상화하면 약관 변경을 client update 없이 반영할 수 있다는 설명이다. (`05:01-05:58`)
- 해당 약관 API는 code가 나온 상태로 추가 검토 중이며, 완료 여부는 아직 확정되지 않았다. (`05:58-06:07`)

### Android release 준비와 시연 flow

- Kotlin version 등을 최신화할 필요가 있는지 검토했지만, 기존 기능에 문제가 생길 경우 upgrade를 적용하지 않는 보수적 접근이 언급되었다. (`06:14-07:05`)
- 실제 앱 영상은 Android Studio recording으로 촬영하고 AI 응답 대기 약 40초 등 loading 구간은 cut editing하기로 했다. UI·UX를 우선 정리해 수요일 밤까지 2~3개 recording 후보를 만들 계획이 공유되었다. (`08:14-09:46`)
- 시연 범위는 onboarding을 제외하고 login 이후 data 확인·선택, timeline 생성 loading, 결과 편집과 save까지 실제 app에서 동작하는 flow로 잡았다. 실제 수집 data를 우선 사용하되 결과가 부족하면 mock data를 검토할 수 있다는 제안이 있었다. (`09:46-12:38`)
- 실제 개발 진행상황을 보여주는 것이 목적이므로 prototype만 사용하기보다 실제 기기 결과를 촬영하는 쪽을 선호했다. (`11:21-12:38`)

### Notification 수집과 filtering

- 당시 notification 수집 조건은 아직 적용되지 않았다. 결제·예약·배송 같은 keyword 또는 category와 많이 쓰는 app을 기준으로 수집하고, 클릭된 notification도 참고하며, 후보가 약 100개라면 category가 먼저 선택되도록 하는 1차 방안이 설명되었다. (`12:40-14:31`)
- 기존에 filter 없이 local DB에 쌓인 notification을 새 전략에 맞춰 삭제·재구성할지, 현재 UI에서 수동 삭제 기능만 제공할지 논의되었다. 수동 삭제는 시연을 빠르게 준비하기 위한 임시 대안이었다. (`16:02-17:43`)
- 논의 중 시연 준비와 beta/release 완성의 목적이 혼동되었으나, 최종적으로 filter는 단순한 demo 편의가 아니라 timeline 생성에 필요한 최소 data를 제품이 자동 선택하기 위한 핵심 user flow로 정리되었다. (`17:47-22:39`)
- 사용자가 app별 notification을 직접 제외하는 것은 과도한 조작으로 보았고, 제품이 기준을 정해 자연스럽게 filtered data를 보여주는 방향이 제시되었다. (`21:25-22:16`)
- Kotlin migration, module 정리, logging보다 사용자에게 어색하지 않은 flow와 notification filter를 먼저 구현하고, 기술 정리는 beta 기간으로 미루기로 했다. (`22:41-24:00`)

### 제품 가치와 mentor feedback

- Mentor feedback은 “일기 자체를 쓰는 것보다 더 높은 가치를 어떻게 제공해 지속 사용을 만들 것인가”로 해석되었다. (`28:21-29:23`)
- 공유 기능, 목표 관리, 기록이 쌓일수록 사용자를 닮아가는 AI memory·character, message 답변이나 calendar 입력을 돕는 assistant 같은 아이디어가 나왔다. 모두 brainstorming이며 구현 약속이나 roadmap 결정은 아니다. (`29:23-32:56`)
- 팀의 기존 problem definition은 사람들이 이미 기록 욕구를 갖고 있지만 기록 비용 때문에 지속하지 못한다는 가설에 기반해 있어, “기록하고 싶게 만드는 동기” 문제와는 범위가 다르다는 지적이 있었다. (`29:43-30:47`)
- 중간 보고서에 불충분한 답을 억지로 넣기보다 mentor에게 난도가 높은 질문이었다고 설명하고, report 이후에도 계속 해결할 project-level feedback으로 다루기로 했다. (`33:10-34:03`)

## 주의 사항

- `notification 100개`는 설명을 위한 한도 예시로 들리며 실제 platform 제한 또는 확정 product requirement인지 확인이 필요하다.
- Notification filtering 설계는 category, keyword, click 여부가 섞여 있어 code 수준의 확정 rule로 해석하면 안 된다.
- API merge 보고는 발언 기준이며 deployment와 integration test 완료까지 뜻하지 않는다.
- AI memory·character·assistant 아이디어는 brainstorming이며 확정 기능이 아니다.
- 자동 전사의 이름·도구명 오류가 있어 정확한 repository, branch, class, API endpoint는 code와 issue에서 확인해야 한다.
- 원문에는 개인 일정이 포함되어 있으므로 공개 범위를 제한해야 한다.
