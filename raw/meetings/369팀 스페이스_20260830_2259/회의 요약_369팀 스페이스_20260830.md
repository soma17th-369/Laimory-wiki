# 369팀 스페이스 회의 요약 - 2026-08-30

## 개요

이번 회의에서는 AI model 선택과 비용 최적화, local LLM judge, 프로모션·onboarding asset, 약관 작성·배포 방식, load test 전용 server, Android permission·notification 설정, timeline empty state를 논의했다.

전사상 `노바트 라이트`로 들리는 model은 message에서 실제 행동을 추론하는 성능이 부족해 주력 후보에서 제외하기로 했다. 한 model로 모든 단계를 처리하지 않고 간단한 event 처리에는 저렴한 `5.6 Luna` 계열을, 핵심 timeline 구성에는 기존 `5.3 mini`로 들리는 상위 model을 쓰는 단계별 routing 방향을 잡았다. 정확한 model명과 배포 설정은 코드 확인이 필요하다. (`00:39-04:15`)

품질 평가 비용을 줄이기 위해 local LLM judge가 API를 직접 호출하는 대신 이미 결제한 Codex CLI 자원을 사용하는 방향을 시험하기로 했다. 이는 개발·평가 도구의 실행 방식이며 production inference 전환과는 별개다. (`02:46-03:50`)

약관은 최대한 보수적으로 데이터 처리 국가와 항목을 기재해 database에 올렸고, mobile에서는 initializer API가 최신 약관 URL을 받아 WebView로 보여주는 방식으로 정리했다. 현재 Spring application이 HTML을 서빙하지만, landing page를 만들면서 약관을 별도 static hosting 쪽으로 옮겨 application 부하를 줄이는 방안도 합의되었다. (`11:37-12:17`, `14:31-22:18`)

## 상세 요약

### model 선정과 단계별 routing

- 전사상 `노바트 라이트`로 들리는 model은 message 내용을 바탕으로 실제 활동을 추론하는 수준이 부족했고, 많은 prompt instruction을 추가해도 개선 가능성이 낮다고 판단해 배제하기로 했다. (`00:39-01:21`)
- `5.6 Luna`로 들리는 model도 기존 mini보다 추론력이 낮을 수 있으나 비용이 절반 이하라는 설명이 있었다. 실제 가격과 성능 수치는 검증 자료 없이 회의 중 비교한 내용이다. (`01:22-01:48`)
- 비용과 품질을 함께 맞추기 위해 importance가 낮은 event 처리에는 저렴한 model을, timeline 구성처럼 중요한 단계에는 더 강한 model을 쓰는 routing 구조를 선택했다. (`01:48-02:45`)
- 구체적으로 간단한 event 처리는 `5.6 Luna`, 핵심 timeline은 전사상 `5.3 mini`로 들리는 model을 쓰는 계획이 제시되었다. 이 조합의 실제 release 적용 완료 여부는 확인되지 않았다. (`03:50-04:15`)

### LLM judge와 timeline 품질 방향

- prompt 개선을 위해 생성 결과를 분석 중이지만 API 기반 judge는 반복 평가 비용을 발생시킨다는 문제가 있었다. (`02:46-03:19`)
- 이미 구독 중인 Codex CLI를 local evaluation program과 연결해 LLM judge로 활용하는 방식으로 바꾸려 했고, 기술적으로 가능해 보인다고 보고했다. (`03:19-03:50`)
- timeline은 `어디 갔다`, `무엇을 했다`를 나열하는 수준을 넘어 `왜 갔는지`, `무엇을 했는지`를 더 높은 수준으로 추론하도록 prompt와 결과물을 개선하는 방향이었다. (`04:15-04:49`)
- notification 처리 rule도 앞선 회의에서 확인한 과잉 event 문제를 바탕으로 계속 개선 중이었다. (`04:15-04:27`)

### 프로모션 팸플릿과 onboarding asset

- Figma project에서 promotion page가 사라진 것으로 잠시 오해했으나 다른 위치에 남아 있는 것을 확인했다. 환불 처리로 편집 권한이 제한된 상태일 가능성이 언급되었다. (`04:51-05:38`)
- promotion의 1·2 page에는 사진과 배경이 자연스럽게 섞이는 image를 만들고, 이후에는 photo·calendar·location·notification이 timeline으로 정리되는 실제 screen 또는 예시를 보여주려 했다. (`05:42-08:22`)
- promotion과 onboarding의 설명 흐름은 거의 같게 맞추고, 개인정보가 들어간 실제 사례보다 AI로 만든 완성도 높은 example을 사용하는 방향을 선호했다. (`08:25-10:36`)
- 일부 구분용 page는 제거하거나 기능 설명과 자연스럽게 이어지게 조정할 수 있다는 의견이 있었다. 최종 page 구성은 확정되지 않았다. (`10:33-11:20`)

### 약관 작성과 beta test infrastructure

- 개인정보 처리와 외부 AI·agent 관련 국가·처리 범위를 가능한 한 보수적으로 모두 명시하는 방식으로 약관을 작성해 database에 올렸다고 보고되었다. 놓친 항목이 있을 때의 risk가 약관이 길어지는 부담보다 크다고 판단했다. (`11:37-12:17`)
- load test 때문에 development environment가 중단되는 일을 피하려고 dev 환경을 복제한 on-demand test server를 계획했다. database와 Redis는 기존 자원을 공유하고 server만 켰다 끄는 구상이며, 월 비용은 매우 작을 것으로 추정했다. (`12:19-12:53`)
- dev AI는 dev EC2로 연결했고 OpenAI `5.4 mini`로 들리는 기존 설정으로 rollback한 상태라고 설명했다. production 연결과 action 실행은 별도 확인이 필요하다. (`12:56-13:36`)

### Android permission, notification, onboarding

- system permission을 앱 내부에서 직접 해제하면 재실행이 필요한 문제를 고려해, permission 관리 화면으로 안내하고 해당 진입 횟수를 logging하는 방향이 언급되었다. 전사 일부가 누락·왜곡되어 정확한 UI 흐름은 code나 Figma 확인이 필요하다. (`13:39-14:49`)
- onboarding 화면 제작과 함께 permission과 notification 수신 동의의 남은 부분을 처리할 계획이었다. (`14:31-14:54`)
- 읽기·편집 mode는 약관과 onboarding을 붙인 뒤 진행할 예정이며, Figma에는 일부 reference만 있어 code 작업 후 다시 정리하기로 했다. (`22:31-24:02`)

### 약관 version과 WebView 제공

- 동의가 필요한 문서는 여러 개로 나뉘고, 이용약관과 개인정보 처리방침은 login 시 확인되는 흐름으로 설명되었다. user가 어떤 version에 동의했는지는 별도로 저장한다. (`14:59-17:17`)
- mobile에는 항상 최신 약관을 보여주기 위해 initializer API가 URL을 반환하고 WebView가 그 주소를 여는 방식을 택했다. 중요한 변경이 아니면 과거 version 동의가 유지될 수 있다는 발언이 있었지만, 이는 법률 검토 결과가 아니다. (`15:51-17:50`, `20:17-21:46`)
- 현재 약관 HTML은 Spring application resource에서 서빙하고 있다. landing page를 만들 때 약관 route도 static hosting에 두어 WAS 부하를 줄이고, backend가 반환하는 URL만 바꾸는 구조로 옮기기로 했다. mobile 변경은 필요 없다고 확인했다. (`17:48-22:18`)

### loading 화면과 입력 없는 날의 empty state

- 사진이 없는 날 loading 화면이 매우 비어 보이는 문제가 있어 photo뿐 아니라 calendar·notification icon이 움직이는 motion graphic 같은 기본 loading visual을 고려했다. 이 개선은 후속 작업으로 남았다. (`24:02-25:38`)
- 수집된 사진·calendar·location·notification이 모두 없는 경우 AI가 아무 결과 없이 종료되고 화면도 `생성된 게 없음`으로 끝나는 문제가 확인되었다. (`25:38-26:08`)
- user memory가 있으면 이를 활용하고, memory도 없는 신규 user라면 기본 질문이나 입력 field, 왜 데이터가 없는지 설명하는 empty-state timeline을 보여줘 첫 경험이 막히지 않게 해야 한다는 방향이 제시되었다. (`26:08-29:12`)
- input이 없을 때 AI 호출 비용을 피하고 server에서 기본 결과를 반환하는 대안도 나왔지만, user memory 활용과 어떤 내용을 채울지까지 포함한 최종 design은 미결이다. (`27:24-29:12`)

## 열린 질문

- 단계별 model routing의 각 단계·fallback·timeout·quality threshold는 어떻게 정의하는가?
- Codex CLI를 automated judge로 쓸 때 reproducibility, rate limit, local authentication을 어떻게 관리하는가?
- 약관에 열거한 국가·처리자·data category가 실제 infrastructure와 일치하는가?
- load test server가 production 또는 development database·Redis를 공유할 때 data isolation 위험은 없는가?
- 약관의 중요한 변경을 어떻게 판단하고 언제 재동의를 받을 것인가?
- input과 user memory가 모두 없는 첫 user에게 어떤 default timeline과 질문을 제공할 것인가?

## 주의 사항

- model명은 `Nova Lite`, `GPT 5.6 Luna`, `5.3 mini`, `5.4 mini`로 추정되지만 자동 전사 표기가 일관되지 않아 code·deployment configuration 확인이 필요하다.
- model 가격과 성능 비교는 회의 중 판단이며 공식 benchmark나 billing data가 아니다.
- 약관 설계에 관한 발언은 법률 자문이 아니며, 실제 고지·재동의 의무는 별도 검토해야 한다.
- test server 비용 추정은 database·Redis 공유를 전제로 한 대략값이며 실제 cloud bill과 isolation cost가 포함되지 않을 수 있다.
- Figma 화면과 일부 permission 논의는 시각 자료가 전사에 없거나 문장이 누락되어 정확한 UI를 재현할 수 없다.
