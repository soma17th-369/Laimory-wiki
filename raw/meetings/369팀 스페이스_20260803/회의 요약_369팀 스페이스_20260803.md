# 369팀 스페이스 회의 요약 - 2026-08-03

## 개요

회의에서는 다음 날 개인정보 관련 mentoring 준비, timeline 생성 prompt의 version 분리와 품질 개선, 예산에 맞춘 AWS 구조, Android 기능 업데이트를 공유했다. 이어서 사용자가 timeline을 생성할 때 입력해야 하는 항목을 줄이기 위해 수면 시간과 timeline window를 하나의 흐름으로 통합하고, 당일과 지난날의 경계를 오전 6시로 두는 UX를 구체적으로 논의했다. (`01:34-18:34`, `18:41-37:06`)

팀은 당일 timeline은 기상 시각부터 생성 시점까지, 오전 6시 이후 과거 날짜로 간주되는 timeline은 시작과 종료 시각을 모두 사용자가 고르는 구조에 대체로 합의했다. 최소 window를 6시간으로 제한하는 안은 직관적으로 제안됐지만 근거와 세부 boundary는 더 조정할 수 있는 상태였다. 사진은 현재처럼 선택한 timeline window 안에서만 처음 생성에 사용하고, 나중에 event 편집에서 window 밖 사진을 추가할 수 있게 유지하기로 했다. (`23:01-47:37`)

인프라에서는 AgentCore 사용 방향, 개발용 AI server 유지, model별 Bedrock 또는 API key 호출 방식이 논의됐다. production AgentCore는 유력한 기준으로 받아들여졌지만 최종 model과 billing 방식은 남아 있었다. MQ는 비용과 serverless 구조를 고려해 지금 바로 넣지 않고 실제 필요가 생겼을 때 도입하는 쪽으로 정리됐다. (`05:36-15:30`)

## 상세 요약

### 개인정보 mentoring 준비

- 다음 날 20시 mentoring에서 현재 수집하는 개인정보, 처리 흐름, 권한 동의 방식을 설명하기로 했다. Android 권한 동의 부분은 전사상 해당 작업을 맡은 발언자가 정리해 전달하겠다고 했다. (`01:34-02:36`)

### Prompt version과 품질 개선

- 현재 version과 개선 version을 environment parameter로 바꿔 끼울 수 있도록 V1·V2 구조를 나누고, V2 변경 사항을 PR로 올리는 중이라고 보고했다. (`02:45-03:47`)
- wiki의 모범 사례, 실제 결과의 문제점, high-level specification과 기존 prompt의 불필요한 부분을 함께 분석해 개선안을 설계했다. (`04:04-04:47`)
- 1차 품질 개선은 마무리 단계였지만 token 양이 증가했으며, 이후 V3에서는 token 절감을 목표로 하겠다고 설명했다. (`04:47-05:29`)

### AWS 구성과 AI runtime

- AWS 구조는 비용을 고려해 database 이중화를 제외하고, SSM·ECR·AgentCore 접근을 각 VPC endpoint로 분리하지 않고 NAT gateway를 경유하는 설계로 설명됐다. 월 3,000회, 호출당 약 70원이라는 AI token 가정이 포함됐으나 rough estimate이다. (`05:36-07:00`)
- 개발 환경의 AI server를 작은 EC2 instance로 계속 유지할지 AgentCore로 옮길지 비교가 필요하다고 했다. 이미 설정된 EC2가 있고 소수 test traffic에서는 EC2가 더 저렴할 가능성이 있어 dev server는 남기는 쪽으로 대화가 기울었다. (`07:19-09:03`, `12:41-12:51`)
- 전사상 GPT 계열과 Gemini 계열은 API key로 직접 호출하고, Bedrock에서 제공되는 model은 IAM role 기반으로 호출한다는 현재 구조가 설명됐다. 특정 model 이름은 전사 오류 가능성이 크다. (`09:14-11:59`)
- production에서 AgentCore를 사용할 방향은 비교적 명확했지만, 그 위에서 어떤 model을 어떤 billing 계정으로 호출할지는 확정되지 않았다. (`11:15-12:39`)
- MQ는 batch 단일 실행이나 다중 API server coordination에 쓸 여지는 있지만, AgentCore가 serverless이고 현재 필요가 명확하지 않아 즉시 추가하지 않기로 했다. 실제 문제를 확인한 뒤 도입하는 방향이다. (`13:01-15:30`)

### Android 구현 현황

- record date 기반 API 변경을 반영한 test app을 Firebase App Distribution 계열 도구로 배포했다고 보고했다. (`15:45-16:08`)
- WorkManager로 3일 지난 local data를 삭제하고, patch 응답이 null일 때 재조회해 event log를 남기며, event card에서 모든 사진을 볼 수 있게 하고 photo 중심 card를 1:1 비율로 바꿨다고 보고했다. (`16:08-17:38`)
- calendar 조회와 개인정보·위치 처리 mentoring 준비, timeline 생성 UX 변경을 다음 작업으로 제시했다. (`17:38-18:34`)

### Timeline window와 수면 입력 통합

- 수면 시간 입력과 timeline window를 모두 받는 것은 번거롭고, timeline 생성에서 중요한 값은 기상 시각이라는 문제의식이 공유됐다. (`18:41-20:30`)
- 당일 생성은 사용자가 기상 시각을 start로 고르고 end는 생성하는 현재 시각으로 두는 구조가 합의됐다. 다음 날 오전 6시 전까지는 전날 timeline을 당일 방식으로 만들 수 있고, 오전 6시가 지나면 지난날 방식으로 전환하는 기준이 정리됐다. (`23:01-34:07`)
- 지난날 timeline은 해당 날짜 00시부터 다음 날 06시까지의 범위에서 start와 end를 모두 고르는 안이 논의됐다. start와 end 사이를 최소 6시간으로 제한하는 값은 근거 없는 초기 제안이라고 명시돼 최종 정책으로 단정할 수 없다. (`34:07-37:06`)
- 입력된 기상 시각을 별도 sleep data로 확장하지 않고 timeline window start로만 사용하는 방향이 나왔다. 기존 sleep item은 천천히 제거할 가능성이 언급됐다. (`20:46-23:18`, `43:58-44:25`)
- Health Connect 또는 Samsung Health에서 수면 data를 읽어 초기값을 채우는 방식은 설정·설명 비용이 크므로, 우선 사용자가 직접 입력하고 최근 입력값 정도를 default로 활용하는 안이 제시됐다. (`44:29-47:37`)

### 사진 선택 정책

- timeline window 밖에서 촬영하거나 내려받은 사진을 생성 단계에서 허용하면 전체 gallery를 열어야 하고, 촬영 시각 metadata가 보존되지 않을 수 있어 품질 위험이 있다는 우려가 있었다. (`38:17-40:55`)
- 최초 생성에서는 현재처럼 timeline window 안의 사진만 보여주고, 이후 event 편집에서는 AI를 거치지 않고 사용자가 원하는 사진을 추가할 수 있도록 유지하기로 했다. 다운로드 사진도 download 시각이 window 안이면 현재 구현에서 선택 가능하다고 확인했다. (`40:57-43:53`)

### 시간 UI와 API 후속 작업

- 수면·기상 시각 입력은 익숙한 timer/dialog 형태가 좋다는 의견이 나왔다. 24시간제와 오전·오후 표시는 당장 추가하지 않고 향후 option으로 고려하기로 했다. (`47:43-51:02`)
- record date API path 전환 직후 특정 휴대폰에서 기록이 보이지 않는 현상을 확인했고, client path를 회의 직후 수정해 공유하기로 했다. (`51:21-52:43`)
- event 안의 개별 photo item을 삭제할 API가 필요하다는 요청이 나왔고, item 또는 photo delete 표현과 endpoint를 검토해 추가하기로 했다. (`52:46-54:27`)
