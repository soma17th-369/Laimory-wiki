# 369팀 스페이스 회의 요약 - 2026-08-26

## 개요

이번 회의의 핵심은 AgentCore와 application server 사이의 양방향 호출 장애를 실제 기기 요청으로 진단하고, AI callback 경로를 private server IP 대신 ALB로 보내는 방향을 정한 것이다. 이와 함께 onboarding initializer API, monitoring domain 구성, 약관·privacy policy 준비, Android onboarding과 읽기 화면, beta release 시점, 사업자 등록 상태를 점검했다.

AgentCore로 AI dispatch하는 요청은 성공했지만 AgentCore가 EC2/application 쪽 callback을 보내지 못하는 상태가 확인되었다. private DNS와 private IP, security group·inbound rule, VPC endpoint, public/private AgentCore mode, dev·production server 분기 방식이 논의되었다. application instance를 직접 고르는 대신 ALB endpoint로 callback하면 load balancing과 server 분기를 application infrastructure에 맡길 수 있다는 이유로 ALB 사용을 결정했다. 다만 server-to-server authentication·encryption은 별도 확인 과제로 남았다. (`00:24-15:20`)

Backend 쪽에서는 user initializer 조회와 onboarding 완료 기록 API가 추가되었고, onboarding 완료 값은 일회성으로 true만 기록하는 구조로 설명되었다. Kibana·Grafana용 subdomain을 ALB에서 monitoring EC2로 연결했고, beta test에 필요한 backend 기능은 거의 끝난 것으로 자체 점검했다. (`15:29-20:14`)

Android 쪽에서는 onboarding 화면의 module dependency를 정리하며 구현 중이었고, timeline typography·사진 thumbnail 수정과 감정·event 추가 UI 설계도 진행했다. 목표는 온보딩을 8월 28일 전까지 마치는 것이었으나, 회의 후반에는 전체 앱을 주말쯤 심사 요청할 수 있을 것이라는 전망이 나왔다. 이는 확정 일정이 아니라 목표와 예상이다. (`20:14-21:49`, `28:18-34:28`)

## 상세 요약

### AgentCore callback 장애 진단

- 한 기기에서는 `초안 만들기`가 반응하지 않는 현상이 있었지만 다른 두 기기의 요청은 loading까지 진입했고 AgentCore dispatch 성공 log가 확인되었다. 따라서 mobile 공통 장애인지 특정 기기 상태인지, server callback 문제인지 분리할 필요가 있었다. (`00:36-04:18`)
- AgentCore가 application server로 다시 보내는 조회·저장 callback은 성공하지 않은 것으로 관찰되었다. 양쪽 IAM·network permission이 모두 필요하고 관리 지점이 많아 누락 가능성이 있다는 설명이 있었다. (`02:42-07:36`)
- private DNS로 실패하고 private IP로 바꿔 시험하는 과정이 있었으며, inbound rule과 security group 설정 여부도 함께 확인했다. (`05:21-07:36`)
- dev·production과 production의 여러 instance 중 어느 server로 callback할지 AgentCore가 직접 분기하도록 하면 환경 정보와 IP 관리가 복잡해진다는 문제가 제기되었다. (`07:43-08:39`)
- AgentCore를 private subnet과 VPC endpoint로 연결한 현재 구조와, public endpoint에서 HTTPS로 ALB를 호출하는 대안이 비교되었다. (`08:41-12:23`)
- 결론적으로 AI callback을 ALB endpoint로 보내고 load balancing과 destination 선택은 ALB 뒤에서 처리하는 방향을 택했다. 기존 private IP 경로는 회의 중에도 실패했고, callback 보호를 위한 authentication·encryption은 추가 확인이 필요하다. (`11:23-13:16`)
- 특정 기기에서만 난 `초안 만들기` 먹통은 local log를 연결해 보거나 이후 대면 시 확인하기로 했으며, 이 회의에서는 원인이 확정되지 않았다. (`13:20-15:20`)

### initializer API와 monitoring infrastructure

- user별 initializer 조회 API와 onboarding 완료 기록 API가 추가되었다. onboarding은 최초 한 번 제공하는 흐름이므로 완료 상태를 true로 기록하고 false로 되돌리는 endpoint는 두지 않았다고 설명했다. (`15:29-16:48`)
- 사용자가 onboarding 완료 전에 앱을 종료하면 다음 실행에서 다시 보여줄 수 있도록 완료 button을 누른 시점에 기록하는 흐름이 적절하다는 의견이 나왔다. (`16:00-16:48`)
- Kibana·Grafana가 path 아래에 있던 구성을 각각 별도 subdomain으로 분리하고, ALB가 monitoring EC2로 연결하도록 infrastructure를 정리했다고 보고되었다. (`16:49-17:20`)
- initializer response는 향후 공지, 알림 시간·허용 여부 등 앱 초기 상태를 추가할 수 있는 확장 지점으로 이해되었다. (`19:32-20:14`)

### 약관, 홍보 채널, 알림 정책

- 기존 앱의 정책·약관을 참고해 privacy policy와 consent 문서를 준비 중이라고 보고했다. (`17:20-17:35`)
- Threads와 Instagram account를 만들어 홍보를 준비하는 작업도 언급되었으나, 실제 운영 시작이나 게시 완료는 확인되지 않았다. (`17:35-17:56`)
- notification policy 공유 문서에 timeline 생성에 도움 된 사례를 올렸지만 payment keyword만 걸려 delivery notification 등은 충분히 수집되지 않았다는 관찰이 있었다. (`18:38-19:30`)

### Android onboarding과 timeline UI

- 전날 feedback을 반영해 text size와 photo thumbnail을 수정하고, initializer API를 연결한 onboarding 구현을 진행 중이었다. module dependency가 복잡해 경계를 침범하지 않도록 설계를 정리하는 데 시간이 걸렸다고 보고했다. (`20:14-21:23`)
- 감정 수정과 event 추가 UI의 위치도 설계 중이었으며, onboarding은 8월 28일 전까지 빠르게 마치는 목표를 제시했다. (`21:23-21:49`)
- 읽기 mode는 편집 화면을 덜어내고 감정 표시 등을 반영한 뒤 목요일이나 금요일에 다시 보여줄 예정이라고 말했다. 이는 작업 계획이며 구현 완료 보고는 아니다. (`28:18-28:52`)

### Figma billing 문제

- Figma 권한 설정 과정에서 예상보다 큰 약 65~66달러 결제가 발생했다고 보고되었다. 정확한 청구 원인은 팀원 seat 또는 권한 할당으로 추정했지만 확정되지 않았다. (`21:51-25:59`)
- Figma support에 환불을 요청하고, 환불이 안 되면 지원 사무국에 비용 처리 가능 여부를 문의하는 순서가 제안되었다. 실제 환불·지원 결과는 이 회의에서 확인되지 않았다. (`23:01-26:50`)

### mentoring과 beta release 일정

- 8월 28일 mentoring은 대면 일정과 시간 조정이 필요했고, AI 품질 개선 feedback을 받을 다른 mentoring은 준비가 덜 되어 별도 비대면 일정으로 미루는 방향이 제시되었다. 인명과 정확한 일정은 자동 전사가 불안정해 생략한다. (`29:03-32:14`)
- 금요일 완료가 가장 좋지만 현재 상태를 고려하면 주말에 Play Store 심사 요청을 시도할 수 있다는 전망이 나왔다. 심사 중에도 update를 반영할 수 있다는 전제로, 부족한 부분을 계속 고치는 방식이 언급되었다. (`32:14-34:28`)
- 9월부터 beta test와 본격 운영을 시작하는 큰 일정 구상이 공유되었지만, 실제 release 완료나 심사 승인 상태는 아니다. (`33:01-34:28`)

### 사업자 등록과 약관 URL

- 앱 심사에 약관 URL이 필요할 수 있다는 지적 후 사업자 등록 상태를 확인했고, 민원 처리 완료와 증명서 출력 가능 상태를 확인했다. PDF를 팀에 공유해 필요한 정보를 채우기로 했다. (`34:47-39:17`)
- 향후 유료 결제는 Play Store 결제 체계를 사용할 수 있다는 일반적 대화가 있었지만 실제 결제 기능을 scope에 넣거나 PG 방식을 확정한 것은 아니다. (`39:22-40:18`)

## 열린 질문

- AgentCore callback을 ALB로 보낼 때 요청 authentication, replay 방지, encryption은 어떻게 적용하는가?
- 특정 device의 `초안 만들기` 먹통은 local state, mobile bug, network 중 어디에서 발생했는가?
- initializer response에 onboarding, 공지, 약관 version, notification 설정을 어떤 schema로 포함할 것인가?
- 약관·privacy policy가 Play Store 심사와 실제 데이터 처리 범위를 충분히 설명하는가?
- 주말 심사 요청 전에 반드시 완료해야 할 mobile UI와 operational check는 무엇인가?

## 주의 사항

- AWS network 구성에 관한 대화는 troubleshooting 중의 가설과 임시 변경을 포함한다. 최종 infrastructure는 IaC·console·배포 log로 확인해야 한다.
- 전사상 `ESA`, `이 시트`, `WAS SG`, `ALB`, `VPC endpoint` 등 기술 용어가 혼재하며 일부는 잘못 인식되었다.
- Figma 결제액과 원인은 발언자의 확인 중 정보이며 invoice나 support 답변으로 검증되지 않았다.
- mentoring 인명·시간과 branch·endpoint 이름은 전사가 불명확해 확정 정보로 기록하지 않았다.
- 원문에는 개인 비용과 일정, 사업자 관련 정보가 포함되어 있으므로 공개 범위를 제한해야 한다.
