# Laimory AI 타임라인 알파 테스트 개선 계획

## 목적

Laimory AI 타임라인의 목적은 센서 데이터와 알림을 나열하는 것이 아니라, 사용자가 그날 무엇을 했는지 자연스럽게 회상하고 수정할 수 있는 일기형 타임라인을 만드는 것이다.

알파 테스트에서 발견된 문제는 다음 두 축으로 개선한다.

1. 프롬프트 개선: 정상적으로 전달된 근거의 의미를 해석하고, 서로 연결하며, 일기형 사건으로 표현하는 품질을 높인다.
2. 코드 추가 및 구조 개선: 시간, 하루 경계, 원본 누락, 이동·체류 병합, 사진 연결처럼 결정론적으로 보장해야 하는 문제를 해결한다.

기본 책임 분리는 다음과 같다.

> 프롬프트는 “이 근거들이 사용자의 어떤 하루 사건을 의미하는가”를 담당하고, 코드는 “근거가 빠지지 않았는가, 시간이 정확한가, 어떤 단위로 묶어 전달할 것인가”를 담당한다.

---

## 1. 프롬프트를 개선해서 해결할 부분

### 1.1 모든 Agent가 공유할 Laimory의 비전과 목표

모든 시스템 프롬프트의 첫 부분에 역할별 세부 규칙보다 먼저 같은 high-level 목표를 둔다. 특히 Timeline Agent와 Repair Agent는 이 목표를 최종 결과의 최우선 평가 기준으로 사용하고, 각 Event Agent는 자기 데이터가 최종 하루 복원에서 어떤 역할을 하는지 이해해야 한다.

공통으로 전달할 핵심 내용은 다음과 같다.

- Laimory는 사용자가 직접 기록하지 않아도 일상 데이터를 바탕으로 그날의 경험을 되살릴 수 있게 돕는 Personal AI Memory 서비스다.
- 목표는 센서, 캘린더, 사진, 건강 데이터, 알림을 요약하는 것이 아니라 데이터가 생긴 원인이 된 사용자의 실제 하루를 복원하는 것이다.
- 좋은 결과는 원본을 많이 나열한 결과가 아니라 `어디서 출발해`, `왜 이동했고`, `어디에 도착해`, `누구와 무엇을 했으며`, `하루가 어떻게 끝났는지`가 자연스럽게 이어지는 결과다.
- 위치는 거의 모든 사건을 시간과 장소에 고정하는 기본 축이고, 캘린더는 사용자의 의도와 목적을 설명하는 핵심 축이다.
- 사진, 알림, 건강 데이터는 위치와 캘린더가 만든 하루의 뼈대를 설명하거나 보강하는 근거로 사용한다.
- 데이터는 불완전하고 잘못 분류될 수 있다. 센서 라벨을 그대로 믿지 말고 시간·거리·장소·전후 흐름과 현실 가능성을 함께 검토한다.
- 직접 관측된 사실과 여러 근거를 연결한 추론, 가능성에 불과한 가설을 구분한다.
- 근거가 충분하면 높은 수준의 생활 맥락을 적극적으로 추론하되, 근거가 부족한 장소·사람·행동은 창작하지 않는다.
- 사건의 개수보다 사용자가 그날을 회상하는 데 중요한 핵심 사건을 우선한다.
- 최종 결과는 분석 보고서가 아니라 사용자가 읽고 고칠 수 있는 자연스러운 일기 초안이어야 한다.

프롬프트 첫머리의 공통 메시지는 다음 의미를 분명히 전달해야 한다.

> 당신은 한 종류의 데이터를 변환하는 기계가 아니라, 다른 Agent와 협력해 사용자의 실제 하루를 복원하는 AI 협력자다. 자기 데이터에서 최종 하루의 중심 흐름을 설명할 수 있는 사실, 연결 단서, 고수준 가설을 찾아야 한다.

### 1.2 모든 Agent가 공유할 고수준 추론 기준

각 Agent는 raw item 하나를 event 하나로 바꾸는 방식에서 벗어나, 자기 입력 전체의 시간적·공간적 흐름과 반복 패턴을 먼저 이해한다.

- 개별 raw보다 하루 전체 또는 해당 데이터 유형 전체의 흐름을 먼저 본다.
- 여러 raw가 하나의 행동을 가리키면 하나의 candidate로 병합하고 모든 `sourceRefs`를 보존한다.
- 센서가 만든 작은 조각과 사용자가 경험한 실제 사건의 단위가 다를 수 있음을 전제로 한다.
- 물리적으로 불가능하거나 상식적으로 모순되는 값은 그대로 사건으로 만들지 않고 데이터 오류 가능성을 기록한다.
- candidate를 만들 때 단순 제목뿐 아니라 Timeline Agent가 다른 source와 병합할 수 있는 활동 의미, 장소 의미, 중요도, 불확실성을 전달한다.
- 핵심 사건 후보와 보조 맥락을 구분한다. 보조 단서는 독립 카드를 만들기보다 중심 사건을 풍부하게 설명하는 데 사용한다.
- 거의 모든 candidate는 위치 연결을 검토하고, 연결된 위치 근거 또는 위치 부족·충돌 상태를 명시한다.
- 추론이 여러 단계로 이어질 때 각 단계의 근거를 잃지 않는다.

공통 추론 강도는 다음처럼 구분한다.

- `DIRECT`: 원본이 시간, 장소 또는 행동을 직접 말한다.
- `EVIDENCE_BASED`: 서로 다른 여러 근거와 전후 흐름이 같은 결론을 지지한다.
- `INFERRED`: 맥락상 가능성이 높지만 직접 확인되지 않았다.
- `UNCERTAIN`: 근거가 약하거나 다른 가능성과 충돌한다.

### 1.3 Location Event Agent 개선

Location Event Agent는 개별 STAY와 MOVEMENT를 번역하는 Agent가 아니라, 하루 위치 데이터에서 실제 방문, 장거리 여정, 출발과 도착, 귀가를 복원하는 Agent로 정의한다. 새로운 Agent를 추가하지 않고 현재 Location Event Agent의 추론 단위를 높인다.

- 입력된 하루 위치 흐름 전체를 먼저 시간순으로 검토한다.
- 연속 Movement와 이동 중 생긴 짧은 STAY를 출발지와 최종 목적지 중심의 하나의 여정 후보로 병합한다.
- GPS가 이동 경로를 따라 생성한 중간 STAY와 실제 방문·활동 장소의 STAY를 구분한다.
- 시간, 거리, 좌표 변화, 장소 유형, 이동 전후 흐름을 함께 보고 이동 목적과 교통수단 가능성을 추론한다.
- `WALKING 13.3km, 3분`처럼 현실적으로 불가능한 분류를 그대로 믿지 않고 센서 분류 오류를 uncertainty 또는 anomaly로 남긴다.
- 역·공항·터미널 근처로 이동한 뒤 장거리 경로가 이어지면 대중교통 탑승 가능성을 검토한다.
- 중간 좌표가 철도 또는 주요 교통 경로를 따라 이어지고 최종적으로 다른 도시의 역에 도착하면 도시 간 이동 하나로 복원한다.
- 7월 31일 사례에서는 신암동 방향 이동, 경부선 방향의 중간 좌표, 서울역 도착을 연결해 `동대구역에서 서울역까지 열차로 이동했을 가능성`을 제시할 수 있어야 한다.
- 열차 이동 가능성이 높더라도 정확한 열차 종류가 확인되지 않으면 `KTX 또는 다른 열차`처럼 대안 가능성을 보존한다.
- 반복적인 야간 주거지 체류, User Memory, 반복 출발·도착 패턴을 함께 사용해 집 후보를 판단한다.
- 아침 첫 체류와 마지막 이동·체류를 확인해 출발과 귀가 후보를 빠뜨리지 않는다.
- 장소만으로 활동 목적을 알 수 없으면 다른 Agent와 병합할 수 있는 장소·시간·이동 의미를 충분히 남긴다.
- Location candidate는 Timeline Agent가 경로를 다시 조립하지 않아도 될 정도로 상위 이동 의미를 전달해야 한다.

Location Agent의 목표 출력 수준은 다음과 같다.

> 대구 동구 신암동 이후 경부선 방향의 여러 위치 조각을 지나 서울역에 도착했으므로, 중간 체류들은 실제 방문보다 이동 중 GPS 기록이며 동대구역에서 서울역까지 열차로 이동했을 가능성이 높다.

### 1.4 Calendar Event Agent 개선

Calendar Event Agent는 일정 문구를 그대로 옮기는 데 그치지 않고, 일정이 하루에서 차지하는 목적과 중요도를 Timeline Agent가 이해할 수 있도록 전달한다.

- 일정 제목에서 회의, 교육, 업무, 약속, 행사, 이동 목적과 같은 활동 의미를 적극적으로 추출한다.
- `소마 369팀 정기 회의`처럼 장시간 이어지는 팀 일정은 단순 회의뿐 아니라 팀 활동·프로젝트 작업이 이어질 가능성을 포함한 중심 일정 후보로 전달한다.
- 캘린더는 계획이지 참석 증거가 아니므로 실제 참석 여부는 같은 시간의 위치·사진·알림과 결합해 판단하도록 한다.
- 일정 전후 이동과 결합할 수 있도록 목적지, 활동 태그, 중요도, 예상 관계자를 명확히 남긴다.
- 여러 날 이어지는 일정은 전체 시작·종료를 일기처럼 반복하지 않고 요청 날짜의 배경 맥락으로 표현한다.
- 그날의 중심 일정과 단순 리마인더·배경 일정을 구분한다.
- 모든 캘린더 raw는 누락 없이 candidate가 되지만, 화면에서 어떤 중요도로 보일지는 Timeline Agent가 다른 근거와 함께 판단한다.

### 1.5 Photo Event Agent 개선

Photo Event Agent는 사진이 존재한다는 사실보다 사진이 어떤 활동과 순간을 보여주는지 전달한다.

- 실제 이미지 description에서 음식, 행사, 발표, 작업, 이동, 휴식, 장소 단서를 추출한다.
- 촬영 시각과 위치를 같은 시간대의 STAY, MOVEMENT, CALENDAR와 연결할 수 있는 형태로 전달한다.
- 음식 사진은 촬영 시각 부근의 식사 후보로 만들고 긴 체류 전체를 식사 시간으로 사용하지 않는다.
- 촬영 시각이 크게 다른 음식 사진은 점심과 저녁처럼 별도 후보로 분리한다.
- 사진 자체를 `사진 촬영` 사건으로 과장하지 않고 중심 활동을 보강하는 근거로 우선 사용한다.
- 사진에 보이지 않는 음식, 장소, 사람은 창작하지 않는다.
- 같은 사진이 여러 후보의 근거가 될 수 있더라도 어떤 사건의 대표 사진으로 가장 적합한지 우선순위를 전달한다.

### 1.6 Notification Event Agent 개선

Notification Event Agent는 수신 알림을 사용자의 행동으로 오해하지 않고, 핵심 활동을 설명하는 맥락으로 해석한다.

- 메신저 알림은 상대가 보낸 메시지이며 사용자 발신·답장을 증명하지 않는다는 점을 최우선으로 지킨다.
- 수신 기록이 있고 동일한 상대가 반복된다면 `대화를 주고받았다`, `대화가 이어졌다`고 단정한다.
- 단순 메신저 수신은 기본적으로 fragment로 두고, 사용자가 직접 열거나 행동했다는 근거 또는 핵심 일정과의 강한 관련성이 있을 때만 candidate를 고려한다.
- 같은 상대·대화방·주제의 알림을 묶되 비연속 메시지를 연속된 몇 시간짜리 행동으로 만들지 않는다.
- 결제, 송금, 예약, 교통, 업무 알림은 실제 행동과 연결될 가능성이 높은 근거로 우선한다.
- Discord의 개발 메시지는 독립적인 `알림 확인` 사건보다 진행 중인 프로젝트 작업을 보강하는 단서로 전달한다.
- 팀원 3인의 정산 요청은 공동 식사나 공용 비용 가능성을 제시할 수 있지만 비용의 성격을 확정하지 않는다.
- User Memory 또는 명시적 관계 근거가 있을 때만 `여자친구`, `가족`, `팀원` 같은 관계를 확정한다.
- JWT, 인증 토큰, 개인정보 등 민감한 본문은 복사하거나 최종 일기에 노출하지 않고 보안 경고만 남긴다.
- 일반 수신 메시지가 장거리 이동이나 핵심 캘린더 일정보다 중요한 독립 사건이 되지 않도록 중요도를 낮춘다.

### 1.7 Sleep/Activity Event Agent 개선

Sleep/Activity Event Agent는 수면 세션과 누적 건강 집계의 시간 의미를 구분한다.

- 수면 시작·종료가 명시된 수면 세션만 `SLEEP`의 직접 근거로 사용한다.
- 기상은 신뢰할 수 있는 수면 종료 시각이 있을 때만 생성한다.
- `health.endAt`이나 활동 집계 종료 시각을 기상 또는 특정 행동 발생 시각으로 사용하지 않는다.
- `00:00~13:38 동안 1,864보` 같은 데이터는 누적 집계이며 `13:38에 기상했다`는 뜻이 아님을 명시한다.
- 하루 누적 걸음 수·거리·칼로리는 기본적으로 fragment로만 전달하고 독립 이벤트를 만들지 않는다.
- 걸음 수는 `이동량이 많았는지`, `주로 차량·열차와 실내 활동이었는지` 같은 하루 전체 맥락을 보강하는 데 사용한다.
- 수면 이벤트를 제품에서 제외하기로 결정하면 `SLEEP`·`WAKE_UP` 생성 규칙을 함께 제거한다.

### 1.8 Timeline Agent 개선

Timeline Agent는 모든 후보를 카드로 바꾸는 Agent가 아니라, 후보와 단서를 종합해 사용자의 하루에서 중요한 사건을 선택하고 서로 연결하는 최종 하루 복원 Agent다.

Timeline 프롬프트 첫머리에는 공통 비전과 함께 다음 우선순위를 특히 강하게 둔다.

1. 최종 event를 만들기 전에 하루 전체 후보를 시간순으로 읽는다.
2. `이날은 어떤 날이었는가`를 한 문장으로 내부적으로 먼저 정리한다.
3. 출발지, 장거리 이동, 최종 목적지, 중심 일정, 마지막 활동을 찾아 하루의 큰 흐름을 세운다.
4. Location Agent의 상위 여정 후보와 Calendar Agent의 중심 일정 후보를 먼저 연결한다.
5. 사진·알림·건강 fragment는 핵심 사건을 설명하거나 confidence를 조정하는 근거로 사용한다.
6. 핵심 사건을 모두 포함한 뒤에만 보조 사건의 독립 카드 가치를 판단한다.
7. 같은 사건을 가리키는 후보는 source 유형이 달라도 하나로 병합한다.
8. 사건의 개수보다 하루 설명력과 회상 가치를 우선한다.

중요도는 다음 순서로 판단한다.

- 장거리 이동과 생활권 변화
- 사용자가 직접 등록한 중심 캘린더 일정
- 장시간 주요 체류와 목적 있는 활동
- 여러 source가 함께 뒷받침하는 사건
- 사진·결제·예약처럼 실제 행동과 가까운 단서
- 일반 수신 알림과 하루 누적 건강 집계

Timeline Agent는 다음 실패를 만들지 않아야 한다.

- 대구→서울 장거리 이동을 여러 지역의 작은 이동과 체류로만 남기기
- `소마 369팀 정기 회의`를 위치 이동과 분리된 캘린더 문장으로만 쓰기
- 같은 회의 일정을 중복 카드로 만들기
- 활동 집계 종료 시각을 `늦은 아침 기상`으로 오해하기
- 일반 카카오톡 수신 알림을 장거리 이동보다 큰 사건으로 표시하기
- 같은 시간대의 위치 근거가 있는데 이벤트에 연결하지 않기
- 오후 위치 데이터가 없는데 회의 장소나 귀가를 확정하기

7월 31일 입력에서 목표로 하는 Timeline 수준은 다음과 같다.

> 대구 집에서 출발해 동대구역 방향으로 이동한 뒤 서울행 열차를 이용한 것으로 보이며, 정오 무렵 공덕·마포 인근에 도착해 소마 369팀 회의와 프로젝트 작업을 저녁까지 진행한 날로 추정된다. 저녁 식사와 팀 비용 정산의 정황은 있지만 사진과 오후 위치가 부족해 구체적인 장소와 귀가 여부는 확정할 수 없다.

최종 이벤트는 이 중심 흐름을 설명하는 핵심 사건을 우선하고, 일반 메시지와 건강 집계는 필요한 경우 보조 맥락으로만 남긴다.

### 1.9 Repair Agent 개선

Repair Agent는 문장 몇 개를 다듬는 Agent가 아니라, 최종 타임라인이 Laimory의 하루 복원 목표를 달성했는지 검토하는 마지막 품질 관리자다. 현재 도구 호출 방식과 기존 구조는 유지한다.

Repair Agent는 먼저 다음 high-level 질문을 확인한다.

- 이 결과만 읽어도 사용자가 어디서 출발해 어디로 이동했고 무엇을 했는지 알 수 있는가?
- 가장 중요한 이동과 일정이 모두 포함됐는가?
- 센서 조각이 실제 경험 단위로 병합됐는가?
- 약한 알림이나 건강 집계가 핵심 사건보다 과도하게 부각되지 않았는가?
- 거의 모든 사건이 위치 해석을 거쳤는가?
- 하루의 시작과 마지막 흐름이 근거가 허용하는 범위에서 연결됐는가?
- 직접 사실, 근거 기반 추론, 가능성, 데이터 오류가 구분됐는가?

7월 31일과 같은 결과에서는 다음을 반드시 문제로 잡아야 한다.

- 장거리 위치 흐름이 있는데 대구→서울 이동이 상위 사건으로 복원되지 않음
- 경로상의 GPS 조각이 실제 방문 장소처럼 분리됨
- 같은 `소마 369팀 정기 회의`가 중복 생성됨
- 활동 집계 종료 시각 13:38을 기상으로 잘못 해석함
- 수신 메시지를 `주고받은 대화`로 과장함
- 일반 메시지 카드가 장거리 이동보다 중요하게 노출됨
- 회의가 전후 이동과 연결되지 않아 하루의 중심 서사가 사라짐
- 오후 위치와 사진이 없는데 식사 장소나 귀가를 확정함

문제가 발견되면 기존 도구를 다음 원칙으로 사용한다.

- Location 해석 단위가 잘못됐으면 해당 Location Event Agent를 다시 실행한다.
- 후보는 맞지만 하루의 중심 흐름과 병합이 잘못됐으면 Timeline Agent를 다시 실행한다.
- 잘못된 개별 사건 하나로 해결할 수 있으면 `update_event` 또는 `delete_event`를 사용한다.
- 전체 재생성은 핵심 여정이나 중심 일정이 구조적으로 누락됐을 때만 사용한다.
- 문장이 자연스럽다는 이유로 사실성과 중요도 문제를 통과시키지 않는다.

### 1.10 공통 출력 품질과 문체

- `어디에 머물렀다`, `어디에서 어디까지 이동했다`, `알림을 확인했다` 수준에서 끝내지 않는다.
- 이동은 출발·목적지·다음 활동이 연결된 여정으로 표현한다.
- 체류는 가능한 경우 그 장소에서 한 활동으로 표현한다.
- 사용자의 행동이 아니라 Agent의 판단 과정을 설명하는 `추론됩니다`, `판단했습니다` 같은 보고서 말투를 피한다.
- 확실하지 않은 내용은 `듯하다`, `가능성이 있다`처럼 자연스럽게 표현하고 구조화된 uncertainty에도 남긴다.
- 사람, 관계, 장소, 활동을 추론할 때 근거와 대안 가능성을 보존한다.
- 모든 candidate와 최종 event에는 실제 `sourceRefs`를 남긴다.
- 여러 raw를 병합해도 어떤 원본이 어떤 결론을 지지했는지 추적할 수 있어야 한다.
- 민감한 알림 원문, 인증 토큰, 개인정보를 최종 일기에 노출하지 않는다.

### 1.11 7월 31일 모범 답안의 활용

`7월 31일 실제 값과 모범 답안.md`는 문장을 그대로 복사하는 예시가 아니라, 현재 Agent들이 도달해야 하는 추론 수준을 정의하는 회귀 평가 기준으로 사용한다.

평가해야 할 능력은 다음과 같다.

- 대구의 주거지 체류를 집 후보로 해석
- 집 출발, 동대구역 방향 이동, 경부선 방향 위치, 서울역 도착을 하나의 장거리 여정으로 연결
- 이동 중 GPS 조각과 실제 방문 체류를 구분
- 비현실적인 도보 분류를 데이터 오류로 판단
- 서울역 도착 후 공덕·도화동 이동을 중심 일정의 도착 흐름으로 연결
- 소마 정기 회의를 단순 일정이 아니라 회의·프로젝트 작업의 중심 활동으로 해석
- Discord 개발 메시지를 진행 중인 팀 작업의 보조 근거로 사용
- 팀 정산을 공동 비용 또는 식사 가능성으로 해석하되 확정하지 않음
- 수신 메시지와 실제 양방향 대화를 구분
- 13:38 활동 집계 종료를 기상으로 오해하지 않음
- 오후 위치·사진 부족과 귀가 미확인을 명확히 남김
- 최종적으로 하루를 `대구에서 서울로 이동해 소마 팀 활동을 한 날`이라는 중심 서사로 설명

모범 답안과 완전히 같은 문장을 생성할 필요는 없지만, 핵심 여정·중심 활동·보조 맥락·데이터 오류·불확실성을 같은 수준으로 복원해야 한다.

## 2. 코드 추가 및 구조 개선으로 해결할 부분

### 2.2 필수 원본 누락 방지

- 모든 캘린더 `rawId`가 최종 이벤트의 `sourceRefs`에 포함됐는지 검사한다.
- 모든 유효 Movement가 하나 이상의 의미 있는 이동 사건에 포함됐는지 검사한다.
- 주요 STAY가 최종 사건에 포함됐는지 검사한다.
- Vision 처리가 완료된 모든 사진이 최종 결과에 반영됐는지 검사한다.
- 소마 센터와 같은 장시간 주요 체류가 누락됐는지 검사한다.
- 마지막 이동과 집 체류가 입력에 있는데 귀가 흐름이 누락됐는지 검사한다.
- 존재하지 않는 `rawId`를 참조하는 결과를 차단한다.
- 누락 발견 시 코드로 복원하거나 Repair Agent에 구체적인 수정 요청을 전달한다.

모든 유효 원본은 최종적으로 다음 상태 중 하나를 가져야 한다.

- 최종 이벤트 근거로 사용
- 다른 원본과 병합
- 노이즈로 제외
- 처리 실패
- 사용자 확인 필요

### 2.3 이동과 체류의 결정론적 전처리 -> Repair 에서 수행? 일단 대기 클라이언트에서 개선 예정

- 시간 연속성, 출발지, 도착지, 이동 수단을 기준으로 연속 Movement를 하나의 경로로 병합한다.
- 수원시청역→기흥역→동백역과 같은 경로를 목적지 중심의 하나의 이동으로 구성한다.
- 대구→서울 이동을 동대구역→서울역과 같은 장거리 여정으로 구성할 수 있도록 역과 주요 교통 거점을 인식한다.
- 환승과 짧은 중간 체류를 별도 카드보다 상위 여정의 하위 근거로 처리한다.
- 같은 장소의 STAY 사이에 Movement가 없으면 하나의 연속 체류로 병합한다.
- GPS 노이즈로 생성된 짧은 체류 조각을 제거하거나 병합한다.
- 병합 전 원본 `rawId`를 최종 사건에 모두 보존한다.
- LLM에는 센서 조각 전체보다 코드가 만든 의미 있는 이동·체류 묶음을 전달한다.

### 2.4 이벤트 병합·분할 제약

- 지나치게 짧은 이벤트의 최소 지속시간 또는 중요도 기준을 둔다.
- 식사 이벤트는 최대 60분으로 제한한다.
- 촬영 시각 차이가 큰 사진은 서로 다른 시간 클러스터로 분리한다.
- 서로 다른 장소를 동시에 주장하는 이벤트를 검출한다.
- 수면과 다른 이벤트가 겹치는지 검사한다.
- 시간·장소가 연속된 이동이 여러 카드로 과도하게 분리되지 않도록 후처리한다.
- 여러 날 일정은 당일의 background context로 투영해 Agent에 전달한다.

### 2.5 사진 처리 확인

사진 기능은 이미 개선된 상태이므로 추가 변경보다 기존 알파 테스트 입력을 이용한 재검증을 우선한다.

- 수집된 사진 수를 기록한다.
- 이미지 다운로드 성공·실패 상태를 기록한다.
- Vision 호출 성공·실패 상태를 기록한다.
- 각 사진의 description 생성 여부를 확인한다.
- Photo Event Agent 입력·출력 개수를 확인한다.
- Timeline Agent에 사진 candidate가 전달됐는지 확인한다.
- 저장 과정에서 사진 연결이 유지됐는지 확인한다.
- UI에서 사진이 실제로 표시됐는지 확인한다.
- 점심과 저녁 사진이 별도 사건으로 분리됐는지 확인한다.
- 동일 사진이 여러 카드에 중복 표시되지 않았는지 확인한다.

사진 연결은 다음 두 개념으로 분리한다.

- `sourceRefs`: 사진이 사건의 추론 근거로 사용됐는지 나타낸다.
- `primaryEventId`: 사진을 UI에 표시할 단 하나의 대표 사건을 나타낸다.

### 2.6 위치 강제 연결 및 장소·집 후보 전처리

- Timeline 생성 전후에 거의 모든 이벤트에 대해 같은 시간대의 STAY, MOVEMENT, GPS를 연결한다.
- 위치 연결 결과는 `CONFIRMED`, `INFERRED`, `CONFLICTED`, `MISSING` 중 하나여야 하며 빈 상태를 허용하지 않는다.
- 같은 시간대에 위치 데이터가 있는데 `MISSING`으로 끝난 이벤트는 검증 실패로 처리한다.
- `CONFIRMED`인데 위치 `sourceRefs`가 없는 이벤트는 검증 실패로 처리한다.
- 캘린더의 예정 장소인 `eventPlace`와 기기에서 관측한 `observedLocation`을 분리해 저장한다.
- `eventPlace`와 `observedLocation`이 일치하면 병합 confidence를 높이고, 충돌하면 `CONFLICTED`로 표시해 질문 또는 경고를 생성한다.
- 반복적인 야간 체류 좌표를 `HOME_CANDIDATE`로 계산한다.
- User Memory의 집 주소와 생활 장소를 위치 데이터에 연결한다.
- 역, 병원, 교육 센터, 학교, 회사 등 주요 장소 유형을 구조화한다.
- 좌표만으로 장소명을 창작하지 않고 수집된 장소 정보 또는 지도·POI 결과를 사용한다.
- 이동 출발지와 도착지에 대표 장소명과 장소 유형을 제공한다.
- 마지막 이동과 마지막 체류를 이용해 귀가 근거를 계산한다.
- Agent에 `placeName`, `placeType`, `homeConfidence`처럼 해석 가능한 정보를 제공한다.

권장 위치 구조는 다음과 같다.

```json
{
  "locationContext": {
    "status": "CONFIRMED|INFERRED|CONFLICTED|MISSING",
    "eventPlace": {
      "label": "캘린더·사진 등이 가리키는 사건 장소 또는 null",
      "sourceRefs": []
    },
    "observedLocation": {
      "label": "같은 시각의 실제 관측 장소 또는 null",
      "sourceRefs": []
    },
    "uncertainty": []
  }
}
```

### 2.7 알림 사전 그룹화

- 앱, 대화방, 발신자, 시간, 주제별로 알림을 미리 묶는다.
- 광고, 시스템, 반복 알림을 제거한다.
- 결제, 송금, 예약, 교통, 메신저 알림을 유형별로 분류한다.
- 같은 사건과 연결될 가능성이 있는 알림 그룹을 만든다.
- 띄엄띄엄 발생한 메시지는 연속 시간 구간이 아닌 비연속 대화 묶음으로 표현한다.
- User Memory에 저장된 관계 정보와 알림 발신자를 연결한다.
- 개인정보 원문을 그대로 전달하지 않고 필요한 수준으로 요약한다.

### 2.8 처리 구조 개선

권장 처리 흐름은 다음과 같다.

```text
원본 데이터
  → timezone·하루 경계 정규화
  → 위치·이동·체류 전처리
  → 사진 Vision 처리
  → 알림 필터링 및 그룹화
  → 장소·집 후보 계산
  → 데이터별 Event Agent
  → 시간·장소 기반 후보 연결
  → Timeline Agent 의미 병합
  → 결정론적 누락·중복·시간·위치 연결 검증
  → Repair Agent
  → 사실을 변경하지 않는 일기체 문장화
  → 저장
  → UI 표시 검증
```

Repair Agent는 검증기가 발견한 구체적인 오류만 수정하도록 제한한다.

- 누락된 source 추가
- 잘못 병합된 사건 분리
- 관련 사건 재병합
- 근거 없는 활동 제거
- 일부 구간 재생성
- 전체 타임라인 재생성은 최후 수단으로 사용

### 2.9 관측성과 회귀 테스트

- 디버그 환경의 타임라인 화면에 `taskId`를 표시한다.
- taskId로 원본 입력부터 UI 결과까지 전 단계를 추적한다.
- 각 단계의 입력 수, 출력 수, 제외 사유를 기록한다.
- Agent별 입력과 출력을 기록한다.
- timezone 변환 전후 값을 기록한다.
- 사진 다운로드와 Vision 처리 상태를 기록한다.
- 각 source가 어느 이벤트에 병합됐는지 기록한다.
- 기존 알파 테스트 taskId를 회귀 테스트 데이터셋으로 고정한다.
- 프롬프트나 코드를 변경할 때 같은 입력으로 이전 결과와 비교한다.

## 최종 점검 결과

- 원본 개선사항에서 누락된 요구사항은 없다.
- 프롬프트 개선, 코드·구조 개선, 사진 재검증, 수면 정책 결정으로 모든 항목을 분류했다.
- Agent 구조는 새로 추가하지 않고 기존 Event Agent → Timeline Agent → Repair Agent 흐름을 유지한다.
- 모든 Agent의 프롬프트 첫머리에 Laimory의 비전과 고수준 하루 복원 목표를 공유하도록 반영했다.
- 7월 31일 실제 결과와 모범 답안을 각 Agent의 추론 수준과 회귀 평가 기준으로 반영했다.
- 다음 항목은 사실성 보호를 위해 원문 그대로가 아니라 조건부 요구사항으로 반영했다.
  - 집과 귀가는 실제 위치·반복 패턴·User Memory 근거가 있을 때만 확정한다.
  - 여자친구와 같은 관계는 User Memory 또는 사용자 확인이 있을 때만 확정한다.
- 거의 모든 이벤트에 위치 해석을 강제한다. 위치 근거가 존재하면 반드시 연결하고, 정확한 장소를 찾지 못하더라도 `CONFLICTED` 또는 `MISSING` 상태를 명시한다.
- 위치 연결을 강제하더라도 근거에 없는 장소명을 창작하지 않는다.
- 사진 기능은 이미 개선되었다는 현재 상태를 반영해 추가 설계보다 기존 taskId를 이용한 재검증 항목으로 분류했다.
- 수면은 시간 정규화 이후 `유지`, `기상만 유지`, `전체 제외` 중 하나를 선택해야 한다.

## 완료 기준

다음 조건을 모두 만족하면 이번 개선 작업이 완료된 것으로 본다.

- 동일 알파 테스트 입력에서 UTC/KST와 하루 경계 오류가 발생하지 않는다.
- 모든 필수 Calendar, Photo, 유효 Movement, 주요 STAY의 처리 상태를 추적할 수 있다.
- 거의 모든 최종 이벤트가 `CONFIRMED`, `INFERRED`, `CONFLICTED`, `MISSING` 중 하나의 위치 상태를 가진다.
- 같은 시간대에 위치 근거가 존재하는 이벤트는 해당 STAY, MOVEMENT 또는 GPS를 반드시 참조한다.
- 연속 이동과 끊긴 체류가 의미 있는 사건 단위로 병합된다.
- 7월 31일 입력에서 대구 출발, 동대구역 방향 이동, 경부선 방향 위치 조각, 서울역 도착을 하나의 장거리 여정으로 복원한다.
- 7월 31일 입력에서 `health.endAt` 13:38을 기상 이벤트로 만들지 않는다.
- 7월 31일 입력에서 수신 카카오톡 알림을 양방향 대화로 단정하거나 장거리 이동보다 중요한 사건으로 표시하지 않는다.
- 7월 31일 입력에서 소마 정기 회의를 중복 생성하지 않고 서울 도착 이후의 중심 팀 활동으로 연결한다.
- 사진은 최종 UI에서 누락되지 않고 대표 사건 한 곳에만 표시된다.
- 위치·캘린더·사진·알림이 같은 사건을 가리키면 하나의 생활 사건으로 연결된다.
- 근거 없는 집, 귀가, 관계, 장소, 활동을 창작하지 않는다.
- 최종 제목과 설명이 데이터 라벨 나열이 아니라 자연스러운 일기 초안으로 읽힌다.
- 기존 알파 테스트 taskId에 대한 회귀 테스트가 통과한다.
