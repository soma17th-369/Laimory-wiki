# Laimory AI 타임라인 핵심 개선 요구사항

## 1. 목적

이번 개선의 목표는 기존 Agent 구조를 크게 바꾸는 것이 아니다.

현재 구조인

```text
Event Agents → Timeline Agent → Repair Agent
```

를 유지하면서, 다음 네 가지 핵심 문제만 우선 해결한다.

1. Timeline Agent가 사용자의 하루를 높은 수준에서 복원하고 일기처럼 설명하도록 한다.
2. Location Agent가 여러 위치·이동 기록을 하나의 이동·체류 흐름으로 추론하도록 한다.
3. Repair Agent가 데이터 정합성뿐 아니라 최종 타임라인의 의미와 일기 품질까지 검증하도록 한다.
4. Fragment의 의미와 우선순위를 모든 Event Agent와 Timeline Agent가 동일하게 이해하도록 한다.

이번 단계에서는 기능 범위를 과도하게 넓히지 않는다. 기존 구조를 유지하고, 위 네 가지를 중심으로 프롬프트와 검증 코드를 수정한다.

---

# 2. 공통 제품 비전

모든 Agent는 다음 high-level vision을 공유해야 한다.

> Laimory의 목적은 센서 데이터, 캘린더, 사진, 알림을 나열하는 것이 아니라, 그 정보가 생긴 원인이 된 사용자의 실제 하루를 예측하고 복원해 사용자가 읽고 수정할 수 있는 일기형 타임라인으로 만드는 것이다.

Event Agent는 자기 데이터 유형을 전문적으로 해석한다. Timeline Agent는 그 결과를 단순 연결하지 않고 사용자가 실제로 어떤 하루를 보냈는지 최종적으로 재구성한다. Repair Agent는 그 결과가 이 비전을 충족하는지 검증한다.

# 3. Timeline Agent 개선

## 3.1 핵심 역할

Timeline Agent는 Event Agent의 candidate를 연결하거나 나열하는 Agent가 아니다.

각 candidate와 fragment를 힌트로 삼아 다음 질문에 답해야 한다.

> 이 정보들을 남긴 사용자는 이날 언제, 어디서, 누구와, 무엇을, 어떻게, 왜 했는가?

최종 결과는 다음 수준을 지향한다.

- `어디에 갔다`
- `어디에 머물렀다`

수준에서 끝나지 않는다.

가능한 근거 범위 안에서 다음이 자연스럽게 연결되어야 한다.

- 언제 발생했는가
- 어디서 시작하고 어디로 이동했는가
- 누구와 관련된 일이었는가
- 무엇을 했는가
- 어떤 방식으로 이동하거나 활동했는가
- 왜 그 행동을 했을 가능성이 있는가
- 그 사건이 하루 전체에서 어떤 의미를 가졌는가

최종 타임라인은 이벤트 카드 목록이 아니라 사용자가 읽었을 때 자신의 하루를 떠올릴 수 있는 일기 초안이어야 한다.

## 3.2 Timeline Agent 프롬프트에 추가할 핵심 문구

Timeline Agent 시스템 프롬프트 첫 부분에 아래 의미를 명확히 추가한다.

> 당신의 임무는 Event Agent가 만든 후보를 단순히 연결하거나 나열하는 것이 아니다. Candidate와 fragment를 하루의 단서로 사용해, 그 정보를 남긴 사용자가 실제로 어떤 하루를 보냈는지 예측하고 복원해야 한다. 최종 결과는 언제, 어디서, 누구와, 무엇을, 어떻게, 왜 했는지가 가능한 범위에서 드러나는 자연스러운 일기형 타임라인이어야 한다.

> 먼저 `이날은 어떤 날이었는가`를 내부적으로 한 문장으로 정리한 뒤, 그 중심 서사를 설명하는 핵심 사건을 선택하고 시간순으로 연결한다.

> 후보 제목과 설명을 그대로 복사하지 않는다. 여러 후보와 fragment를 연결해 더 높은 수준의 실제 사건으로 재구성한다.

## 3.3 Timeline Agent 처리 순서

Timeline Agent는 다음 순서로 처리한다.

1. 모든 candidate와 fragment를 시간순으로 읽는다.
2. 위치 흐름과 중심 캘린더 일정을 기준으로 하루의 큰 흐름을 파악한다.
3. `이날은 어떤 날이었는가`를 내부적으로 한 문장으로 정리한다.
4. 중심 서사를 설명하는 핵심 사건을 우선 선택한다.
5. 같은 사건을 가리키는 candidate를 병합한다.
6. fragment를 관련 candidate 또는 최종 event의 보조 근거로 연결한다.
7. 핵심 사건을 모두 반영한 뒤 보조 사건의 독립 event 가치를 판단한다.
8. 최종 결과가 육하원칙과 일기 흐름을 충분히 설명하는지 자체 검토한다.

## 3.4 Timeline Agent가 피해야 할 결과

- candidate 제목을 거의 그대로 복사한 카드 목록
- 이동, 체류, 알림, 캘린더가 서로 연결되지 않은 결과
- 하루에서 가장 큰 이동이나 중심 일정이 빠진 결과
- 일반적인 작은 단서가 핵심 사건보다 과도하게 강조된 결과
- 같은 사건이 source별로 따로 분리된 결과
- 사용자가 읽어도 `이날 어떤 하루를 보냈는지` 알 수 없는 결과

## 3.5 7월 31일 목표 수준

해당 입력에서는 최종적으로 다음 중심 흐름이 드러나야 한다.

> 대구에서 출발해 서울로 이동한 뒤, 공덕·마포 인근에서 소마 369팀 회의와 프로젝트 작업을 진행한 날.

# 4. Location Agent 개선

## 4.1 핵심 역할

Location Agent는 STAY와 MOVEMENT를 각각 문장으로 변환하는 Agent가 아니다.

하루 위치 데이터 전체를 보고 다음을 추론해야 한다.

- 어디서 출발했는가
- 어디에서 어디까지 이동했는가
- 여러 이동 구간이 하나의 여정인가
- 이동 중간의 짧은 STAY가 실제 방문인지 센서 분절인지
- 서로 다른 이동 사이의 시간 공백 동안 체류했을 가능성이 있는가
- 최종적으로 어디에 얼마나 머물렀는가
- 나갔다가 돌아온 흐름인지
- 장거리 이동, 지역 간 이동, 환승 또는 귀가 흐름인지

## 4.2 Location Agent 프롬프트에 추가할 핵심 문구

> 개별 STAY와 MOVEMENT를 독립적으로 해석하기 전에 하루의 위치 기록 전체를 시간순으로 검토한다. 여러 이동과 짧은 체류가 하나의 연속된 여정을 가리키면 출발지와 최종 도착지 중심의 하나의 이동 candidate로 병합한다.

> 서로 다른 MOVEMENT 사이에 시간 공백이 있고 그 구간에 명시적인 이동 기록이 없다면, 이전 도착지 또는 다음 출발지에서 체류했을 가능성을 검토한다. 단, 센서 누락 가능성을 고려해 근거보다 강하게 확정하지 않는다.

> 중간 STAY가 짧고 전체 경로가 한 방향으로 이어지며 최종적으로 다른 지역이나 교통 거점에 도착하면, 중간 STAY를 실제 방문보다 이동 중 위치 분절로 판단할 수 있다.

> 시간, 거리, 좌표 변화, 출발지, 도착지, 이동 수단, 전후 흐름을 함께 분석한다. 센서의 transport 라벨이 현실적으로 불가능하면 해당 라벨을 그대로 믿지 않는다.

## 4.3 Location Agent가 생성해야 하는 후보 수준

나쁜 출력:

- 대전에서 차량 이동
- 화성에서 잠깐 체류
- 금천구에서 도보 이동

좋은 출력:

- 대구에서 서울역까지 장거리 교통수단으로 이동한 여정
- 서울역 도착 후 공덕·도화동 방향으로 이동
- 오전까지 주거지로 보이는 장소에 머물다가 외출

## 4.4 Location Agent 검증용 코드 요구사항

프롬프트만으로 처리하지 않고 아래 항목은 코드에서 계산하거나 검증 정보를 제공한다.

### 필수 전처리

- 모든 STAY와 MOVEMENT 시간순 정렬
- 이동별 거리와 소요시간 계산
- 평균 속도 계산
- 이동수단과 평균 속도의 현실성 검사
- 이전 도착지와 다음 출발지의 위치 차이 계산
- 연속 MOVEMENT 사이의 시간 공백 계산
- 짧은 중간 STAY 표시
- 출발지와 최종 도착지의 도시·지역 변화 표시

### Agent 입력에 추가하면 좋은 값

```json
{
  "durationMinutes": 12,
  "averageSpeedKmh": 68.4,
  "isTransportAnomalous": false,
  "gapFromPreviousMinutes": 8,
  "isShortIntermediateStay": true,
  "regionChanged": true
}
```

### 검증 코드

- 장거리 이동 raw가 여러 개 존재하지만 상위 여정 candidate가 없는 경우 경고
- 물리적으로 불가능한 WALKING/IN_VEHICLE 분류를 그대로 사용한 경우 경고
- 모든 이동 rawId가 candidate 또는 fragment 중 어디에도 포함되지 않은 경우 오류
- 중간 짧은 STAY가 여러 개의 독립 방문 candidate로 생성된 경우 검토 요청

# 5. Notification Event Agent 개선

## 5.1 핵심 역할

Notification Event Agent는 알림을 단순 수신 기록으로 나열하지 않고, 예약·결제·업무·소통 등 사용자의 하루와 관련된 사건 후보와 맥락으로 해석한다.

알림은 종류에 따라 의미가 다르다. 결제·예약·교통·업무 알림은 실제 행동과 직접 연결될 가능성이 높고, 메신저 알림은 상대가 보낸 메시지라는 한계를 가지지만 반복 연락, 구체적인 주제, 관계 맥락, 사용자 열람·응답 근거가 있으면 소통 자체가 의미 있는 하루 사건이 될 수 있다.

## 5.2 Notification Event Agent 프롬프트에 추가할 핵심 원칙

- 메신저 알림은 상대가 보낸 메시지이며 사용자 발신·답장을 직접 증명하지 않는다. 그러나 소통을 무조건 약한 단서로만 취급하지 않는다. 반복 연락, 구체적인 주제, 관계 맥락, 사용자 열람·응답 근거가 있으면 소통 자체를 의미 있는 candidate로 만들 수 있다.
- 같은 상대·대화방·주제의 알림은 하나의 소통 흐름으로 묶을 수 있다. 다만 비연속 메시지를 몇 시간 동안 계속된 연속 활동으로 표현하지 않는다.
- 결제, 송금, 예약, 교통, 업무 알림은 실제 행동과 연결될 가능성이 높은 근거로 우선 검토한다.
- 메신저 알림의 `title`에 명시된 값은 기본적으로 보낸 사람 또는 대화방 이름으로 해석한다. 이 사람과의 관계가 User Memory에 등록되어 있지 않으면 관계를 임의로 만들지 않고 입력에 있는 이름을 그대로 사용한다.
- 메신저 알림의 `text`를 통해 어떤 내용의 소통이 이루어졌는지 추론한다. 예: 단순 안부, 업무, 일정 조율, 정산, 식사, 예약, 이동 관련 소통.
- 동일한 사람에게서 여러 메시지가 왔더라도 사용자의 답장 근거가 없으면 `대화를 주고받았다`고 단정하지 않는다. 대신 `연락이 이어졌다`, `관련 메시지를 받았다`, `소통 정황이 있었다`처럼 근거 범위에 맞게 표현한다.
- 소통의 내용과 반복성이 충분하고 사용자의 하루에서 의미가 크다면 독립 candidate가 될 수 있다. 그렇지 않으면 관련 일정이나 활동을 보강하는 fragment로 남긴다.
- JWT, 인증 토큰, 개인정보 등 민감한 본문은 복사하거나 최종 일기에 노출하지 않는다. 필요한 경우 `개발 관련 인증 정보가 공유됨`처럼 민감 내용을 제거한 수준으로만 요약한다.

## 5.3 Candidate와 Fragment 판단 기준

### Candidate로 고려할 수 있는 경우

- 예약 확정, 결제 완료, 송금, 교통 일정처럼 실제 행동과 직접 연결되는 알림
- 업무 지시, 회의 조율, 일정 변경처럼 하루의 행동에 영향을 준 소통
- 같은 상대와 구체적인 주제로 반복된 연락이 있고, 사용자 열람·응답 또는 다른 근거가 함께 있어 소통 자체가 의미 있는 사건으로 볼 수 있는 경우

### Fragment로 남길 경우

- candidate로 확정하기에는 약하지만 다른 사건의 맥락을 설명할 수 있는 메시지
- 진행 중인 회의·업무·프로젝트를 보강하는 Discord 또는 메신저 알림
- 식사나 공동 비용 가능성을 암시하지만 그 성격을 확정할 수 없는 정산 요청
- 관계나 주제가 불분명한 짧은 연락

Notification fragment도 다른 Event Agent의 fragment와 마찬가지로 candidate에 포함되지 않은 raw item을 보존한 가장 낮은 우선순위의 단서로 취급한다. Timeline Agent는 이를 독립 event로 우선 생성하지 않고, 관련 candidate의 사람·주제·목적·confidence를 보강하는 근거로 사용할 수 있다.

## 5.4 Notification 검증 코드 요구사항

- 메신저 알림의 `title`, `text`, 앱 정책을 기준으로 발신자·대화방·주제를 구조화한다.
- 같은 상대·대화방·주제의 알림을 그룹화하되 각 메시지의 실제 시각은 보존한다.
- 비연속 메시지를 하나의 긴 연속 시간 구간으로 저장하지 않는다.
- 각 Notification raw item이 candidate, fragment, noise 중 하나의 상태를 갖는지 확인한다.
- candidate에 포함되지 않은 유효 알림이 이유 없이 유실되지 않았는지 확인한다.
- 민감한 토큰, 개인정보, 인증 문자열이 candidate, fragment, 최종 event 설명에 노출되지 않았는지 검사한다.
- User Memory에 없는 관계명이 임의로 생성되지 않았는지 검사한다.
- Notification fragment가 최종 event의 근거로 사용되었으면 해당 rawId가 `sourceRefs`에 포함됐는지 확인한다.

# 6. Repair Agent 개선

## 6.1 핵심 역할

Repair Agent는 시간, rawId, 중복만 확인하는 Agent가 아니다.

Timeline Agent가 Laimory의 high-level vision에 맞게 사용자의 하루를 충분히 복원했는지 검증하는 최종 품질 관리자다.

## 6.2 Repair Agent 프롬프트에 추가할 핵심 문구

> Timeline Agent의 결과를 단순한 데이터 정합성 관점에서만 검토하지 않는다. 이 결과가 candidate와 fragment를 종합해 사용자의 실제 하루를 일기처럼 충분히 설명하는지 검증한다.

> 결과만 읽었을 때 사용자가 언제, 어디서, 누구와, 무엇을, 어떻게, 왜 했는지가 근거가 허용하는 범위에서 드러나는지 확인한다.

> 가장 중요한 이동, 중심 일정, 주요 체류가 누락됐는지 확인하고, 작은 단서만 나열되어 하루의 중심 서사가 사라지지 않았는지 검증한다.

## 6.3 Repair Agent high-level 검증 질문

- 이 결과만 읽어도 이날 어떤 하루였는지 이해할 수 있는가?
- 출발, 주요 이동, 목적지, 중심 활동이 자연스럽게 연결되는가?
- 핵심 candidate가 빠지고 낮은 우선순위 fragment만 과도하게 강조되지 않았는가?
- 동일한 사건이 source별로 분리되지 않았는가?
- 사건 설명이 단순 위치·데이터 기록 수준에 머물지 않았는가?
- 근거가 충분한데도 지나치게 소극적으로 표현하지 않았는가?
- 반대로 근거가 부족한 내용을 과도하게 확정하지 않았는가?
- 사용자가 읽고 수정할 수 있는 자연스러운 일기체인가?

## 6.4 Repair Agent 도구 사용 요구사항

다음 문제가 있으면 해당 도구를 사용해야 한다.

- Location 상위 여정이 누락됨 → `rerun_event_agent(Location)`
- 후보는 충분하지만 중심 서사가 잘못 구성됨 → `rerun_timeline_agent`
- 개별 event의 문장·시간·중요도만 잘못됨 → `update_event`
- 근거 없이 생성된 event → `delete_event`
- 관련 event가 불필요하게 분리됨 → 병합 도구 또는 Timeline 재실행

전체 Timeline 재실행은 핵심 서사 자체가 잘못된 경우에만 사용한다.

# 7. Photo 검증 요구사항

사진은 사용자가 직접 선택해 입력하는 방식으로 변경되었으므로, 선택된 사진은 모두 의도적으로 포함된 중요한 입력으로 간주한다.

따라서 모든 선택 사진은 최종 처리 상태가 추적되어야 한다.

## 7.1 필수 검증

- 사용자가 선택한 사진 수 기록
- Vision 처리에 전달된 사진 수 확인
- description이 생성된 사진 수 확인
- Photo Event Agent 입력 및 출력 수 확인
- 각 사진 rawId가 candidate 또는 fragment에 포함됐는지 확인
- 각 사진 rawId가 최종 Timeline event의 `sourceRefs`에 포함됐는지 확인
- UI에서 사진이 표시되는 대표 event가 지정됐는지 확인
- 동일 사진이 여러 event UI에 중복 표시되지 않는지 확인

## 7.2 실패 처리

선택된 사진이 최종 event 근거로 사용되지 않았다면 다음 중 하나의 상태를 반드시 남긴다.

- `USED_IN_EVENT`
- `MERGED_AS_FRAGMENT`
- `VISION_FAILED`
- `EVENT_AGENT_FAILED`
- `EXCLUDED_WITH_REASON`
- `REQUIRES_USER_REVIEW`

이유 없이 선택 사진이 사라지는 상태를 허용하지 않는다.

# 8. Candidate와 Fragment 정의

## 8.1 Candidate

Candidate는 해당 Event Agent가 독립적인 하루 사건으로 제안할 만큼 의미와 근거가 충분한 결과다.

예:

- 대구에서 서울로 이동
- 소마 369팀 정기 회의 일정
- 음식 사진을 근거로 한 저녁 식사 후보
- 예약 확정 알림을 근거로 한 일정 후보

## 8.2 Fragment

Fragment는 **candidate에 포함되지 않은 raw item을 보존한 낮은 우선순위의 근거 조각**이다.

Fragment는 다음 특징을 갖는다.

- 독립 event candidate를 만들기에는 근거가 약하다.
- candidate에 사용되지 않은 유효 raw item을 잃지 않기 위해 저장한다.
- Timeline Agent가 다른 candidate의 의미, 시간, 장소, 사람, 목적, confidence를 보강하는 데 사용할 수 있다.
- 기본 우선순위는 candidate보다 낮다.
- 광고, 중복, 명백한 노이즈는 fragment로도 남기지 않아도 된다.

예:

- 회의 시간대에 도착한 Discord 개발 메시지
- 식사 가능성을 암시하지만 단독으로 확정하기 어려운 결제 요청
- 같은 사람에게서 반복적으로 수신된 짧은 메시지
- 이동 candidate에 포함되지 않은 약한 위치 조각

## 8.3 Event Agent 프롬프트 요구사항

모든 Event Agent 프롬프트에 다음 정의를 동일하게 추가한다.

> Candidate는 독립적인 하루 사건으로 제안할 수 있을 만큼 의미와 근거가 모인 결과다.

> Fragment는 candidate에 포함되지 않은 나머지 유효 raw item을 보존한 낮은 우선순위의 단서다. 독립 사건으로 확정하기에는 약하지만 Timeline Agent가 다른 candidate의 의미·시간·장소·사람·목적·confidence를 보강하는 데 사용할 수 있다.

> Candidate의 sourceRefs에 이미 포함된 raw item을 동일한 의미의 fragment로 중복 저장하지 않는다.

> Candidate에 포함되지 않았고 명백한 노이즈도 아닌 raw item은 가능한 한 fragment로 남긴다.

## 8.4 Timeline Agent의 Fragment 사용 규칙

- candidate를 우선 검토한다.
- fragment는 우선 독립 event로 만들지 않는다.
- 시간·장소·주제가 맞는 candidate의 보조 근거로 연결한다.
- fragment를 사용하면 해당 rawId를 최종 event의 `sourceRefs`에 포함한다.
- 여러 fragment가 함께 하나의 의미 있는 사건을 충분히 설명할 때만 새로운 event로 승격한다.
- fragment 수가 많다는 이유만으로 독립 event를 만들지 않는다.
- 사용되지 않은 fragment는 최종 event에 억지로 넣지 않는다.

## 8.5 Fragment 검증 코드

- 각 raw item이 candidate, fragment, noise 중 하나의 상태를 갖는지 확인
- 같은 rawId가 동일 의미의 candidate와 fragment에 중복 포함되지 않았는지 확인
- candidate에 포함되지 않은 유효 raw가 이유 없이 유실되지 않았는지 확인
- Timeline에서 fragment를 근거로 사용했는데 sourceRefs가 누락되지 않았는지 확인
- 낮은 우선순위 fragment만으로 핵심 event가 생성된 경우 Repair 검토 대상으로 표시

# 9. 구현 우선순위

이번 단계에서는 다음 순서로만 수정한다.

## 1순위 — 프롬프트

1. Timeline Agent high-level mission 강화
2. Location Agent의 상위 이동·체류 흐름 추론 규칙 추가
3. Repair Agent의 high-level 일기 품질 검증 추가
4. Notification Event Agent의 소통·결제·예약 해석 원칙 추가
5. 모든 Event Agent 및 Timeline Agent에 candidate/fragment 정의 통일

## 2순위 — 검증 코드

1. Location 시간·거리·속도·공백 전처리
2. 장거리 이동 candidate 누락 검사
3. 선택 사진 전체 처리 상태 검사
4. raw item의 candidate/fragment/noise 상태 추적
5. Notification 그룹화·민감정보·관계명 검증
6. fragment sourceRefs 보존 및 중복 검사

## 이번 단계에서 하지 않는 것

- Agent 구조 전면 재설계
- 새로운 Agent 추가
- 모든 데이터 유형의 프롬프트 전면 수정
- 중요도 시스템의 대규모 스키마 변경
- Sleep/Activity 기능 개선

Sleep/Activity Agent는 현재 비활성화 대상으로 별도 처리한다.

# 10. 완료 기준

다음 조건을 만족하면 이번 핵심 개선이 완료된 것으로 본다.

- Timeline 결과가 candidate 목록이 아니라 하루의 중심 서사를 가진 일기처럼 읽힌다.
- 최종 event 설명에서 가능한 범위의 육하원칙이 드러난다.
- Location Agent가 여러 이동·체류 raw를 상위 여정과 체류 흐름으로 복원한다.
- 7월 31일 입력에서 대구→서울 이동이 하나의 핵심 여정으로 생성된다.
- Timeline Agent가 소마 일정을 전후 이동과 연결해 중심 활동으로 표현한다.
- Repair Agent가 핵심 이동 누락이나 카드 나열식 결과를 문제로 판단한다.
- 사용자가 선택한 모든 사진의 처리 상태가 추적되고 이유 없이 누락되지 않는다.
- Notification Agent가 발신자·대화방·주제를 올바르게 해석하고, 수신과 양방향 대화를 구분한다.
- 의미 있는 소통은 candidate로 만들 수 있고, 약한 알림은 fragment로 보존된다.
- JWT·인증 토큰·개인정보가 최종 일기에 노출되지 않는다.
- Candidate에 포함되지 않은 유효 raw가 fragment로 보존된다.
- Timeline Agent가 fragment를 낮은 우선순위의 보조 근거로 올바르게 활용한다.
- Fragment가 사용된 최종 event에는 해당 rawId가 sourceRefs로 보존된다.
