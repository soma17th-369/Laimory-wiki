# Laimory 중간보고서 피드백 반영안

## 문서 취급 원칙

- Google Docs 원문은 수정하지 않았다.
- 2026-08-16에 읽기 전용으로 확인한 내보내기본을 기준으로 위치를 표시했다.
- 모든 위치는 문서 하단에 인쇄된 실제 페이지 번호만 사용한다.
- 이 파일은 교체 문안과 의사결정을 검토하기 위한 초안이다. 승인 전에는 `wiki/`에 인제스트하지 않는다.

## 먼저 확정할 결론

1. 개인정보 설명의 기준 문장은 `원본이 아닌 요약·인덱스만 AI 서버에 전달`이 아니다. 현재 구조에서는 사진·위치·일정·건강·알림의 작업별 source item을 AI 서버가 가져와 분석하고, 사진은 멀티모달 모델이 처리할 수 있다. 대신 `사용자 선택`, `목적에 필요한 최소 범위`, `작업 단위 접근`, `AI 서버 비영속`, `외부 모델 전송 전 고지·동의·마스킹`을 일관된 보호 원칙으로 써야 한다.
2. 회고 기능을 제품 범위에서 제외했다면 현재의 `첫 일간 회고 완료`를 First Value Action과 KPI로 유지할 수 없다. 권장 First Value Action은 `첫 타임라인을 확인하고 자신의 기록으로 확정·저장함`이다.
3. 목표 추적은 별도 할 일 관리 기능으로 전면에 두지 않는다. 일간 타임라인의 품질과 반복 사용이 검증된 뒤, 축적된 기록에서 사용자가 정한 목표와 관련된 행동의 근거를 보여주는 선택적 확장 기능으로 둔다.
4. 장기 가치는 AI가 의미 있는 회고를 대신 제공하는 데 두지 않는다. `기억 복원 → 비교 → 검색 → 선택적 목표 근거`처럼 축적된 사실을 다시 쓸 수 있게 하는 데 둔다.
5. 시장·가격·운영비는 모두 `무엇을, 어느 지역·플랜에서, 언제 확인했는지`를 함께 적는다. 현재 확인되지 않는 수치는 삭제하거나 검증 대기로 표시한다.

## 2. 개인정보 설명 통일안

### 현재 모순의 원인

12페이지의 `AI 서버 전송 시 원본이 아닌 요약·인덱스 형태로만 전달`은 10페이지와 13~16페이지의 구현 설명과 맞지 않는다. 현재 구조 문서에 따르면 App Server는 사용자가 선택한 source를 보유하고, AI Server는 `taskId`와 작업용 token으로 해당 작업의 source item을 가져와 처리한다. 사진은 멀티모달 모델의 입력이 될 수 있으므로 `원본은 전혀 전송되지 않는다`고 일괄 표현하면 안 된다.

### 보고서 전체에서 사용할 정본 데이터 흐름

```text
Android 앱
  - 사용자가 허용한 권한 범위에서 생활 데이터를 수집
  - 사용자가 타임라인 생성에 사용할 항목을 선택
        ↓
App Server
  - 선택된 사진·위치·일정·건강·알림 source를 검증·전처리·보관
  - 타임라인 작업에 필요한 source만 작업 단위 공간에 구성
        ↓ taskId + 작업용 token
AI Server
  - 현재 작업에 필요한 source item만 임시 조회·분석
  - 필요 시 선택된 상용 LLM에 최소 필드를 전달
  - 결과를 App Server에 반환하고 제품 source를 영속 저장하지 않음
        ↓
App Server → Android 앱
  - 생성 결과 저장·전달
  - 사용자가 수정·삭제·확정
```

### 12페이지 교체 문안

> 사진·위치·일정·건강·알림 데이터는 사용자가 권한을 허용하고 타임라인 생성에 사용하도록 선택한 범위에서만 App Server로 전송한다. App Server는 현재 생성 작업에 필요한 source item만 작업 단위로 구성하며, AI Server는 taskId와 제한된 작업용 token으로 해당 source를 임시 조회해 분석한다. AI Server는 생활 데이터 원본과 제품 기록을 영속 저장하지 않고 생성 결과만 App Server에 반환한다. 외부 LLM 호출이 필요한 경우에는 처리 항목·목적·수신자·보유 기간을 고지하고 동의를 받은 뒤, 전화번호·이메일 등 불필요한 식별정보를 마스킹하고 목적에 필요한 최소 필드만 전달한다.

### 페이지별 맞춤 수정

- 7페이지 `개인정보 전략`: 정규식 마스킹만으로 충분하다고 쓰지 말고, 사용자 선택·작업 단위 최소화·외부 제공 고지·민감정보 로깅 금지를 함께 적는다.
- 10페이지: `AI 서버가 데이터를 받는다`보다 `task source를 임시 조회한다`로 App Server와 AI Server의 책임을 구분한다.
- 13페이지: `수집된 데이터`가 아니라 `권한이 허용되고 사용자가 타임라인 생성에 선택한 데이터`라고 쓴다.
- 14페이지: 작업 token의 목적, 만료, 현재 task 범위 제한을 명시한다.
- 15~16페이지: PHOTO가 멀티모달 LLM으로 전달될 수 있다는 사실을 개인정보 절과 동일하게 쓴다.

### 보고서에 넣지 말아야 할 표현

- `모든 개인 데이터는 기기 내에서만 처리된다.`
- `사진·위치 등 원본 데이터는 서버나 AI에 전송되지 않는다.`
- `요약·인덱스만 AI에 전달된다.`
- `AI 서버가 개인정보를 저장하지 않으므로 외부 모델에도 개인정보가 전달되지 않는다.`

마지막 문장은 AI Server의 비영속성과 외부 모델 제공 범위를 혼동한다. 외부 모델이 실제로 보는 필드는 별도로 밝혀야 한다.

| `claude fable 5` | 공식 모델은 있으나 표기 부정확 | `Claude Fable 5` 또는 API ID `claude-fable-5` |

| `GPT 4.0 mini` | 공식 표기 아님 | 의도한 모델이 맞다면 `GPT-4o mini` |
| `Bedrock(GPT 4.0 mini)` | 서비스·모델·과금 경로가 혼재 | 실제 경로에 따라 `OpenAI API — GPT-4o mini`, `Amazon Bedrock — Amazon Nova 2 Lite`, 또는 현재 Bedrock에서 실제 선택한 모델로 표기 |
| `AgentCore Runtime + Bedrock(...)` | 실행 환경 비용과 모델 추론 비용 혼재 | `AgentCore Runtime`과 `Bedrock 모델 추론`을 별도 비용 행으로 분리 |

### 7페이지 개발환경 표 교체안

개발 생산성 도구와 제품 런타임 모델을 한 행에 넣지 않는다.

| 구분 | 사용 환경 | 모델·상태 |
|---|---|---|
| 개발 보조 AI | Codex·ChatGPT·Claude Code 등 실제 사용 도구 | 실제 사용 이력으로 확인된 모델만 정확한 공식명으로 기재 |
| 서비스 AI Provider | OpenAI API, Gemini API, Amazon Bedrock 공통 provider interface | 후보 모델을 평가 중이며 운영 모델은 아직 확정하지 않았다고 표시 |
| 현재 AI Server Runtime | AWS EC2 기반 Docker 배포 | 현재 운영 구조 |
| 향후 Runtime 후보 | Amazon Bedrock AgentCore Runtime | 전환 검토·수동 배포 경로, 미완료 상태 |

개발 도구 행의 권장 문장:

> 코드 작성·리뷰·문서화에 생성형 AI 도구를 활용했으며, 문제 정의·아키텍처·품질 기준·최종 검증은 팀이 수행했다. 제품에서 사용자 데이터를 처리하는 서비스 모델과 개발 보조 모델은 별도로 관리한다.

### 17페이지 서비스 모델 후보 표기안

> 동일한 평가 fixture에서 품질, 구조화 출력 성공률, source 충실도, 이미지 처리, p50·p95 지연시간, task당 실제 token·비용을 비교해 운영 모델을 선정한다. 후보 예시는 `OpenAI API — GPT-4o mini`, `Gemini API — Gemini 2.5 Flash`, `Amazon Bedrock — Amazon Nova 2 Lite`이며, 후보라는 사실과 실제 운영 선택을 구분한다.

후보를 바꾸면 보고서의 7페이지, 17페이지, 25페이지 세 곳을 동시에 바꿔야 한다.

### 18·25페이지 인프라 정리안

- 현재 3개월 비용표에는 현재 사용하는 EC2 AI Server 비용을 넣는다.
- AgentCore 전환이 3개월 안에 확정된 계획이 아니라면 현재 비용 합계에서 제외하고 `향후 시나리오`로 분리한다.
- AgentCore를 넣는다면 Runtime의 active vCPU-hour·GB-hour와 모델 추론 token 비용을 별도 계산한다.
- `개발용 AI 서버`가 EC2 API 서버 비용 행 또는 AgentCore Runtime 비용과 중복되지 않는지 확인한다.

### 25페이지 운영비

현재 인프라 네 행의 합은 271.6만 원이고 3개월 월평균은 약 90.5만 원이다. 이 산술은 맞지만 각 행의 산정 근거가 부족하다.

각 비용 행에 다음 가정을 각주 또는 부록으로 붙인다.

| 비용 | 반드시 적을 가정 |
|---|---|
| API 서버·인프라 | Region, instance type·대수, 월 실행시간, Load Balancer, data transfer, 산정 기간 |

| AI Runtime | 현재 EC2인지 AgentCore인지, CPU·memory·active time, 중복 계상 여부 |
| 모니터링 | EC2/EBS, 로그 ingest GB, retention, CloudWatch 등 실제 사용 서비스 |

LLM 비용은 `회당 70원`을 먼저 정하지 말고 다음 식으로 산정한다.

```text
월 LLM 비용
= 월 타임라인 수
  × 타임라인당 각 모델 호출의 합계
    [(평균 input token × input 단가 + 평균 output token × output 단가) / 1,000,000]
  × 기준 환율
  × (1 + 재시도율)
```

2026-08-16 공식 가격 예시:

- OpenAI API의 GPT-4o mini: 1M input token당 $0.15, output token당 $0.60.
- Gemini API의 Gemini 2.5 Flash Standard: 1M text·image·video input token당 $0.30, output token당 $2.50.
- AgentCore Runtime: active vCPU-hour당 $0.0895, active GB-hour당 $0.00945. 모델 추론비는 별도다.

실제 trace에서 호출 수·token·vision 사용량을 뽑기 전에는 75.7만 원을 확정치가 아니라 `예비 시나리오`로 표시한다.

## 5. 목표 설정 기능을 설득력 있게 배치하는 방법

### 왜 현재는 뜬금없어 보이는가

- 사용자 문제는 `흩어진 하루를 쉽게 복원하고 기록한다`인데 목표 기능은 갑자기 자기계발·할 일 관리 문제로 이동한다.
- First Value Action과 KPI는 회고 완료에 맞춰져 있고 목표 기능의 가치 행동은 연결되지 않는다.
- 타임라인의 정확성과 반복 사용이 검증되기 전에 목표 추적을 MVP에 넣으면 제품의 성공 조건이 두 개가 된다.
- 목표와 생활 데이터의 관계를 AI가 임의로 판단하면 잘못된 성장 서사를 만들 수 있다.

### 권장 포지셔닝

> 목표 추적은 별도의 할 일 관리 기능이 아니라, 사용자가 직접 정한 방향을 렌즈로 삼아 축적된 일상 기록에서 관련 행동의 근거를 다시 찾게 해주는 확장 기능이다.

핵심 흐름:

```text
일간 타임라인을 확정한다
→ 기록이 일주일·한 달 쌓인다
→ 사용자가 선택한 목표와 관련 있어 보이는 장면을 후보로 보여준다
→ 사용자가 관련 있음·없음을 확인한다
→ 주·월 단위로 실제 행동의 근거와 변화를 확인한다
```

이 기능은 목표 달성 여부를 AI가 판정하지 않는다. 관련 행동 후보와 근거가 된 타임라인 장면을 보여주고 사용자가 최종 확인한다.

### 권장 범위 결정

#### 권장안: MVP 이후 확장

- 4페이지의 `일상 기반 목표 추적`을 `축적 기록 기반 변화 확인(확장 기능)`으로 바꾼다.
- 9페이지의 MVP 범위를 `일간 타임라인 생성·확인·수정·확정`으로 좁힌다.
- 목표 기능은 `타임라인 품질과 D7 반복 사용 검증 후` 개발하는 2단계로 적는다.

#### 목표 기능을 반드시 MVP에 남길 경우

- 목표 등록은 한 개만 허용한다.
- 사용자가 확정한 타임라인만 근거로 쓴다.
- AI는 관련 행동 후보만 제안하고 사용자가 확인한다.
- 목표 알림 클릭률이 아니라 `근거 확인률`, `관련성 승인율`, `목표 근거를 본 뒤 타임라인 재확정률`을 측정한다.

## 6. 회고를 대신할 장기 누적 가치

### 제품의 장기 가치 한 문장

> 하루의 기록은 그날을 남기지만, 축적된 기록은 잊힌 순간을 다시 찾고 이전과 지금의 변화를 비교하며 내가 실제로 해온 선택을 확인할 수 있는 개인 기억 자산이 된다.

### 반복 방문의 이유

| 축적 기간 | 사용자가 받는 가치 | 기능 예시 | 재방문 이유 |
|---|---|---|---|
| 하루 | 흩어진 흔적을 하나의 기록으로 확정 | 수정 가능한 일간 타임라인, 오늘의 한 장면 선택 | 오늘을 잃지 않고 마무리하기 위해 |
| 일주일 | 최근 기억 중 남길 장면을 다시 발견 | 이번 주 기억 3개, 사용자가 하나 선택·메모 | 한 주가 지나기 전에 중요한 순간을 붙잡기 위해 |
| 한 달 | 이전 기간과 달라진 사실을 비교 | 자주 간 장소·활동 시간·일정 유형 변화와 근거 장면 | 막연한 인상이 아니라 실제 기록으로 변화를 확인하기 위해 |
| 6개월 | 과거 경험을 검색하고 복원 | `마지막으로 누구와 어디에 갔지?`, 날짜·장소·사진 기반 기억 검색 | 필요할 때 자신의 과거를 다시 꺼내 쓰기 위해 |
| 선택 기능 | 목표와 관련된 행동 근거를 확인 | 목표 관련 장면 후보와 사용자 확인 | 선언한 목표가 실제 생활에 어떻게 나타났는지 확인하기 위해 |

### 유의미한 회고를 과장하지 않는 대안

1. **기억 다시 보기**: 같은 날짜, 같은 장소, 최근 잊고 있던 장면을 source와 함께 보여준다.
2. **주간 기억 선택**: AI가 의미를 단정하지 않고 이번 주의 후보 장면 3개를 제시해 사용자가 하나를 고른다.
3. **사실 기반 변화 비교**: 장소·활동·시간 분포의 전월 대비 차이를 보여주되 원인·감정을 추론하지 않는다.
4. **개인 기록 검색**: 사진·위치·일정과 사용자가 확정한 문장으로 과거 사건을 찾는다.
5. **사용자 주도 질문**: AI가 `무슨 의미였나요?`를 대신 답하지 않고 특정 장면에 대한 한 문장 질문만 제공한다.
6. **선택적 목표 근거**: 목표 관련성을 사용자가 승인한 장면만 누적한다.

제품의 역할은 `회고를 대신해 주는 AI`보다 `기억은 찾아주고, 의미는 사용자가 붙이게 하는 도구`로 정의하는 편이 현재 구현과 신뢰 원칙에 맞다.

### 25~26페이지 기대효과 교체 문안

> Laimory는 첫날에는 사진·위치·일정 등 흩어진 흔적을 수정 가능한 타임라인으로 만들어 기록 시작의 부담을 낮춘다. 기록이 일주일 쌓이면 사용자는 놓칠 뻔한 장면을 다시 선택해 남길 수 있고, 한 달 이상 쌓이면 이전 기간과 달라진 장소·활동·일정의 사실을 근거 기록과 함께 비교할 수 있다. 장기적으로는 날짜·장소·사진·사용자 메모를 바탕으로 과거 경험을 검색하고 복원할 수 있어, 데이터가 단순 저장량이 아니라 다시 사용할 수 있는 개인 기억 자산이 된다. 목표 기능은 이 기록을 사용자가 정한 방향으로 다시 보는 선택적 확장으로 제공한다.

### 28페이지 반복 방문 답변 교체 문안

> 반복 방문은 알림 자체가 아니라 기록이 쌓일수록 생기는 활용 가치로 만든다. 사용자는 매일 자동 생성된 하루를 자신의 기록으로 확정하고, 매주 놓친 장면을 다시 선택하며, 매월 이전 기간과 달라진 사실을 근거 기록과 함께 비교한다. 충분히 축적된 뒤에는 과거 경험 검색과 선택적 목표 근거 확인으로 확장한다. 개인화 질문과 알림은 이 가치에 도달하도록 돕는 수단이며, 그 자체를 리텐션 가치로 보지 않는다.

## 7. First Value Action과 Time to First Value

### 21페이지 First Value Action 교체 문안

> Laimory의 첫 가치 행동(First Value Action)은 사용자가 처음 생성된 타임라인을 확인하고, 필요한 경우 사실 오류를 수정하거나 불필요한 항목을 삭제한 뒤 자신의 첫 하루 기록으로 확정·저장하는 것이다. 권한 동의와 타임라인 생성은 준비·기능 실행 단계이며, 사용자가 결과를 확인하고 자신의 기록으로 받아들여야 핵심 가치인 `기록 부담 감소와 하루 기억 복원`을 경험했다고 본다. 수정이나 메모 추가는 품질과 참여를 보여주는 보조 행동이지 첫 가치 행동의 필수 조건으로 강제하지 않는다.

측정 흐름:

```text
회원가입 완료
→ 필요한 권한 안내·선택
→ 첫 타임라인 생성 성공
→ 타임라인 열람
→ 첫 타임라인 확정·저장 = First Value Action
```

### 23페이지 KPI 추가 행

| KPI | 정의 | 확인 목적 |
|---|---|---|
| 첫 가치 도달 시간(Time to First Value) | 회원가입 완료 시점부터 첫 타임라인 확정·저장까지 걸린 시간의 중앙값과 75백분위 | 사용자가 얼마나 빨리 핵심 가치를 경험하는지와 권한·생성·확인 단계의 병목 확인 |

평균만 쓰면 일부 장시간 이탈 사용자 때문에 왜곡될 수 있으므로 중앙값과 p75를 함께 본다. 초기 베타에서 기준선을 만든 뒤 개선 목표를 정한다.

### 함께 기록할 단계별 시간

- 회원가입 완료 → 권한 선택 완료
- 권한 선택 완료 → 첫 타임라인 생성 요청
- 생성 요청 → 생성 성공
- 생성 성공 → 첫 열람
- 첫 열람 → 확정·저장

생성 실패 사용자를 TTFV 계산에서 조용히 제외하지 않는다. `First Value 도달률`, 생성 실패율, 미도달자의 단계별 이탈률을 함께 보고한다.

### 23~24페이지 KPI 체계 교체안

| 구분 | 핵심 지표 |
|---|---|
| Acquisition | 광고 클릭률, 설치 전환율, 캠페인별 획득 비용 |
| Activation | 첫 타임라인 확정률, TTFV median·p75 |
| Quality | 타임라인 수정·삭제율, 생성 실패율, 확정 전 수정 부담, 정성 만족도 |
| Retention | 첫 확정 이후 D1·D7·D30에 다시 타임라인을 확정한 비율 |
| Cumulative value | 주간 기억 다시 보기 사용률, 월간 비교 열람률, 과거 기록 검색 성공률 |

단순 앱 재실행이나 푸시 클릭보다 `다시 타임라인을 확정함`을 핵심 리텐션 행동으로 유지한다.

## 9. 팀 확인이 필요한 항목

다음은 문서만으로 확정할 수 없으므로 제출 전에 팀이 답해야 한다.

- 외부 LLM에 사진 원본 또는 이미지 bytes가 직접 전달되는가, 사전 설명문만 전달되는가?

- AI task token의 만료·재사용 방지·scope 제한이 구현됐는가, 설계인가?

- 목표 기능은 중간보고서 시점 MVP인가, 이후 roadmap인가?
- 초기 마케팅 150만 원은 실제 승인된 예산인가? 30만 원 외의 배분은 무엇인가?
- 인프라 비용의 Region·instance·storage·로그 보존·환율 가정은 무엇인가?
- 경쟁 가격 비교는 iOS, Android, Web 중 어느 채널을 기준으로 할 것인가?
